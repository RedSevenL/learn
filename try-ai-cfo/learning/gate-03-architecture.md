# 第三关：设计完整系统边界

> 关卡类型：架构判断  
> 建议用时：45～60 分钟  
> 是否需要编码：否  
> 前置条件：完成第二关，已经形成 MVP、关键约束和延后功能清单  
> 当前状态：待完成

## 一、当前情境

前两关已经回答了两个问题：

1. 产品为谁解决什么问题。
2. 第一版最少需要交付什么。

现在需要回答第三个问题：

> 页面、API、校验、业务规则、数据库、财务计算和 AI 应该怎样分工？

团队提出了几种看似省事的做法：

- 页面提交表单后直接写入 SQLite。
- Route Handler 同时处理请求、校验、数据库查询和全部业务规则。
- 数据库查询后顺便把净资产计算出来。
- 让 AI 读取账户信息并直接回答净资产金额。
- 每个功能都拆成一个独立服务，以便“将来扩展”。

这些方案可能在短期内减少文件数量，却会让职责、测试、错误定位和后续修改变得混乱。

本关不要求写代码。你需要先建立一张完整系统地图，明确每一层负责什么、不负责什么，以及各层之间允许怎样依赖。

## 二、本关目标

完成本关后，你应该能够：

- 从 MVP 和产品约束推导系统需要哪些层。
- 为每层写出“负责什么”和“不负责什么”。
- 判断一段逻辑应该归属页面、API、校验、service、数据库、计算引擎还是 AI。
- 说明类型检查、运行时校验和业务规则的区别。
- 说明为什么页面不能直接访问数据库。
- 说明为什么 AI 不能直接计算财务结果。
- 解释当前为什么采用单体全栈结构，而不是提前拆成多个独立服务。
- 画出模块边界和允许的依赖方向。

## 三、任务

### 任务 1：承接第二关的范围

从第二关复制：

- 最终 MVP 定义。
- 端到端价值路径。
- 已确认的产品约束。
- 暂时采用的假设。
- 当前推演实际编码范围。

架构必须服务已经确定的范围。不要为了展示技术复杂度，设计 MVP 暂时不需要的模块。

### 任务 2：识别系统层级

本产品至少需要考虑以下层级：

| 层级 | 你需要回答的问题 |
| --- | --- |
| 页面和组件 | 用户输入、交互状态和结果展示由谁负责？ |
| Route Handler / API | HTTP 请求和响应的边界在哪里？ |
| Zod schema | 哪些外部输入需要在运行时校验？ |
| service | 业务操作和数据访问怎样被组织？ |
| Drizzle 与 SQLite | 数据怎样持久化和查询？ |
| 确定性财务计算 | 金额公式和中间步骤在哪里执行？ |
| AI 集成 | 自然语言理解和表达在哪里发生？ |

如有必要，可以增加“共享类型”“响应格式”等辅助模块，但必须说明增加它解决了什么问题。

不要直接照抄目录结构。先从职责出发，再考虑模块名称。

### 任务 3：定义每层的职责边界

为每层分别写出：

1. 输入是什么。
2. 输出是什么。
3. 负责什么。
4. 不负责什么。
5. 可以依赖哪些层。
6. 不应该依赖哪些层。

职责描述必须具体。

例如，“负责业务逻辑”仍然过于模糊，需要进一步说明是负责组织账户创建、执行账户唯一性规则，还是负责计算净资产公式。

### 任务 4：完成逻辑归属判断

判断以下逻辑首先应该放在哪一层，并说明理由：

1. 表单提交期间显示 `loading`。
2. 检查请求体是否包含合法的账户名称和余额。
3. 判断账户是否满足创建规则。
4. 查询 SQLite 中未被删除的账户。
5. 对多个账户余额求和，计算净资产。
6. 把“我现在一共有多少钱？”识别为净资产查询意图。
7. 把净资产计算结果组织成自然语言。
8. 将错误转换成合适的 HTTP 状态码和 JSON 响应。
9. 把金额显示成用户可读的格式。
10. 保存一次计算使用的输入、步骤和结果。

某项逻辑可能会经过多个层，但必须指出：

- 哪一层拥有这项规则。
- 其他层只是调用、传递还是展示。

不要用“都可以”“看情况”结束判断。如果确实存在两个合理位置，需要写出选择条件和当前决定。

### 任务 5：区分三类正确性保障

分别说明：

| 保障 | 要解决的问题 |
| --- | --- |
| TypeScript 类型 | 开发和编译阶段能发现什么问题？ |
| Zod 运行时校验 | 外部输入进入系统时要防止什么？ |
| 业务规则与确定性计算 | 数据格式正确后，还需要保证什么？ |

使用“创建账户”或“计算净资产”举例，说明为什么三者不能互相替代。

### 任务 6：画出系统模块图

画一张概念模块图，至少包含：

- 用户。
- 页面和组件。
- API。
- Zod。
- service。
- Drizzle 与 SQLite。
- 确定性计算引擎。
- AI。

图中需要标出：

- 用户从哪里输入和查看结果。
- 哪些模块属于应用内部。
- 哪些属于外部依赖。
- 主要依赖方向。
- AI 与确定性计算之间的边界。

这张图只画模块和边界，不展开每次请求的完整步骤。详细数据流将在第四关完成。

### 任务 7：判断部署与拆分方式

当前候选方案：

#### 方案 A：单体全栈

页面、API、service、计算模块和数据库访问位于同一个 Next.js 项目中，通过代码模块保持边界。

#### 方案 B：提前拆分服务

页面、账户服务、计算服务和 AI 服务分别运行和部署，通过网络通信。

请从以下角度比较：

- 当前用户和流量规模。
- 部署与调试成本。
- 数据隐私。
- 网络故障和接口协调成本。
- 独立扩展的真实需求。
- 学习与交付目标。
- 将来拆分的可能触发条件。

作出当前选择，并说明：

- 为什么它适合当前 MVP。
- 它有哪些局限。
- 什么证据出现后应重新评估。

## 四、约束

- 本关不写业务代码，不创建项目目录。
- 不直接复制知识线项目的目录结构作为答案。
- 不用文件数量或“看起来专业”评价架构。
- 不把所有逻辑都放在 Route Handler。
- 不让页面直接访问数据库。
- 不让数据库查询层拥有财务公式。
- 不让 AI 自由生成应由确定性代码计算的金额。
- 不因为使用 TypeScript 就省略运行时校验。
- 不为了未来可能出现的规模提前拆分微服务。
- 本关只确定模块边界和依赖方向，不展开第四关的数据流步骤。

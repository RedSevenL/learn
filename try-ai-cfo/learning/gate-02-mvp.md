# 第二关：澄清约束并划定完整产品 MVP

> 关卡类型：范围判断  
> 建议用时：40～60 分钟  
> 是否需要编码：否  
> 前置条件：完成第一关，已经选定主要用户、典型场景和核心问题  
> 当前状态：待完成

## 一、当前情境

第一关结束后，你已经把模糊想法整理成了一个相对明确的用户问题。

需求方随后补充了一份愿望清单：

- 管理现金、银行卡和投资账户。
- 记录收入与支出流水。
- 管理信用卡、消费贷等负债。
- 设置储蓄目标。
- 使用 AI 回答财务问题。
- 导入银行或支付平台的 CSV 账单。
- 使用图表展示财务变化。
- 模拟买车、换工作、提前还款等选择。
- 保存计算过程，让用户能够核对结果。
- 将来可以安全地长期使用。

这些能力都可能有价值，但不能因此全部进入第一版。

如果范围过大，你可能花很长时间搭建页面和模块，却始终没有一条真正可使用、可验证的产品路径。如果范围过小，例如只做一个账户录入表单，又无法证明“个人财务 CFO”比普通记事工具更有价值。

你需要先澄清产品约束，再划定一个完整产品 MVP。

## 二、本关目标

完成本关后，你应该能够：

- 说明哪些约束会直接改变产品方案。
- 区分必须确认的事实和暂时采用的假设。
- 按“必须、应该、以后”给功能分级。
- 设计一条能够证明核心价值的端到端路径。
- 区分完整产品蓝图、完整产品 MVP 和当前推演编码范围。
- 使用可观察结果定义“第一版完成”，而不是使用“基本完成”。

## 三、任务

### 任务 1：承接第一关的产品判断

从第一关复制经过审查后的内容：

- 一句话产品目标。
- 主要用户。
- 典型场景。
- 用户需要作出的决定。
- 一个典型财务问题。
- 回答该问题所需的关键数据。

如果第一关仍有影响范围选择的重要未知项，先保留它们，不要在本关偷偷把它们当成已确认事实。

### 任务 2：澄清关键约束

至少判断以下五项约束：

| 约束 | 需要澄清的核心问题 |
| --- | --- |
| 数据位置 | 数据必须只保存在本机，还是允许同步到远程服务？ |
| 用户范围 | 第一版只服务一个本地用户，还是需要账户、登录和多人隔离？ |
| 币种 | 只处理一种币种，还是需要换汇与多币种汇总？ |
| 金额精度 | 金额以什么形式输入、保存、计算和展示？如何避免精度错误？ |
| 隐私与安全 | 哪些数据敏感？哪些数据可以发送给 AI？用户如何知道数据去了哪里？ |

每项约束都要记录：

1. 当前是否已经确认。
2. 如果没有确认，暂时采用什么假设。
3. 这个判断会排除或推迟哪些能力。
4. 判断错误时，未来需要付出什么调整成本。

不要在本关设计数据库或编写安全方案，只需要说明约束如何影响范围。

### 任务 3：给功能分级

把愿望清单中的能力分为三类：

| 级别 | 判断标准 |
| --- | --- |
| 必须 | 缺少它，就无法走通核心场景或验证核心价值 |
| 应该 | 能明显改善可用性或可信度，但暂时缺少仍能完成核心验证 |
| 以后 | 当前价值尚未验证、依赖较多，或不影响第一版闭环 |

每项功能都必须写出分级理由。

不能使用“这个功能很重要”作为理由。你需要说明它与主要用户、典型场景、核心决定或可信结论之间的关系。

功能分级不是永久决定。它只回答：

> 在当前用户、当前场景和当前约束下，第一版最少需要什么？

### 任务 4：设计一条端到端价值路径

从用户开始操作，到用户获得一个可以理解和核对的结论，写出一条完整路径。

这条路径必须同时包含：

1. 必要的数据输入。
2. 一个确定、可信的财务计算。
3. 一个用户能够理解的输出。
4. 一个用户可以继续采取的行动或作出的决定。
5. 一个开发者可以观察和验证的结果。

可以使用下面的空白结构：

```txt
用户处于【具体场景】
  ↓
输入或已有【必要数据】
  ↓
系统执行【明确计算】
  ↓
系统展示【结论与依据】
  ↓
用户据此决定【具体行动】
  ↓
我们通过【可观察证据】确认路径成立
```

不要用“AI 给出专业建议”代替中间的数据、计算和依据。

### 任务 5：划定 MVP 边界

使用三张清单说明范围：

- MVP 内：第一版必须交付。
- MVP 外：有价值，但明确延后。
- 非目标：当前产品方向主动不解决。

然后分别定义：

- 产品完成条件：哪些用户行为和结果出现后，可以说 MVP 闭环已经成立。
- 产品失败条件：出现什么情况，说明这版 MVP 没有证明核心价值。

### 任务 6：区分三种产品范围

分别说明以下三者：

| 范围 | 要回答的问题 |
| --- | --- |
| 完整产品蓝图 | 这个产品长期可能包含什么？ |
| 完整产品 MVP | 最少具备什么，才能验证产品核心价值？ |
| 本轮推演编码范围 | 根据当前知识和练习目标，这一轮实际独立实现什么？ |

完整产品 MVP 可以大于本轮推演编码范围。

例如，某项能力可能属于产品 MVP，但由于当前知识尚未解锁，不进入本轮编码。此时要记录依赖和延后原因，不能假装它不重要，也不能提前进入实现。

## 四、约束

- 本关不编写代码、不创建页面、不设计数据库表。
- 不因为技术已经学过，就自动把相关功能放入 MVP。
- 不因为某个功能有吸引力，就把它当成核心价值。
- 不以页面数量、接口数量或代码量定义 MVP。
- 不使用“支持账户管理”“支持 AI 问答”这类功能描述代替端到端用户路径。
- 不把“以后再优化”当成隐私、金额正确性或结果可信度的处理方式。
- 不要求一次解决所有财务问题；MVP 可以只验证一个代表性问题。
- 不直接复制 `ai-finance-cfo/` 的功能清单作为自己的判断。

## 六、验收标准

提交 Tutor 审查前，逐项检查：

- [ ] 第二关的范围判断能追溯到第一关的主要用户和核心问题。
- [ ] 已判断本地优先、单用户、币种、金额精度和隐私要求。
- [ ] 未确认的约束被标记为假设，没有伪装成事实。
- [ ] 每个“必须”功能都能对应端到端价值路径中的必要一步。
- [ ] 每个“以后”功能都有明确的延后理由。
- [ ] 端到端路径包含数据输入、可信计算、可理解输出和用户决定。
- [ ] 端到端路径没有让 AI 直接产生无法核对的财务数字。
- [ ] 完成条件是可观察、可操作或可验证的。
- [ ] 失败条件能够帮助判断 MVP 是否真正证明了价值。
- [ ] 已明确区分完整蓝图、产品 MVP 和本轮编码范围。
- [ ] 没有用技术模块数量或页面数量代替产品价值。
- [ ] 主动写出了 MVP 外和非目标内容。

本关的最小验证必须同时满足：

1. 必要数据能够进入系统。
2. 系统能够完成一个可信计算。
3. 用户能够理解计算结果和依据。
4. 用户可以据此作出一个明确决定。
5. 开发者能通过具体证据判断这条路径是否成立。

口头验证时，应能不看文档回答：

- 为什么某个功能属于“必须”而另一个属于“以后”？
- 如果移除 AI，这个 MVP 的核心价值是否仍然成立？为什么？
- 为什么完整产品 MVP 不等于本轮要写完的全部代码？

- 初始范围中最重要的过度设计是什么？

# 第四关：画出三条核心数据流

> 关卡类型：数据流与故障定位  
> 建议用时：60～75 分钟  
> 是否需要编码：否  
> 前置条件：完成第三关，已经形成模块图、层级职责和依赖规则  
> 当前状态：待完成

## 一、当前情境

第三关已经确定了系统包含哪些层，以及每层负责什么。

但只有模块图还不够。团队仍然可能对同一项功能产生不同理解：

- 表单数据由谁转换成请求？
- Zod 在页面、API 还是 service 中执行？
- service 返回数据库对象还是计算结果？
- 净资产计算应该在查询数据库时完成，还是交给独立计算函数？
- AI 解析出的意图不合法时，错误从哪里返回？
- 页面没有变化时，应该先检查 React state、请求、API 还是数据库？

现在需要让三个代表性操作真正“流过”系统：

1. 账户 CRUD。
2. 确定性净资产计算。
3. AI 查询净资产。

你需要画出成功路径、失败路径和关键数据形态，并能够沿数据流定位故障。

## 二、本关目标

完成本关后，你应该能够：

- 把第三关的静态模块图转化为动态数据流。
- 标明数据从哪里产生、以什么形式传递。
- 标明每条链路的运行时校验位置。
- 区分读取数据、业务组织和确定性计算。
- 说明错误在哪一层产生、怎样返回用户。
- 根据页面现象选择首先检查的层级和证据。
- 比较三条数据流的共同部分和不同部分。
- 发现数据流与第三关职责边界之间的冲突。

## 三、绘图规则

三条数据流可以使用 Mermaid、ASCII 箭头或表格，但必须保持统一。

每一个关键节点至少标明：

- 层级或模块。
- 收到的输入。
- 执行的动作。
- 产生的输出。
- 可能产生的错误。

每一条关键连线至少能回答：

- 谁把什么数据交给谁？
- 这是函数调用、HTTP 请求、数据库操作还是外部 AI 调用？

建议使用以下节点格式：

```txt
【层级或模块】
输入：
动作：
输出：
失败：
```

不要只写：

```txt
前端 → 后端 → 数据库
```

这种图没有说明数据形态、职责和错误路径，不能用于实现或调试。

## 四、任务

### 任务 1：承接第三关的架构边界

从第三关复制：

- 最终模块图。
- 各层职责。
- 依赖原则。
- AI 与确定性计算的边界。
- 当前仍未确认的架构假设。

本关的数据流必须遵守第三关的边界。如果绘制时发现无法遵守，不要悄悄修改架构，需要记录冲突并说明修改理由。

### 任务 2：定义本关使用的数据形态

在画图之前，先为三条链路列出关键数据形态。

例如可以考虑：

- 用户在表单中输入的数据。
- 发往 API 的 JSON。
- Zod 校验后的数据。
- service 使用的数据。
- 数据库记录。
- 计算函数输入。
- 计算函数输出。
- AI 解析出的结构化意图。
- 返回页面的成功或错误响应。

此处只描述字段含义和数据形态，不要求编写 TypeScript 类型、Zod schema 或数据库表。

同一个业务概念在不同边界上可能具有不同形态。需要说明转换发生在哪里，以及为什么需要转换。

### 任务 3：画出账户 CRUD 数据流

以“创建账户”为主线，画出完整成功路径：

```txt
用户填写表单
  ↓
页面状态
  ↓
HTTP 请求
  ↓
API
  ↓
运行时校验
  ↓
service
  ↓
Drizzle 与 SQLite
  ↓
成功响应
  ↓
页面状态和账户列表更新
```

你的图不能直接照抄上面的概览，必须补充：

- 输入数据在哪里产生。
- 页面进行哪些交互处理。
- 请求体在哪里做运行时校验。
- 账户创建规则由谁负责。
- 数据由谁写入 SQLite。
- 新账户怎样回到页面。
- 页面怎样让用户观察到创建成功。
- 校验失败、写入失败和网络失败怎样返回。

创建账户画完整路径后，再说明以下操作与创建流程的异同：

- 查询账户列表。
- 修改账户。
- 删除账户。

删除操作还需要说明：

- 是物理删除还是软删除。
- 删除后的查询规则。
- 页面如何同步删除结果。

本关只分析数据流，不替第五关决定实际编码顺序。

### 任务 4：画出确定性净资产计算数据流

画出不经过 AI 的净资产计算路径。

这条链路至少需要包含：

- 谁发起净资产查询。
- API 或调用入口。
- service 如何取得账户数据。
- 数据库返回什么。
- 金额输入在哪里归一化。
- 哪个纯函数执行净资产计算。
- 计算结果是否包含输入、步骤和最终结果。
- 结果如何回到 Dashboard。
- 无账户、非法金额和数据库失败分别怎样处理。

你需要明确区分：

| 动作 | 应回答的问题 |
| --- | --- |
| 查询 | 谁负责从 SQLite 取得账户？ |
| 整理 | 谁把数据库记录转换成计算所需输入？ |
| 计算 | 谁拥有净资产公式？ |
| 展示 | 谁负责格式化金额和展示依据？ |

计算函数不得直接读取 React state、请求对象、SQLite 或 AI 输出。

### 任务 5：画出 AI 查询净资产的数据流

情境：

> 用户在对话框中输入：“我现在一共有多少钱？”

画出从问题输入到最终回答的完整路径，至少包含：

- 页面收集自然语言问题。
- API 接收问题。
- AI 将问题解析为结构化意图。
- Zod 校验 AI 输出。
- 系统根据意图选择所需数据和计算函数。
- service 读取账户。
- 确定性净资产函数计算结果。
- AI 将已经计算好的结果组织成自然语言。
- 页面同时展示回答和计算依据。

需要额外画出以下失败分支：

- 用户问题为空或格式不合法。
- AI 调用失败。
- AI 返回的结构不符合 schema。
- 意图暂不支持。
- 账户数据读取失败。
- 计算输入不合法。
- 解释阶段 AI 调用失败，但确定性计算已经成功。

最后一种情况需要单独判断：

> 财务结果已经正确算出，但 AI 无法生成自然语言解释时，系统是否仍能向用户返回可用结果？

### 任务 6：标记三类边界

在三张图中使用统一标记区分：

1. 信任边界：用户输入、HTTP 请求、AI 输出等不可信数据进入系统的位置。
2. 持久化边界：数据开始或结束数据库读写的位置。
3. 确定性边界：数据进入和离开财务计算函数的位置。

对每个边界说明：

- 为什么这里需要边界。
- 进入前后数据发生了什么变化。
- 失败时由谁产生错误。
- 错误最终怎样被页面理解。

### 任务 7：设计统一的成功与错误返回思路

不要求写具体代码，但需要描述页面从响应中至少能判断什么。

成功时至少要判断：

- 操作是否成功。
- 返回了什么业务数据。

失败时至少要判断：

- 错误类型或错误码。
- 用户可以理解的提示。
- 是否存在字段级问题。
- 是否可以重试。

比较下面几类错误是否应该得到相同处理：

- 用户输入错误。
- 业务规则不满足。
- 资源不存在。
- 数据库或服务器故障。
- AI 外部服务故障。

### 任务 8：完成故障定位练习

针对每个现象，写出：

1. 首先检查的层级。
2. 首先收集的证据。
3. 至少两个按可能性排序的假设。
4. 如何一次验证一个假设。
5. 修复后需要回归的相邻路径。

#### 故障 A：点击提交后页面没有变化

需要区分：

- 提交事件是否触发。
- 请求是否发出。
- 响应是否成功。
- 页面 state 是否更新。

#### 故障 B：API 返回 400

需要区分：

- 请求 JSON 是否符合约定。
- Zod schema 是否与需求一致。
- 错误是否来自业务规则而不是格式校验。

#### 故障 C：新增成功，但刷新后账户消失

需要区分：

- 页面是否只更新了本地 state。
- API 是否真正执行写入。
- 写入和读取是否连接同一个数据库。
- 查询是否错误过滤了记录。

#### 故障 D：AI 回复的金额和 Dashboard 不一致

需要区分：

- 两条路径读取的账户范围是否一致。
- 两条路径是否调用同一个净资产函数。
- 金额归一化和格式化是否一致。
- AI 是否重新计算或改写了金额。

## 五、约束

- 本关不写业务代码，不创建 API、schema 或数据库表。
- 不直接复制知识线项目的数据流作为答案。
- 不使用“前端、后端、数据库”三个词代替具体层级。
- 不省略失败路径。
- 不让页面直接访问 SQLite。
- 不让 Zod schema 执行业务计算。
- 不让数据库查询层拥有净资产公式。
- 不让 AI 重新计算确定性代码已经产生的金额。
- 不把格式化后的金额字符串重新用于计算。
- 不因为最终都会返回错误提示，就把所有错误视为同一种错误。
- 不提前决定第五关的具体实现计划。

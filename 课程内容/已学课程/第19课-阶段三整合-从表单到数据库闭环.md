# 第 19 课：阶段三整合：从表单到数据库闭环

## 本课目标

阶段三已经学过：

- HTTP 与 API。
- SQLite。
- Drizzle ORM。
- 财务数据模型。
- Zod 数据校验。
- CRUD。

现在要把这些内容整理成一条完整链路：

```txt
表单输入
  ↓
fetch 请求 API
  ↓
Zod 校验
  ↓
service 层处理业务逻辑
  ↓
Drizzle 写入 SQLite
  ↓
API 返回 JSON
  ↓
前端刷新账户列表
```

这一课不追求新增很多功能。

重点是让账户数据闭环稳定可用。

学完本课后，你应该能够：

- 画出账户 CRUD 的完整数据流。
- 说明前端类型、Zod schema、Drizzle schema 如何协作。
- 说明 service 层为什么存在。
- 调试 API、Zod、数据库和前端状态问题。
- 确认新增账户后刷新页面数据仍然存在。

## 一、当前页面要从本地状态切到 API

`app/dashboard/page.tsx` 当前负责账户管理。

它之前用的是：

```ts
initialAccounts
```

这种方式只适合前端练习。

现在要改成：

```txt
页面加载时请求 GET /api/accounts
提交表单时请求 POST /api/accounts
请求成功后更新账户列表
刷新页面后重新从数据库读取账户
```

页面不再自己“制造”账户数据。

页面只负责：

- 保存表单输入状态。
- 调用 API。
- 展示 loading、empty、error 状态。
- 把 API 返回的数据传给组件。

## 二、账户闭环的数据流

新增账户的数据流是：

```txt
用户填写账户名称、类型、余额
  ↓
点击新增账户
  ↓
handleSubmit
  ↓
fetch POST /api/accounts
  ↓
createAccountSchema.safeParse(body)
  ↓
createAccount(result.data)
  ↓
db.insert(accounts).values(account)
  ↓
SQLite 保存账户
  ↓
API 返回新增账户
  ↓
setAccounts([...accounts, account])
```

查询账户的数据流是：

```txt
页面首次打开
  ↓
useEffect
  ↓
fetch GET /api/accounts
  ↓
listAccounts()
  ↓
db.select().from(accounts)
  ↓
API 返回账户列表
  ↓
setAccounts(result.data.accounts)
```

这就是本阶段最重要的闭环。

## 三、三种 schema 如何协作

项目里会同时出现三类数据结构。

| 名称 | 示例文件 | 负责什么 |
| --- | --- | --- |
| 前端类型 | `types/finance.ts` | 帮 React 组件知道数据长什么样 |
| Zod schema | `schemas/finance.ts` | 校验 API 请求体是否合法 |
| Drizzle schema | `lib/db/schema.ts` | 描述 SQLite 表结构 |

以账户为例：

```txt
前端类型 Account
  用于 AccountCard、AccountList、DashboardPage

createAccountSchema
  用于 POST /api/accounts 校验用户提交内容

accounts 表
  用于 Drizzle 创建表和读写 SQLite
```

它们不是互相替代关系。

它们分别守住不同位置。

```txt
组件展示靠前端类型
请求入口靠 Zod
数据库结构靠 Drizzle
```

## 四、统一账户类型

当前数据库里的账户余额是字符串。

前端账户类型也应该和 API 返回值保持一致。

打开：

```txt
types/finance.ts
```

账户类型可以整理成：

```ts
export type AccountType = "cash" | "bank" | "credit" | "investment";

export type Account = {
  id: string;
  name: string;
  type: AccountType;
  currency: string;
  balance: string;
  createdAt: number;
  updatedAt: number;
  deletedAt: number | null;
};
```

这样组件读到的账户结构，就和数据库返回的数据一致。

### AccountCard 适配

改完 `types/finance.ts` 后，打开 `AccountCard.tsx`，TypeScript 会立即报错。这是因为 `balance` 从 `number` 变成了 `string`，两处代码需要修改：

**第 25 行** — 用 `Number()` 转换后比较：

```tsx
// 改前
const balanceClassName = account.balance < 0 ? "text-red-600" : "text-gray-900";

// 改后
const balanceClassName =
  Number(account.balance) < 0 ? "text-red-600" : "text-gray-900";
```

**第 38 行** — 用 `Number()` 转换后格式化：

```tsx
// 改前
{account.balance.toLocaleString()} 元

// 改后
{Number(account.balance).toLocaleString()} 元
```

> 为什么是 `Number()` 而不是 `parseFloat`？因为数据库存储的金额已经是合法数字字符串（例如 `"20000"` 、`"-3500"`），`Number()` 够用且简单。后续接入 `decimal.js` 后，可以再统一封装金额格式化函数。

## 五、整理 API 返回类型

前端调用 API 时，可以先定义一个简单类型帮助理解。

例如在页面里临时写：

```ts
type ApiSuccess<T> = {
  ok: true;
  data: T;
};

type ApiFailure = {
  ok: false;
  error: {
    code: string;
    message: string;
    issues?: {
      path: string;
      message: string;
    }[];
  };
};

type ApiResult<T> = ApiSuccess<T> | ApiFailure;
```

然后账户列表响应可以理解成：

```ts
type AccountsResponse = ApiResult<{
  accounts: Account[];
}>;
```

初学阶段也可以先不抽公共类型。

但一定要知道 API 返回结构：

```txt
成功时读 result.data
失败时读 result.error
```

不要直接假设返回结果就是数组。

## 六、改造仪表盘页面

打开：

```txt
app/dashboard/page.tsx
```

顶部需要从 React 导入：

```tsx
import { useEffect, useState } from "react";
```

移除：

```tsx
import { initialAccounts } from "@/lib/mock-data";
```

账户状态从空数组开始：

```tsx
const [accounts, setAccounts] = useState<Account[]>([]);
const [isLoading, setIsLoading] = useState(true);
const [error, setError] = useState("");
const [isSubmitting, setIsSubmitting] = useState(false);
```

页面加载时读取账户：

```tsx
useEffect(() => {
  async function loadAccounts() {
    try {
      setIsLoading(true);
      setError("");

      const response = await fetch("/api/accounts");
      const result = await response.json();

      if (!result.ok) {
        setError(result.error.message);
        return;
      }

      setAccounts(result.data.accounts);
    } catch {
      setError("账户数据加载失败，请稍后重试。");
    } finally {
      setIsLoading(false);
    }
  }

  loadAccounts();
}, []);
```

这样页面刷新后，会重新从 SQLite 读取账户。

## 七、改造表单提交

表单提交不再手动创建本地账户。

改成请求 API：

```tsx
async function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
  event.preventDefault();
  setError("");
  setIsSubmitting(true);

  try {
    const response = await fetch("/api/accounts", {
      method: "POST",
      headers: {
        "Content-Type": "application/json"
      },
      body: JSON.stringify({
        name,
        type,
        balance
      })
    });

    const result = await response.json();

    if (!result.ok) {
      const firstIssue = result.error.issues?.[0];
      setError(firstIssue?.message ?? result.error.message);
      return;
    }

    setAccounts((currentAccounts) => [
      ...currentAccounts,
      result.data.account
    ]);

    setName("");
    setType("bank");
    setBalance("");
  } catch {
    setError("新增账户失败，请稍后重试。");
  } finally {
    setIsSubmitting(false);
  }
}
```

这里不再需要前端自己判断：

```tsx
Number.isFinite(numericBalance)
```

金额是否合法交给 Zod。

前端仍然可以做基础提示，但后端校验一定不能省。

## 八、表单组件支持提交中状态

`AccountForm` 可以增加一个 prop：

```ts
isSubmitting: boolean;
```

按钮根据提交状态变化：

```tsx
<button
  type="submit"
  disabled={isSubmitting}
  className="rounded-md bg-gray-900 px-4 py-2 text-sm font-medium text-white hover:bg-gray-700 disabled:cursor-not-allowed disabled:bg-gray-400"
>
  {isSubmitting ? "提交中..." : "新增账户"}
</button>
```

页面调用组件时传入：

```tsx
<AccountForm
  name={name}
  type={type}
  balance={balance}
  error={error}
  isSubmitting={isSubmitting}
  onNameChange={setName}
  onTypeChange={setType}
  onBalanceChange={setBalance}
  onSubmit={handleSubmit}
/>
```

这样可以避免用户连续点击按钮重复提交。

## 九、处理 loading、empty、error

账户列表区域按顺序判断三种状态。

整体结构是：

```tsx
// 1. loading 优先
if (isLoading) {
  return <p className="text-sm text-gray-500">正在加载账户数据...</p>;
}

// 2. error 在表单和列表上方展示
{error && (
  <p className="mb-4 rounded-md bg-red-50 px-3 py-2 text-sm text-red-700">
    {error}
  </p>
)}

// 3. 列表区域 — AccountList 内部已处理空状态
<AccountList accounts={accounts} />
```

注意几点：

- **loading 是拦截式的**：数据还没到，整个页面内容不展示，直接显示"正在加载"。
- **error 是浮动式的**：页面的表单和列表正常渲染，错误信息额外展示在上面。
- **空状态不归仪表盘管**：`AccountList` 组件内部已经判断过 `accounts.length === 0` 并渲染 `<EmptyAccounts />`。仪表盘页面不需要重复写 `<EmptyAccounts />`，传 `accounts` 给 `AccountList` 即可。

判断顺序：

```txt
先判断 loading（数据未知）
再判断 error（请求失败）
最后交给 AccountList 处理 empty（数据为空）或正常列表（有数据）
```

## 十、检查账户 API

`app/api/accounts/route.ts` 应该只保留 HTTP 相关逻辑。

结构可以是：

```ts
export async function GET() {
  const accounts = await listAccounts();

  return successResponse({
    accounts
  });
}

export async function POST(request: Request) {
  const body = await request.json();
  const result = createAccountSchema.safeParse(body);

  if (!result.success) {
    return errorResponse(...);
  }

  const account = await createAccount(result.data);

  return successResponse({ account }, { status: 201 });
}
```

API 文件不应该直接写：

```ts
db.insert(...)
```

数据库操作放在：

```txt
lib/services/accounts.ts
```

这样后续业务规则变多时，API 文件仍然清楚。

## 十一、检查 service 层

打开：

```txt
lib/services/accounts.ts
```

账户 service 至少需要：

```ts
listAccounts()
createAccount(input)
getAccountById(id)
updateAccount(id, input)
deleteAccount(id)
```

其中 `listAccounts()` 要排除软删除数据：

```ts
where(isNull(accounts.deletedAt))
```

`deleteAccount()` 不直接删除记录，而是设置：


## 十四、常见问题定位

### 1. 表单提交成功但刷新消失

检查 `handleSubmit` 是否只是：

```tsx
setAccounts([...accounts, newAccount])
```

如果只是更新前端状态，没有请求 API，就不会保存到数据库。

### 2. API 返回 VALIDATION_ERROR

查看返回的：

```txt
error.issues
```

常见原因：

- `name` 是空字符串。
- `type` 不是允许值。
- `balance` 不是标准金额字符串。

### 3. 数据库提示表不存在

运行：

```bash
npx drizzle-kit push
```

然后用：

```sql
.tables
```

确认表存在。

### 4. 页面类型报错

检查 `types/finance.ts` 是否和 API 返回结构一致。

尤其注意：

```txt
balance 是 string
createdAt 是 number
currency 是 string
```

### 5. 删除后仍然能查到数据

软删除不会从数据库中移除记录。

它只是设置 `deleted_at`。

列表接口必须过滤：

```txt
deleted_at 为空
```

## 十九、复习问题

1. **为什么刷新页面后数据仍然存在，才算完成数据库闭环？**

   数据只有写进 SQLite 文件才算持久化。如果刷新后数据消失，说明数据只存在 React 的 `useState` 或内存变量里，浏览器一刷新 JS 重新执行，状态归零。真正的持久化路径是：提交时经 API 写入 SQLite，刷新时 API 从 SQLite 读回展示。刷新后还在，是验证"数据真的进了数据库"的唯一可靠方法。

2. **`DashboardPage` 应该直接调用 Drizzle 吗？**

   不应该。`DashboardPage` 是前端组件，运行在浏览器里，没有 Node.js 的 `fs` 模块和 SQLite 驱动。Drizzle 只能跑在服务端。正确路径是：`DashboardPage` → `fetch` → API 路由 → service → Drizzle → SQLite。页面只通过 HTTP 与后端通信。

3. **`route.ts` 和 service 层分别负责什么？**

   `route.ts` 负责 HTTP 层面的工作：解析请求（`request.json()`）、决定响应状态码（200/201/400/404）、包装响应格式。service 层负责业务逻辑和数据库操作：生成 `id` 和时间戳、决定软删除还是真删除、组合多个数据库操作。划分原则是：route 拿到数据后先交给 Zod 校验，校验通过后交给 service；service 不关心 HTTP 的存在，只接受参数、返回数据。

4. **Zod 校验失败后为什么不能继续写数据库？**

   因为不合法数据会破坏数据完整性。例如 `balance` 存了 `"abc"`，后续计算金额时出现 NaN；`type` 存了未定义的值，查询时前端类型匹配不上；`name` 为空字符串，页面展示无意义。Zod 的作用是在数据到达业务逻辑和数据库之前就拦截掉，保证进入 service 的每个字段都符合预期、干净合法。

5. **前端类型为什么要和 API 返回结构一致？**

   不一致会导致运行时错误。例如 API 返回的 `balance` 是字符串 `"20000"`，前端类型写成 `number`，`toLocaleString()` 编译时不报错但运行时报 `toLocaleString is not a function`。再如 API 返回 `{ ok: true, data: { accounts } }`，前端假设直接拿到数组，就会取到 `undefined` 导致页面空白。类型一致性让前端在编码阶段就能发现结构不匹配。

6. **如何判断问题出在前端、API、service 还是数据库？**

   按链路分层排查，一次只查一层：

   - 浏览器 Console 直接 `fetch("/api/accounts")`，看返回结果。API 返回正确 → 问题在前端（fetch 写错、状态没更新、组件渲染错）。API 报错或为空 → 往下查。
   - 看 API 里 Zod 是否拒绝了请求、service 是否被正确调用。API 逻辑没问题 → 往下查。
   - 用 `sqlite3` 直接查询数据库。数据库有数据 → 问题在 API 或 service。数据库没数据 → 问题在 service 或 Drizzle schema。

   核心原则：用 API 响应和数据库内容作为客观证据，不凭感觉乱改。

7. **软删除后，列表查询为什么要过滤 `deletedAt`？**

   软删除只是给记录打上"已删除"的时间戳标记，记录本身仍然存在于表中。如果 `listAccounts()` 不添加 `where(isNull(accounts.deletedAt))`，已删除的账户也会被查出来展示在页面上。过滤 `deletedAt` 为空，就是"只展示未被删除的数据"。

8. **阶段四的计算引擎会依赖阶段三的哪些数据？**

   依赖阶段三构建的三张数据表：`accounts`（账户表）、`transactions`（流水表）、`liabilities`（负债表）。计算引擎会读取这些结构化数据来计算月收入、月支出、月结余、储蓄率、负债率、最低还款、还债策略和目标达成进度。计算引擎执行纯 TypeScript 聚合逻辑，不依赖 AI，但依赖这些表里有数据。

# 第 26 课：计算过程可追溯

## 本课目标

第 23 课已经能计算储蓄目标：

```txt
目标金额
当前金额
每月储蓄
年化收益率
期限
  ↓
预计期末金额
是否达成
缺口或超额
所需月储蓄额
```

第 25 课又把确定性计算接入了页面、API 和数据库。

但目前用户看到的主要还是最终结果：

```txt
24 个月后预计有 402609.52 元
距离 50 万元还差 97390.48 元
每月至少需要储蓄 15942.49 元
```

用户可能继续追问：

- 年化 3% 是怎样变成月收益率的？
- 当前 10 万元经过 24 个月变成了多少？
- 每月储蓄的部分累计成了多少？
- 为什么建议金额是 15942.49 元？
- 以后代码升级了，能否知道当时使用的是哪套规则？

只保存最终结果，还不足以回答这些问题。

这一课会建立：

```txt
输入快照
公式版本
计算步骤
中间值
输出快照
  ↓
calculation_history
```

并在前端展示储蓄目标的完整计算依据。

学完后，你应该能够：

- 解释为什么财务结果需要可追溯。
- 设计可 JSON 序列化的 `CalculationStep`。
- 区分公式、输入、中间值和输出。
- 为储蓄目标返回稳定的计算步骤。
- 给计算规则添加版本号。
- 把一次计算保存到 `calculation_history`。
- 区分场景记录和计算历史。
- 在页面展示计算步骤。
- 验证历史记录可以被重新读取。
- 说明计算追踪和 AI 隐藏推理的区别。

## 二、为什么只保存结果不够

假设历史记录只保存：

```json
{
  "projectedAmount": "402609.52",
  "reached": false
}
```

几个月后，项目调整了：

- 月初投入与月末投入规则。
- 年化收益率换算方式。
- 金额取整方式。
- 所需月储蓄额取整方式。

这时只看结果，无法知道：

```txt
402609.52 是用哪套规则算出的？
```

可追溯记录需要回答：

```txt
当时输入了什么？
使用了哪个计算器？
使用了哪个版本？
采用了什么假设？
经过了哪些确定性步骤？
最后输出了什么？
```

## 三、可追溯不等于“打印几行日志”

普通日志可能是：

```txt
开始计算
计算成功
结果是 402609.52
```

这只能帮助判断程序是否运行。

它没有保存：

- 月收益率。
- 复利因子。
- 年金因子。
- 本金期末价值。
- 每月储蓄期末价值。
- 目标比较过程。

本课需要的是结构化计算证据：

```json
{
  "id": "monthly_rate",
  "title": "换算月收益率",
  "formula": "annualRate / 100 / 12",
  "inputs": {
    "annualRate": "3"
  },
  "outputs": {
    "monthlyRate": "0.0025"
  }
}
```

结构化数据可以：

- 在页面展示。
- 在测试中断言。
- 保存到 JSON。
- 重新读取。
- 比较不同版本。

## 四、CalculationStep 应该包含什么

每一步至少需要：

| 字段 | 作用 |
| --- | --- |
| `id` | 稳定步骤标识 |
| `title` | 用户能看懂的标题 |
| `description` | 这一步为什么存在 |
| `formula` | 使用的确定性公式 |
| `inputs` | 这一步读取的值 |
| `outputs` | 这一步得到的值 |

例如：

```txt
步骤：换算月收益率
输入：年化收益率 3%
公式：3 ÷ 100 ÷ 12
输出：0.0025
```

## 五、步骤 id 为什么不能使用随机值

不要写：

```ts
id: crypto.randomUUID()
```

步骤顺序和含义属于计算规则的一部分。

本课使用稳定 id：

```txt
monthly_rate
growth_factors
future_value_components
projected_amount
target_comparison
required_monthly_saving
```

相同规则、相同输入应该返回相同的步骤 id。

这样可以：

- 在测试中定位步骤。
- 在前端选择性展开。
- 比较不同公式版本。
- 避免每次计算都产生无法关联的随机步骤。

历史记录本身的 `id` 才使用 UUID。

## 六、步骤中不能保存 Decimal 对象

`Decimal` 适合内部计算，但不应直接作为历史 JSON 的业务格式。

步骤中只保存：

```txt
string
number
boolean
null
```

原因是这些值：

- 可以稳定 `JSON.stringify()`。
- 不依赖 `decimal.js` 的对象内部结构。
- 前端不需要重新构造 Decimal 才能展示。
- 数据库读取后仍然容易理解。

## 七、创建通用步骤类型

新建：

```txt
lib/finance/calculation-step.ts
```

写入：

```ts
export type CalculationValue =
  | string
  | number
  | boolean
  | null;

export type CalculationStep = {
  id: string;
  title: string;
  description: string;
  formula: string;
  inputs: Record<string, CalculationValue>;
  outputs: Record<string, CalculationValue>;
};
```

暂时不把 `inputs` 和 `outputs` 限定成某个计算器的固定字段。

因为后续：

- 现金流。
- 储蓄目标。
- 债务偿还。
- What-if。

都会产生不同的输入和输出。

## 八、CalculationStep 不保存什么

步骤中不要保存：

- `Decimal` 实例。
- React 组件。
- 数据库连接。
- API key。
- 完整环境变量。
- 用户密码。
- AI 隐藏推理。
- 未经筛选的模型原始响应。

`CalculationStep` 只保存：

> 由业务代码明确执行、可以公开给用户复算的确定性计算步骤。

## 十、设计储蓄目标步骤

本课使用六个步骤：

```txt
1. monthly_rate
   年化收益率转月收益率

2. growth_factors
   计算复利因子和月末投入因子

3. future_value_components
   分别计算当前金额和月储蓄的期末价值

4. projected_amount
   合并两部分期末价值

5. target_comparison
   判断目标并计算缺口或超额

6. required_monthly_saving
   反推至少需要的月储蓄额
```

为什么不把所有内容放在一个步骤？

因为用户需要看见：

```txt
输入如何变成中间值
中间值如何变成结果
```

为什么也不拆成几十步？

因为每一次加法都单独展示会产生大量噪声。

步骤粒度应该：

> 足够复算，但不过度打断阅读。

## 十一、创建步骤构造函数

在 `savings-goal.ts` 中增加：

```ts

  currentAmount: Decimal;
  monthlySaving: Decimal;
  annualRate: Decimal;
  months: number;
  monthlyRate: Decimal;
  growthFactor: Decimal;
  annuityFactor: Decimal;
  currentAmountFutureValue: Decimal;
  monthlySavingFutureValue: Decimal;
  projectedAmount: Decimal;
  reached: boolean;
  gap: Decimal;
  excess: Decimal;

```

这个类型只在当前文件内部使用，不需要 `export`。

它把已经算出的值交给步骤构造函数。

步骤构造函数不重新计算一遍财务结果。

## 十二、实现步骤构造函数

继续增加：

```ts
function buildSavingsGoalSteps(
  values: SavingsGoalStepValues
): CalculationStep[] {
  const {
    targetAmount,
    currentAmount,
    monthlySaving,
    annualRate,
    months,
    monthlyRate,
    growthFactor,
    annuityFactor,
    currentAmountFutureValue,
    monthlySavingFutureValue,
    projectedAmount,
    reached,
    gap,
    excess,
    requiredMonthlySaving
  } = values;

  return [
    {
      id: "monthly_rate",
      title: "换算月收益率",
      description:
        "把名义年化百分比转换为月收益率。",
      formula: "annualRate / 100 / 12",
      inputs: {
        annualRate: annualRate.toString()
      },
      outputs: {
        monthlyRate: monthlyRate.toString()
      }
    },
    {
      id: "growth_factors",
      title: "计算复利因子",
      description:
        "计算本金增长因子和月末投入年金因子。",
      formula:
        "growth=(1+r)^n; " +
        "annuity=r=0?n:(growth-1)/r",
      inputs: {
        monthlyRate: monthlyRate.toString(),
        months
      },
      outputs: {
        growthFactor: growthFactor.toString(),
        annuityFactor: annuityFactor.toString()
      }
    },
    {
      id: "future_value_components",
      title: "计算两部分期末价值",
      description:
        "分别计算当前金额和每月储蓄的期末价值。",
      formula:
        "currentFV=currentAmount*growth; " +
        "savingFV=monthlySaving*annuity",
      inputs: {
        currentAmount: toMoneyString(currentAmount),
        monthlySaving: toMoneyString(monthlySaving),
        growthFactor: growthFactor.toString(),
        annuityFactor: annuityFactor.toString()
      },
      outputs: {
        currentAmountFutureValue:
          currentAmountFutureValue.toString(),
        monthlySavingFutureValue:
          monthlySavingFutureValue.toString()
      }
    },
    {
      id: "projected_amount",
      title: "计算预计期末金额",
      description:
        "把本金和每月储蓄的期末价值相加。",
      formula:
        "projectedAmount=currentFV+savingFV",
      inputs: {
        currentAmountFutureValue:
          currentAmountFutureValue.toString(),
        monthlySavingFutureValue:
          monthlySavingFutureValue.toString()
      },
      outputs: {
        projectedAmountRaw:
          projectedAmount.toString(),
        projectedAmount:
          toMoneyString(projectedAmount)
      }
    },
    {
      id: "target_comparison",
      title: "比较目标金额",
      description:
        "判断是否达标，并返回缺口或超额。",
      formula:
        "compare(projectedAmount,targetAmount)",
      inputs: {
        projectedAmountRaw:
          projectedAmount.toString(),
        targetAmount: toMoneyString(targetAmount)
      },
      outputs: {
        reached,
        gap: toMoneyString(gap),
        excess: toMoneyString(excess)
      }
    },
    {
      id: "required_monthly_saving",
      title: "反推所需月储蓄额",
      description:
        "计算达到目标至少需要的月储蓄额，" +
        "并向上取到分。",
      formula:
        "max(0,(targetAmount-currentFV)" +
        "/annuityFactor)",
      inputs: {
        targetAmount: toMoneyString(targetAmount),
        currentAmountFutureValue:
          currentAmountFutureValue.toString(),
        annuityFactor: annuityFactor.toString()
      },
      outputs: {
        requiredMonthlySaving:
          requiredMonthlySaving.toFixed(
            2,
            Decimal.ROUND_CEIL
          )
      }
    }
  ];
}
```

## 十三、步骤中的原始中间值和金额输出

示例中有两种字符串：

### 1. 高精度中间值

```txt
growthFactor
annuityFactor
currentAmountFutureValue
```

使用：

```ts
decimal.toString()
```

保存当前计算实际使用的值。

### 2. 面向用户的金额结果

```txt
projectedAmount
gap
excess
requiredMonthlySaving
```

使用：

```ts
toMoneyString()
toFixed(2, Decimal.ROUND_CEIL)
```

保持项目已经确定的金额展示和取整规则。

目标是否达成仍然根据 `projectedAmountRaw` 对应的高精度值判断，不能先把预计金额四舍五入到分再比较。步骤同时记录原始值和展示值，避免历史说明与真实业务判断不一致。

## 十九、为什么需要公式版本

假设未来把规则从：

```txt
每月末投入
```

改成：

```txt
每月初投入
```

即使输入完全相同，结果也会变化。

因此历史不能只写：

```txt
calculator = savings_goal
```

还要写：

```txt
version = 1.0.0
```

版本表示：

> 这条历史记录使用的是哪套计算规则。

本课定义：

```ts
export const SAVINGS_GOAL_FORMULA_VERSION =
  "1.0.0";
```

把它放在：

```txt
lib/finance/savings-goal.ts
```

文件顶部。

只有公式、取整或关键假设发生变化时，才升级公式版本。

普通文案修改不需要升级。

## 二十、现有 calculation_history 表

项目已经有：

```ts
export const calculationHistory = sqliteTable(
  "calculation_history",
  {
    id: text("id").primaryKey(),
    intentType: text("intent_type").notNull(),
    inputJson: text("input_json").notNull(),
    formulaJson: text("formula_json").notNull(),
    outputJson: text("output_json").notNull(),
    modelTraceJson: text("model_trace_json"),
    createdAt: integer("created_at").notNull()
  }
);
```

本课不需要修改数据库结构。

各字段含义：

| 字段 | 本课保存内容 |
| --- | --- |
| `id` | 一次计算历史的 UUID |
| `intentType` | `"savings_goal"` |
| `inputJson` | 通过校验的输入快照 |
| `formulaJson` | 计算器、版本、假设和 steps |
| `outputJson` | 不包含 steps 的最终输出 |
| `modelTraceJson` | 本课为 `null` |
| `createdAt` | 计算历史创建时间 |

## 二十一、为什么 input、formula 和 output 分开保存

不要把所有内容塞进一个不透明 JSON。

分开后可以明确回答：

```txt
inputJson
  用户和系统提供了什么

formulaJson
  使用什么规则、假设和步骤

outputJson
  最终返回了什么
```

以后可以：

- 按意图类型筛选。
- 对比公式版本。
- 重新运行旧输入。
- 检查新旧输出是否一致。

## 二十二、modelTraceJson 应该保存什么

本课没有调用 AI，因此：

```ts
modelTraceJson: null
```

以后接入 AI 时，可以保存结构化元数据，例如：

```json
{
  "provider": "deepseek",
  "model": "模型名称",
  "requestId": "请求标识",
  "parsedIntent": "savings_goal"
}
```

不要保存：

- API key。
- Authorization header。
- 环境变量。
- AI 隐藏推理过程。
- 不需要长期保留的敏感原始文本。

可追溯的重点是：

```txt
系统收到了什么结构化输入
确定性代码如何计算
系统返回了什么结果
```

不是要求模型公开内部推理。

```ts
    id: crypto.randomUUID(),
    intentType: "savings_goal",
    inputJson: JSON.stringify(input),
    formulaJson: JSON.stringify({
      calculator: "savings_goal",
      version: SAVINGS_GOAL_FORMULA_VERSION,
      assumptions: {
        annualRateType: "nominal",
        contributionTiming: "month_end",
        moneyRounding: "half_up_2",
        requiredSavingRounding: "ceil_2"
      },
      steps
    }),
    outputJson: JSON.stringify(output),
    modelTraceJson: null,
    createdAt: Date.now()
  };

  await db
    .insert(calculationHistory)
    .values(history);

  return history;
}

export async function listCalculationHistory(
  limit = 20
) {
  return db
    .select()
    .from(calculationHistory)
    .orderBy(desc(calculationHistory.createdAt))
    .limit(limit);
}
```

## 二十四、为什么输出 JSON 不重复保存 steps

代码执行：

```ts
const { steps, ...output } = result;
```

然后：

```txt
steps → formulaJson
output → outputJson
```

如果 `outputJson` 再包含一份 steps：

- 数据重复。
- 两份步骤可能在以后不一致。
- 历史记录更难理解。

本课统一让 `formulaJson` 保存计算过程。

## 二十六、新增储蓄目标计算 API

新建：

```txt
app/api/calculations/savings-goal/route.ts
```

写入：

```ts
import {
  errorResponse,
  successResponse
} from "@/lib/api/response";
import {
  calculateSavingsGoal
} from "@/lib/finance/savings-goal";
import {
  saveSavingsGoalCalculation
} from "@/lib/services/calculation-history";
import {
  formatZodError
} from "@/schemas/format-zod-error";
import {
  savingsGoalSchema
} from "@/schemas/savings-goal";

export async function POST(request: Request) {
  const body = await request.json();
  const parsed = savingsGoalSchema.safeParse(body);

  if (!parsed.success) {
    return errorResponse(
      "VALIDATION_ERROR",
      "储蓄目标输入不合法",
      { status: 400 },
      {
        issues: formatZodError(parsed.error)
      }
    );
  }

  let calculation;

  try {
    calculation = calculateSavingsGoal(parsed.data);
  } catch (error) {
    return errorResponse(
      "CALCULATION_ERROR",
      error instanceof Error
        ? error.message
        : "储蓄目标计算失败",
      { status: 400 }
    );
  }

  try {
    const history =
      await saveSavingsGoalCalculation(
        parsed.data,
        calculation
      );

    return successResponse(
      {
        historyId: history.id,
        calculation
      },
      { status: 201 }
    );
  } catch {
    return errorResponse(
      "HISTORY_SAVE_ERROR",
      "计算成功，但历史记录保存失败",
      { status: 500 }
    );
  }
}
```

这条 API 的成功条件是：

```txt
计算成功
并且
历史保存成功
```

如果计算成功但保存失败，返回 `500`，不要让页面误以为已经生成了可追溯记录。

## 三十一、为什么保存快照而不是只存 historyId

历史记录不能只保存：

```txt
输入表 id
目标表 id
场景表 id
```

因为这些表以后可能被修改或软删除。

例如用户把目标金额从 50 万改成 60 万。

旧历史仍然应该保留：

```txt
当时计算使用的是 50 万
```

因此：

```txt
inputJson 和 outputJson 是当时快照
```

关联 id 可以额外保存，但不能替代快照。

```tsx
async function handleSubmit(
  event: React.FormEvent<HTMLFormElement>

  event.preventDefault();
  setError("");
  setResult(null);
  setHistoryId("");
  setIsSubmitting(true);

  try {

      "/api/calculations/savings-goal",

          "Content-Type": "application/json"
        },
        body: JSON.stringify({
          targetAmount,

          monthlySaving,
          annualRate,
          months: Number(months)
        })
      }
    );

    const body = await response.json();

    if (!body.ok) {
      const firstIssue = body.error.issues?.[0];
      setError(
        firstIssue?.message ?? body.error.message
      );
      return;
    }

    setResult(body.data.calculation);
    setHistoryId(body.data.historyId);
  } catch {
    setError("储蓄目标计算失败，请稍后重试。");
  } finally {
    setIsSubmitting(false);
  }
}
```

## 四十五、什么是审计记录的意义

本课建立的是：

```txt
应用级计算追溯记录
```

它可以帮助：

- 用户理解结果。
- 开发者复现问题。
- 测试公式变更。
- 对比不同计算版本。
- 检查输入和输出是否一致。

但它不自动等于：

- 法律意义上的审计系统。
- 不可篡改账本。
- 会计凭证。
- 合规认证。

如果未来需要更高等级的审计能力，还要考虑：

- 访问控制。
- 防篡改。
- 数据签名。
- 保留期限。
- 操作人身份。
- 时间可信度。
- 敏感数据脱敏。

## 四十六、历史记录也有隐私风险

`inputJson` 可能包含：

- 收入。
- 支出。
- 账户余额。
- 负债。
- 财务目标。

因此计算历史不是“普通调试日志”。

本地优先项目仍应：

- 不把历史自动发送到第三方。
- 不记录 API key。
- 不在错误日志打印完整敏感输入。
- 提供删除历史的能力。
- 只保存完成产品功能所需的数据。

本课暂时完成保存和读取，删除历史会在后续产品化阶段处理。

## 四十七、公式字符串不能代替真实代码

历史中保存：

```txt
projectedAmount=currentFV+savingFV
```

它是对当时规则的说明。

真正执行计算的仍然是：

```ts
currentAmountFutureValue.plus(
  monthlySavingFutureValue
)
```

因此：

- 公式字符串要与代码同步。
- 公式变化时要更新版本。
- 测试应检查关键步骤。

不能只修改页面公式文字，却不修改计算代码。

也不能只修改代码，却继续保存旧公式说明。

## 四十八、常见错误

### 1. 只保存最终结果

缺少输入、公式版本和步骤时，未来无法解释结果。

### 2. steps 中保存 Decimal 对象

历史 JSON 应保存明确的基础值，不依赖第三方对象结构。

### 3. 步骤 id 使用随机 UUID

步骤含义应稳定，历史记录 id 才需要随机。

### 4. 主函数和步骤构造函数各算一次

两套计算以后可能分叉。步骤应读取主函数已经得到的值。

### 5. outputJson 重复保存 steps

重复数据可能不一致。本课把 steps 统一放进 formulaJson。

### 6. 忘记公式版本

代码改变后无法判断旧记录使用了哪套规则。

### 7. 把 AI 隐藏推理存入 modelTraceJson

模型追踪只应保存必要的结构化元数据，不应保存秘密、凭证或隐藏推理。

### 8. 使用 eval 执行公式字符串

公式字符串只用于解释，计算必须由受测试的确定性代码完成。

### 9. 只保存数据库记录 id

关联数据可能变化，计算历史还需要保存当时输入和输出快照。

### 10. 页面只显示步骤，不显示结论

可解释性不能牺牲可读性。最终结果应该先出现，步骤作为依据随后展示。

## 五十二、复习问题

### 1. 为什么财务计算需要保存中间步骤？

中间步骤可以说明输入如何经过公式变成结果，帮助用户理解、开发者复现和测试公式变更。

### 2. CalculationStep 为什么只保存基础值？

字符串、数字、布尔值和 `null` 能稳定序列化，不依赖运行时对象内部结构。

### 3. 为什么步骤 id 要稳定？

稳定 id 可以用于测试、前端定位和不同版本比较。随机 id 无法表达步骤的固定含义。

### 4. 为什么步骤构造函数不应该重新计算？

如果主函数和步骤各算一次，两套逻辑以后可能产生不同结果。步骤应该记录主函数已经使用的值。

### 5. 为什么需要公式版本？

投入时点、利率换算或取整规则改变后，相同输入可能产生不同输出。版本可以标识旧记录使用的规则。

### 6. inputJson、formulaJson 和 outputJson 分别保存什么？

它们分别保存当时输入、计算规则与步骤、最终输出。

### 7. 为什么 outputJson 不再包含 steps？

步骤已经保存在 formulaJson，重复保存会浪费空间并产生两份内容不一致的风险。

### 8. modelTraceJson 为什么是 null？

本课没有 AI 参与。以后也只应保存必要的模型元数据，不保存 API key 或隐藏推理。

### 9. 为什么不能用 eval 执行历史公式？

公式字符串用于说明和审阅，不是可信执行代码。真实计算必须由经过测试的 TypeScript 函数完成。

### 10. 计算历史和场景记录有什么区别？

场景记录保存“假设是什么”，计算历史保存“某次使用什么输入和规则，得到什么输出”。

### 11. 本课记录是否等于法律审计系统？

不等于。它是应用级追溯记录，更高等级审计还需要防篡改、访问控制、身份和保留策略。

### 12. 为什么历史快照不能只引用当前目标表？

目标表以后可能修改或删除。快照必须保留计算发生时实际使用的值。

# 第 31 课：对话界面开发

## 本课目标

第 30 课已经实现：

```txt
POST /api/chat
```

并返回：

```txt
reply
calculation
historyId
assumptions
```

服务端已经能够完成：

```txt
用户问题
  ↓
DeepSeek 意图解析
  ↓
读取账户和流水
  ↓
确定性储蓄目标计算
  ↓
保存 calculation_history
  ↓
返回自然语言回复和结构化结果
```

但是当前：

```txt
app/chat/page.tsx
```

仍然只是静态占位页面。

用户虽然能通过 `curl` 调用接口，却还不能在浏览器中真正完成：

```txt
输入问题
  ↓
提交请求
  ↓
看到加载状态
  ↓
看到 AI 回复
  ↓
看到结构化计算结果
  ↓
展开查看计算过程
```

这一课会把第 30 课的服务端闭环连接到可交互页面。

学完后，你应该能够：

- 说明 Server Component 和 Client Component 在本页中的选择。
- 为聊天消息设计受限的 TypeScript 类型。
- 使用数组状态保存用户消息和助手消息。
- 使用受控 `<textarea>` 接收问题。
- 使用表单语义提交问题。
- 调用 `POST /api/chat`。
- 把 API 响应当作 `unknown` 进行运行时校验。
- 区分 HTTP 失败、业务失败和响应结构失败。
- 展示发送中的 loading 状态。
- 防止重复提交造成重复计算历史。
- 在失败时保留用户问题并显示明确错误。
- 显示助手自然语言回复。
- 显示预计金额、目标缺口和所需月储蓄额。
- 显示数据月份与年化收益率假设。
- 复用 `CalculationSteps` 展示确定性计算步骤。
- 使用 `<details>` 实现“查看计算过程”。
- 支持示例问题填入输入框。
- 支持 Enter 发送和 Shift+Enter 换行。
- 正确处理中文输入法组合状态。
- 在新增消息后滚动到对话底部。
- 使用 `aria-live` 让加载和错误状态更容易被辅助技术感知。
- 说明为什么当前消息列表不等于真正多轮对话。
- 为第 32 课之前完成一个可用的基础 AI 对话页面。

## 五、为什么 app/chat/page.tsx 必须是 Client Component

当前页面将使用：

```txt
useState
useRef
useEffect
表单事件
键盘事件
浏览器 fetch
```

因此文件第一行需要：

```ts
"use client";
```

这不表示整个项目都要变成 Client Component。

只有需要浏览器交互的组件进入客户端边界。

Chat API、数据库和 DeepSeek 仍然只在服务端运行。

## 六、客户端不能导入服务端实现

不要在页面中写：

```ts
import {
  answerChatQuestion,
} from "@/lib/chat/chat-service";
```

也不要直接导入：

```txt
数据库 client
服务端环境变量
DeepSeek client
```

浏览器只应该调用：

```txt
POST /api/chat
```

正确边界：

```txt
Client Component
  ↓ HTTP
API route
  ↓
chat service
  ↓
数据库和 DeepSeek
```

## 七、不要让页面从 reply 中提取金额

第 30 课同时返回：

```txt
reply
calculation
historyId
assumptions
```

页面应这样使用：

| 字段 | 页面用途 |
| --- | --- |
| `reply` | 助手消息正文 |
| `calculation` | 结果卡片与计算步骤 |
| `historyId` | 审计记录标识 |
| `assumptions` | 数据月份、来源和收益率说明 |

不要使用正则从：

```txt
预计为 402609.52 元
```

中提取：

```txt
402609.52
```

自然语言可以变化，结构化字段才是稳定界面契约。

## 八、先为 Chat API 响应写 Zod schema

浏览器收到的：

```ts
await response.json()
```

在运行时仍然是不可信的外部数据。

TypeScript 类型不会自动校验网络响应。

新建：

```txt
schemas/chat-response.ts
```

写入：

```ts
import * as z from "zod";

const calculationValueSchema = z.union([
  z.string(),
  z.number(),
  z.boolean(),
  z.null(),
]);

const calculationStepSchema = z.object({
  id: z.string(),
  title: z.string(),
  description: z.string(),
  formula: z.string(),
  inputs: z.record(
    z.string(),
    calculationValueSchema,
  ),
  outputs: z.record(
    z.string(),
    calculationValueSchema,
  ),
});

const savingsGoalCalculationSchema = z.object({
  targetAmount: z.string(),
  currentAmount: z.string(),
  monthlySaving: z.string(),
  annualRate: z.string(),
  months: z.number().int().positive(),
  projectedAmount: z.string(),
  reached: z.boolean(),
  gap: z.string(),
  excess: z.string(),
  requiredMonthlySaving: z.string(),
  steps: z.array(calculationStepSchema),
});

const savingsGoalIntentSchema = z.object({
  type: z.literal("savings_goal"),
  targetAmount: z.string(),
  deadlineMonths: z.number().int().positive(),
});

const savingsGoalAssumptionsSchema = z.object({
  dataMonth: z
    .string()
    .regex(/^\d{4}-(0[1-9]|1[0-2])$/),
  currentAmountSource: z.literal(
    "cash_and_bank_accounts",
  ),
  monthlySavingSource: z.literal(
    "current_month_surplus",
  ),
  annualRate: z.string(),
});

export const chatSuccessResponseSchema = z.object({
  ok: z.literal(true),
  data: z.object({
    reply: z.string().min(1),
    historyId: z.string().min(1),
    intent: savingsGoalIntentSchema,
    calculation: savingsGoalCalculationSchema,
    assumptions: savingsGoalAssumptionsSchema,
  }),
});

const apiIssueSchema = z.object({
  path: z.string(),
  message: z.string(),
});

export const chatErrorResponseSchema = z.object({
  ok: z.literal(false),
  error: z.object({
    code: z.string(),
    message: z.string(),
    issues: z.array(apiIssueSchema).optional(),
  }),
});

export const chatApiResponseSchema =
  z.discriminatedUnion("ok", [
    chatSuccessResponseSchema,
    chatErrorResponseSchema,
  ]);

export type ChatSuccessData = z.infer<
  typeof chatSuccessResponseSchema
>["data"];

export type ChatErrorData = z.infer<
  typeof chatErrorResponseSchema
>["error"];
```

## 九、为什么响应仍要运行时校验

你可能会写：

```ts
const body =
  (await response.json()) as ChatSuccessData;
```

`as` 只是在告诉 TypeScript：

```txt
请相信我
```

它不会检查服务端是否真的返回：

```txt
historyId
calculation.steps
assumptions
```

如果 API 契约意外变化，页面可能在很深的位置才报错。

Zod 可以在网络边界立即停止：

```txt
HTTP JSON
  ↓
chatApiResponseSchema
  ↓
可信页面数据
```

## 十一、为页面消息建立受限联合类型

新建：

```txt
types/chat.ts
```

写入：

```ts
import type {
  ChatSuccessData,
} from "@/schemas/chat-response";

export type UserChatMessage = {
  id: string;
  role: "user";
  content: string;
};

export type AssistantChatMessage = {
  id: string;
  role: "assistant";
  content: string;
  result?: ChatSuccessData;
};

export type ChatMessage =
  | UserChatMessage
  | AssistantChatMessage;
```

联合类型能表达：

```txt
用户消息
  → 只有文本

助手欢迎消息
  → 只有文本

助手计算回复
  → 文本 + 结构化结果
```

## 十二、为什么结果只属于助手消息

不要设计：

```ts
type ChatMessage = {
  role: "user" | "assistant";
  result?: ChatSuccessData;
};
```

这种宽类型允许：

```txt
用户消息携带计算结果
```

更准确的联合类型可以让 TypeScript 在：

```ts
message.role === "assistant"
```

之后自动知道：

```ts
message.result
```

可能存在。

## 二十二、消息气泡的语义

每条消息使用：

```html

```

消息列表使用：

```html

```

用户消息靠右：

```txt

```

助手消息靠左：

```txt

```

每条消息还应有可读标签：


```ts
  onQuestionChange(value: string): void;

  error: string;
```

```tsx
export function ChatComposer({
  question,
```

## 三十、为什么使用 form.requestSubmit

键盘 Enter 不应直接调用：

```ts
handleSubmit(...)
```

`requestSubmit()` 会走标准表单提交路径：

```txt
textarea keydown
  ↓
form.requestSubmit()
  ↓
onSubmit
  ↓
统一校验和请求逻辑
```

按钮点击和键盘发送因此共享同一份逻辑。

## 三十一、客户端校验不能代替服务端校验

输入框已经有：

```txt

```

但服务端仍必须保留第 30 课的：

```txt

```

因为浏览器界面可以被绕过。

正确关系：

```txt
客户端校验
  → 更快反馈

服务端校验
  → 最终安全边界
```

## 三十六、为什么消息使用数组

每次提交先加入：

```txt
user message
```

成功后再加入：

```txt
assistant message
```

顺序自然形成：

```ts
[
  welcome,
  userQuestion1,
  assistantAnswer1,
  userQuestion2,
  assistantAnswer2,
]
```

更新数组必须使用函数形式：

```ts
setMessages((current) => [
  ...current,
  newMessage,
]);
```

这样不会依赖闭包中的旧数组。

## 三十七、消息 ID 从哪里来

浏览器中可以使用：

```ts
crypto.randomUUID()
```

它只用于 React 列表 key。

不要把这个本地消息 ID 当成：

```txt
historyId
conversationId
数据库主键
```

三者是不同概念。

## 三十八、为什么需要 submissionLockRef

按钮禁用依赖：

```ts
isSubmitting
```

但 React 状态更新不是同步互斥锁。

用户快速按两次 Enter 时，第二次事件有可能在重新渲染前发生。

所以提交函数开头增加：

```ts
if (submissionLockRef.current) {
  return;
}
```

开始请求时：

```ts
submissionLockRef.current = true;
```

结束时：

```ts
submissionLockRef.current = false;
```

这能降低重复请求和重复历史记录风险。

## 三十九、提交前保存原问题

提交时先执行：

```ts
const normalizedQuestion = question.trim();
```

然后保存：

```ts
const submittedQuestion = normalizedQuestion;
```

因为输入框会立即清空。

网络请求和失败恢复必须使用：

```txt
submittedQuestion
```

不能继续依赖可能变化的 `question` 状态。

## 四十、为什么先显示用户消息

用户按下发送后，页面应立即：

```txt
显示用户气泡
清空输入框
显示 loading
```

不需要等 DeepSeek 和数据库全部完成后再显示用户问题。

这叫：

```txt
optimistic UI 的局部应用
```

但我们只乐观展示“用户已经提交的问题”。

不会提前展示虚构的计算结果。

## 四十一、处理 API 响应的正确顺序

建议顺序：

```txt
fetch
  ↓
读取 JSON
  ↓
Zod 校验整个响应
  ↓
检查 response.ok
  ↓
检查 body.ok
  ↓
加入助手消息
```

需要区分：

### 1. 网络失败

```txt
fetch 抛错
```

### 2. 响应不是合法 JSON

```txt
response.json() 抛错
```

### 3. JSON 不符合 Chat 契约

```txt
chatApiResponseSchema 失败
```

### 4. API 业务失败

```txt
body.ok === false
```

### 5. 完整成功

```txt
response.ok === true
body.ok === true
```

## 四十三、读取响应的辅助函数

在页面文件中建立：

```ts
async function readChatResponse(
  response: Response,
) {
  let value: unknown;

  try {
    value = await response.json();
  } catch {
    throw new ChatPageError(
      "服务器返回了无法读取的响应。",
    );
  }

  const parsed =
    chatApiResponseSchema.safeParse(value);

  if (!parsed.success) {
    throw new ChatPageError(
      "服务器返回的数据结构不符合预期。",
    );
  }

  if (!response.ok || !parsed.data.ok) {
    if (!parsed.data.ok) {
      throw new ChatPageError(
        getChatErrorMessage(parsed.data.error),
      );
    }

    throw new ChatPageError(
      "聊天请求处理失败，请稍后重试。",
    );
  }

  return parsed.data.data;
}
```

## 四十四、为什么同时检查 response.ok 和 body.ok

可能出现异常组合：

```txt
HTTP 500
但 body.ok === true
```

或：

```txt
HTTP 200
但 body.ok === false
```

正常 API 不应该这样返回，但客户端不能把冲突状态误认为完整成功。

完整成功要求：

```txt
HTTP 成功
并且
业务壳成功
```

## 四十五、完整 handleSubmit

页面中的提交函数参考：

```tsx
async function handleSubmit(
  event: FormEvent<HTMLFormElement>,
) {
  event.preventDefault();

  if (submissionLockRef.current) {
    return;
  }

  const submittedQuestion = question.trim();

  if (!submittedQuestion) {
    setError("请输入一个财务问题。");
    return;
  }

  submissionLockRef.current = true;
  setIsSubmitting(true);
  setError("");

  const userMessage: ChatMessage = {
    id: crypto.randomUUID(),
    role: "user",
    content: submittedQuestion,
  };

  setMessages((current) => [
    ...current,
    userMessage,
  ]);
  setQuestion("");

  try {
    const response = await fetch("/api/chat", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
      },
      body: JSON.stringify({
        question: submittedQuestion,
      }),
    });

    const result =
      await readChatResponse(response);

    const assistantMessage: ChatMessage = {
      id: crypto.randomUUID(),
      role: "assistant",
      content: result.reply,
      result,
    };

    setMessages((current) => [
      ...current,
      assistantMessage,
    ]);
  } catch (caughtError) {
    setError(
      caughtError instanceof ChatPageError
        ? caughtError.message
        : "无法连接服务器，请稍后重试。",
    );

    setQuestion((current) =>
      current.length === 0
        ? submittedQuestion
        : current,
    );
  } finally {
    submissionLockRef.current = false;
    setIsSubmitting(false);
  }
}
```

## 四十六、失败时为什么恢复输入

请求失败后，用户已经输入的内容不应该消失。

本课在输入框仍为空时恢复：

```ts
submittedQuestion
```

使用：

```ts
setQuestion((current) => ...)
```

是为了避免覆盖用户在异常情况下已经输入的新内容。

页面保留之前的用户气泡，用来表明：

```txt
哪一个问题发送失败
```

错误提示则说明没有得到有效回复。

## 四十七、为什么不自动重试

第 30 课已经说明：

```txt
POST /api/chat
```

成功时会创建：

```txt
calculation_history
```

如果服务端已经保存历史，但响应在网络中丢失，自动重试可能创建重复历史。

所以本课：

- 不自动重试。
- 不静默重发。
- 由用户明确再次发送。
- 请求中禁用输入和按钮。

以后加入幂等键后，再设计安全重试。

- 助手结果加入后需要滚动。
- loading 消失后页面高度也可能变化。

当用户展开：


页面会变长。

本课不在展开时强制滚动到底部，因为用户正在阅读步骤。

```txt
消息新增

```

不要让页面在用户阅读旧消息时不断抢夺滚动位置。

```tsx
    } catch (caughtError) {
      setError(
        caughtError instanceof ChatPageError
          ? caughtError.message
          : "无法连接服务器，请稍后重试。",
      );

      setQuestion((current) =>
        current.length === 0
          ? submittedQuestion
          : current,
      );
    } finally {
      submissionLockRef.current = false;
      setIsSubmitting(false);
    }
  }

  return (
    <main className="min-h-screen bg-gray-50 px-6 py-8">
      <div className="mx-auto max-w-5xl">
        <header className="mb-8">
          <p className="text-sm font-medium text-gray-500">
            Chat
          </p>
          <h1 className="mt-2 text-3xl font-bold text-gray-900">
            AI 财务对话
          </h1>
          <p className="mt-2 max-w-2xl text-sm text-gray-600">
            用自然语言提出储蓄目标问题。
            AI 负责理解问题，金额结果由确定性计算函数生成。
          </p>
        </header>

        <div className="grid gap-6 lg:grid-cols-[minmax(0,2fr)_minmax(15rem,1fr)]">
          <div className="min-w-0">
            <ChatMessageList
              messages={messages}
              isSubmitting={isSubmitting}
              endRef={messagesEndRef}
            />

            <ChatComposer
              question={question}
              onQuestionChange={(value) => {
                setQuestion(value);

                if (error) {
                  setError("");
                }
              }}
              onSubmit={handleSubmit}
              isSubmitting={isSubmitting}
              error={error}
            />
          </div>

          <aside className="h-fit rounded-lg border border-gray-200 bg-white p-5 shadow-sm">
            <h2 className="text-sm font-semibold text-gray-900">
              示例问题
            </h2>
            <p className="mt-2 text-xs leading-5 text-gray-500">
              当前版本支持储蓄目标问题。
              点击后可以继续修改。
            </p>

            <div className="mt-4 space-y-3">
              {chatExamples.map((example) => (
                <button
                  key={example}
                  type="button"
                  disabled={isSubmitting}
                  onClick={() => {
                    setQuestion(example);
                    setError("");
                  }}
                  className="w-full rounded-md border border-gray-200 px-3 py-2 text-left text-sm text-gray-600 hover:border-gray-400 hover:text-gray-900 disabled:opacity-50"
                >
                  {example}
                </button>
              ))}
            </div>
          </aside>
        </div>
      </div>
    </main>
  );
}
```

## 五十三、为什么主列需要 min-w-0

网格子项默认可能被长内容撑开。

计算步骤中存在：

```txt
长公式
长金额
长 historyId
```

主列增加：

```txt
min-w-0
```

能让：

```txt
overflow-x-auto
break-all
```

按预期工作，减少整个页面横向溢出。

## 五十四、当前消息列表不是真正多轮对话

页面状态中会出现：

```txt
问题 1
回答 1
问题 2
回答 2
```

但每次请求只发送：

```json
{
  "question": "当前问题"
}
```

没有发送：

```txt
之前的 messages
conversationId
上一轮 calculation
```

所以：

```txt
视觉上是连续消息
业务上仍是多个独立单轮请求
```

页面文档和产品文案不能声称已经支持上下文追问。

例如：

```txt
那如果改成三年呢？
```

模型只看到这一句，可能无法知道“那”指哪个目标。

用户当前应输入完整问题：

```txt
如果改成三年，我能攒够 50 万吗？
```

## 五十五、为什么不把全部 messages 发给 API

第 30 课的请求 schema 是：

```ts
{
  question: string;
}
```

如果页面突然发送：

```ts
{
  question,
  messages,
}
```

严格 schema 会拒绝。

更重要的是，多轮对话需要重新设计：

- 哪些历史消息可信。
- 哪些计算结果可引用。
- 如何限制长度。
- 如何保存 conversation。
- 如何防 Prompt Injection 扩散。
- 是否把敏感财务数据重复发送给模型。
- 如何处理历史公式版本。

不能只靠前端多传一个数组。

## 五十六、Loading 状态应该锁定哪些操作

请求中禁用：

- textarea。
- 发送按钮。
- 示例问题按钮。

这样保证一次只有一个正在进行的请求。

不要禁用：

- 已有消息阅读。
- “查看计算过程”展开。
- 页面导航。

如果用户离开页面，请求可能仍在服务端完成。

因此本课不显示误导性的：

```txt
取消计算
```

按钮。

## 五十七、离开页面不一定取消服务端写入

即使浏览器中断等待，服务端可能已经：

```txt
解析意图
完成计算
保存历史
```

所以：

```txt
前端取消 fetch
```

不等于：

```txt
撤销数据库写入
```

真正取消需要服务端协作和清晰事务设计。

本课不实现取消。

## 五十八、错误显示在哪里

本课把错误显示在输入框下方。

原因是错误通常和刚才的提交动作有关。

错误使用：

```html
role="alert"
```

让辅助技术更容易感知。

不要只改变边框颜色而不提供文字。

## 五十九、失败后消息列表应怎样表现

例如：

```txt
你：我两年内能攒够 50 万吗？
```

请求失败后：

- 用户消息保留。
- loading 消失。
- 输入框恢复原问题。
- 错误区域显示原因。
- 不加入伪助手回复。
- 不加入伪计算卡片。

不要显示：

```txt
AI：抱歉，失败了
```

同时又让页面误以为这是一条正常助手消息。

错误状态和成功消息应分开。

## 六十、结构化结果必须放在对应回复下方

每个助手消息自身保存：

```ts
result?: ChatSuccessData
```

所以结果卡片自然出现在对应回复内部。

不要只设置一个全局：

```ts
const [latestResult, setLatestResult] = ...
```

否则第二次请求会覆盖第一次结果，旧回复和新结果可能错配。

## 六十一、历史 ID 应如何展示

第一版可以显示：

```txt
计算历史 ID：...
```

它有两个作用：

- 证明结果已经保存。
- 为排查和后续详情页提供标识。

不要把它当成用户必须理解的核心金额。

因此使用较弱样式：

```txt
text-xs
text-gray-400
```

以后可以改成：

```txt
查看历史详情
```

链接，但本课现有历史 API 还没有单条详情页面。

## 六十二、假设信息不能隐藏

自然语言回复已经包含：

```txt
数据月份
年化收益率
```

结果卡片仍应结构化展示：

```txt
当前金额来源
月储蓄来源
数据月份
年化收益率
```

因为用户需要判断：

```txt
这个结果是否建立在我认可的口径上
```

“假设”不是错误，也不是脚注装饰。

它是财务结果的一部分。

## 六十三、金额暂时为什么不做本地化格式

当前 API 返回：

```txt
402609.52
```

本课直接展示：

```txt
402609.52 元
```

以后可以增加：

```ts
Intl.NumberFormat("zh-CN", {
  style: "currency",
  currency: "CNY",
});
```

但需要明确：

- 输入字符串如何转换。
- 是否保留两位小数。
- 超大金额如何显示。
- 是否在所有页面统一。

本课先保持与计算引擎输出完全一致，避免格式化掩盖原值。

## 六十四、不要用 dangerouslySetInnerHTML 渲染回复

当前 `reply` 是普通文本。

正确：

```tsx
<p>{message.content}</p>
```

不要：

```tsx
<div
  dangerouslySetInnerHTML={{
    __html: message.content,
  }}
/>
```

模型输出和用户输入都不应未经清洗直接当 HTML。

本课也不需要 Markdown 渲染库。

## 六十五、为什么用户消息默认是安全文本

React 使用：

```tsx
{message.content}
```

时会对文本进行转义。

用户输入：

```html
<script>alert(1)</script>
```

会显示成文本，而不会被当作脚本执行。

不要绕过 React 的默认转义。

## 六十六、基础可访问性检查

页面应至少满足：

- textarea 有 `<label>`。
- 发送按钮有明确文字。
- 示例问题使用 `<button>`。
- loading 使用 `aria-live="polite"`。
- 错误使用 `role="alert"`。
- 消息角色有文字标签。
- `<summary>` 可用键盘展开。
- disabled 状态不仅靠颜色表达。
- 文本颜色有足够对比度。

不要把：

```txt

```

当按钮使用。

## 六十八、页面刷新后消息会消失

本课消息只保存在：

```txt

```


## 八十二、常见错误一：只保存最后一次结果

错误：

```ts
const [result, setResult] =
  useState<ChatSuccessData | null>(null);
```

如果页面同时保留多条消息，单个全局结果会和消息错配。

本课把结果放入对应的助手消息：

```ts
{
  role: "assistant",
  content: result.reply,
  result,
}
```

## 八十三、常见错误二：提交后清空全部消息

错误：

```ts
setMessages([userMessage]);
```

这会删除欢迎语和之前结果。

正确：

```ts
setMessages((current) => [
  ...current,
  userMessage,
]);
```

## 八十四、常见错误三：使用数组下标作为 key

错误：

```tsx
messages.map((message, index) => (
  <article key={index}>
```

消息插入、删除或替换时，下标 key 可能导致 React 复用错误节点。

使用稳定本地 ID：

```ts
crypto.randomUUID()
```

## 八十五、常见错误四：只判断 response.ok

HTTP 200 仍可能返回：

```json
{
  "ok": false,
  "error": {}
}
```

页面还需要检查：

```txt
Zod 响应结构
body.ok
```

## 八十六、常见错误五：无条件显示 error.message

错误：

```ts
setError(
  caughtError instanceof Error
    ? caughtError.message
    : "失败",
);
```

任意错误可能带有内部信息。

本课只展示：

- `ChatPageError` 中已经整理过的用户文案。
- 固定网络兜底文案。

## 八十七、常见错误六：允许请求中再次提交

如果不禁用按钮，也没有 ref 锁：

```txt
双击
  ↓
两个 DeepSeek 请求
  ↓
两次计算
  ↓
两条历史
```

前端防重复不是完整幂等保证，但能减少普通误操作。

## 八十八、常见错误七：示例问题自动发送

点击示例就立刻产生费用和历史记录，会让用户失去确认机会。

本课只填入输入框。

## 八十九、常见错误八：把消息保存到 localStorage

用户问题可能包含：

- 收入。
- 资产目标。
- 债务。
- 家庭计划。

不要在没有隐私设计的情况下，把对话长期保存在浏览器。

## 九十、常见错误九：把 loading 加入 messages

如果 loading 是普通消息，请求失败或成功时都要精确删除。

第一版用：

```ts
isSubmitting
```

条件渲染更简单。

## 九十一、常见错误十：把视觉聊天当多轮上下文

页面显示旧消息，不代表下一次模型调用能看到旧消息。

当前每个问题必须独立完整。

## 九十六、复习问题

### 1. 为什么聊天页面需要 `"use client"`？

因为页面使用状态、effect、ref、表单事件、键盘事件和浏览器 fetch。

### 2. 为什么页面不能直接导入 `answerChatQuestion`？

它属于服务端业务编排并依赖数据库和 DeepSeek。浏览器只能通过 API route 调用。

### 3. 为什么网络响应还要使用 Zod？

TypeScript 类型不会在运行时检查 HTTP JSON，Zod 可以在数据进入页面状态前验证结构。

### 4. 为什么同时返回自然语言和结构化结果？

自然语言用于阅读，结构化结果用于稳定展示金额、状态、假设和步骤。

### 5. 为什么不能从 reply 中提取预计金额？

回复文案可能变化，正则提取脆弱；`calculation.projectedAmount` 才是稳定契约。

### 6. 为什么结果保存在助手消息中？

这样每次计算结果都和对应回复绑定，多次请求不会互相覆盖或错配。

### 7. 为什么 loading 不保存进 messages？

它只是当前请求的临时 UI 状态，条件渲染比插入后再删除消息更简单。

### 8. 为什么需要 `submissionLockRef`？

React 状态更新不是同步锁，快速连续事件可能在按钮重新渲染前触发多个请求。

### 9. 为什么不自动重试？

请求可能已在服务端保存历史但响应丢失，在没有幂等键时自动重试可能产生重复记录。

### 10. 为什么失败时恢复输入？

用户不应该因为网络或服务错误丢失刚才编辑的问题。

### 11. 为什么使用 `requestSubmit()`？

它让 Enter 发送和按钮点击走相同的标准表单提交与校验路径。

### 12. 为什么要检查 `isComposing`？

中文输入法中的 Enter 可能是在确认候选词，不检查会导致意外发送。

### 13. 为什么使用原生 `<details>`？

它提供展开、收起、键盘操作和基础语义，不需要额外状态。

### 14. 为什么示例问题不直接发送？

用户应有修改和确认机会，同时避免意外产生真实模型费用与历史记录。

### 15. 为什么当前页面不是真正多轮对话？

每次 API 请求只发送当前问题，没有发送之前消息或 conversationId。

### 16. 页面刷新后为什么消息会消失？

消息只保存在 React 内存状态中，本课尚未设计对话持久化。

### 17. calculation history 和聊天消息有什么区别？

calculation history 保存确定性计算审计；聊天消息是用户界面中的自然语言交流，两者的数据、隐私和生命周期不同。

### 18. 为什么不把对话直接写入 localStorage？

财务问题可能包含敏感信息，长期保存需要明确的隐私、过期和删除规则。

### 19. 为什么 assumptions 必须展示？

用户需要知道结果使用哪个月份、资金口径、月结余口径和收益率假设。

### 20. “查看计算过程”展示的是什么？

展示 `calculateSavingsGoal` 返回的确定性步骤，不是模型隐藏推理。

# 第 35 课：隐私、安全、部署与后续扩展

## 本课目标

第 34 课完成了项目的端到端验收：

```txt
创建账户
  ↓
导入本月流水
  ↓
查看仪表盘
  ↓
提出财务问题
  ↓
DeepSeek 解析意图
  ↓
本地代码读取数据并计算
  ↓
保存计算历史
  ↓
前端展示并回读历史
```

至此，MVP 已经从“许多单独功能”变成了“可以完整演示的产品”。

但是：

```txt
可以演示
```

不等于：

```txt
可以不加保护地交给任何人使用
```

个人财务项目保存的是高敏感数据：

- 账户名称和余额。
- 收入、支出和消费习惯。
- 负债金额、利率和还款信息。
- 储蓄目标和财务计划。
- 用户向 AI 提出的自然语言问题。
- 可以还原计算依据的历史记录。

因此，收官前必须回答四个问题：

```txt
数据存在哪里？
哪些数据会离开本机？
密钥有没有泄露风险？
项目现在适合用什么方式运行？
```

本课不追求“做出一个绝对安全的系统”。

本课要完成的是：

```txt
看清数据边界
  ↓
减少不必要的数据外发
  ↓
检查密钥、数据库和日志
  ↓
比较本地运行、私有部署和桌面封装
  ↓
选择当前阶段最合适的路线
  ↓
形成可以继续执行的开发计划
```

学完后，你应该能够：

- 正确解释“本地优先”，而不是把它误解成“完全离线”。
- 画出浏览器、Next.js、SQLite 和 DeepSeek 之间的信任边界。
- 列出项目保存、处理和外发的数据。
- 区分本地持久化数据、临时处理数据和外部发送数据。
- 说明当前 Chat 链路为什么没有把整份账单交给 LLM。
- 使用“数据最少化”原则设计 AI 请求。
- 判断什么信息不应该进入 Prompt。
- 正确管理 `.env.local` 和 `.env.example`。
- 说明为什么密钥不能使用 `NEXT_PUBLIC_` 前缀。
- 检查密钥和本地数据库是否被 Git 跟踪。
- 在不输出真实密钥的前提下完成基础泄露检查。
- 知道密钥已经泄露时应该先撤销和轮换。
- 识别日志、错误响应、截图和备份中的隐私风险。
- 为本地 SQLite 数据设计最小备份和恢复方案。
- 区分开发模式、生产构建和生产运行。
- 完成测试、lint、构建和本地生产模式冒烟检查。
- 解释本地运行、局域网私有部署、云端私有部署和桌面封装的区别。
- 说明为什么当前应用不能直接做静态导出。
- 判断什么时候必须补充鉴权、HTTPS、限流和多用户隔离。
- 为当前项目做出一份明确的部署决策。
- 把后续功能按风险和价值排序，而不是继续无边界扩展。
- 整理最终隐私安全检查记录和后续开发计划。

## 三、先理解“本地优先”

“本地优先”不是一个宣传口号。

在本项目中，它至少意味着：

1. 账户、流水、负债和计算历史默认保存在本机 SQLite。
2. 核心财务计算在本地确定性代码中完成。
3. 没有必要时，不把数据库内容发送给第三方。
4. 即使 AI 暂时不可用，已有数据和非 AI 计算仍应尽可能可访问。
5. 用户应该能知道哪些操作会访问外部服务。
6. 用户应该能备份、迁移和删除自己的本地数据。

但当前项目仍然不是完全离线应用。

因为：

```txt
用户自然语言问题
  ↓
POST /api/chat
  ↓
本机 Next.js 服务
  ↓
DeepSeek API
```

只要使用 DeepSeek，至少有一部分数据会离开本机。

因此，更准确的描述是：

> 财务数据库和确定性计算本地优先；AI 意图解析依赖外部 DeepSeek API。

不要写成：

```txt
所有数据绝不离开本机
```

这与真实架构不符。

---

## 四、本地优先不等于天然安全

本地保存可以减少一部分云端泄露面，但仍然存在风险：

- 电脑账户没有密码。
- 硬盘没有加密。
- 恶意软件读取本地文件。
- 数据库被错误提交到 Git。
- 备份文件被上传到公开网盘。
- 开发服务器监听了局域网地址。
- 浏览器扩展读取页面内容。
- 截图中出现余额、密钥或路径。
- 错误日志记录用户问题或流水。
- 多人共用同一个系统账户。

所以：

```txt
本地保存
≠
自动加密
≠
自动鉴权
≠
自动备份
≠
不会泄露
```

安全不是由“SQLite”三个字自动提供的。

## 六、给数据划分敏感等级

本课使用四级分类：

| 等级 | 含义 | 本项目示例 |
| --- | --- | --- |
| 低 | 泄露后影响有限 | 页面主题、功能开关 |
| 中 | 能反映个人偏好或行为 | 普通财务问题、目标期限 |
| 高 | 可推断个人财务状况 | 余额、流水、负债、计算历史 |
| 极高 | 泄露后可直接造成严重后果 | API Key、完整原始账单、身份与账户组合信息 |

分类的目的不是制造恐慌。

它用于决定：

- 是否必须保存。
- 保存在哪里。
- 是否允许记录日志。
- 是否允许进入截图。
- 是否允许发给 LLM。
- 应该多久删除。
- 是否需要加密和访问控制。

一个简单原则是：

```txt
敏感度越高
  ↓
默认收集越少
  ↓
保存时间越短
  ↓
访问范围越小
  ↓
检查要求越严格
```

## 七、画出当前项目的信任边界

当前本地运行架构可以画成：

```txt
┌────────────────────── 本机 ──────────────────────┐
│                                                  │
│  浏览器页面                                      │
│      │                                           │
│      │ localhost HTTP                            │
│      ▼                                           │
│  Next.js 页面与 Route Handlers                   │
│      │                     │                     │
│      │                     └── 读取服务端环境变量 │
│      │                         DEEPSEEK_API_KEY   │
│      ▼                                           │
│  service 层                                      │
│      │                                           │
│      ├── SQLite：账户、流水、负债、历史           │
│      │                                           │
│      └── 确定性财务计算                          │
│                                                  │
└──────────────────────┬───────────────────────────┘
                       │ HTTPS
                       │ 用户问题 + 意图解析 Prompt
                       ▼
              ┌──────────────────┐
              │ DeepSeek API     │
              │ 外部信任边界     │
              └──────────────────┘
```

图中的关键边界有三个：

### 边界 1：浏览器与服务端

浏览器不能直接拿到：

- `DEEPSEEK_API_KEY`。
- SQLite 文件。
- 服务端环境变量。

浏览器只能通过 API 请求获得服务端主动返回的数据。

### 边界 2：服务端与本地数据库

Next.js 服务可以读取完整财务数据。

因此服务端代码、API 路由和日志属于高信任区域。

### 边界 3：本机与 DeepSeek

跨过这个边界的数据会离开本机。

任何发送内容都必须回答：

```txt
完成当前任务真的需要这些字段吗？
```

如果答案是否定的，就不应该发送。

## 八、检查当前 Chat 链路到底发送了什么

打开：

```txt
lib/ai/parse-intent-with-deepseek.ts
```

当前核心调用类似：

```ts
const rawOutput = await requestDeepSeekJson({
  systemPrompt: FINANCE_INTENT_PROMPT,
  userMessage: normalized,
  fetcher,
});
```

这表示意图解析阶段发送的是：

- 固定系统 Prompt。
- 用户当前输入的问题。

然后打开：

```txt
lib/chat/chat-service.ts
```

可以看到：

```ts
const [transactions, accounts] = await Promise.all([
  deps.listTransactions(),
  deps.listAccounts(),
]);

const context = buildSavingsGoalContext(
  intent.targetAmount,
  intent.deadlineMonths,
  transactions,
  accounts,
  deps.nowFn,
);

const calculation = calculateSavingsGoal(context.input);
```

顺序是：

```txt
用户问题
  ↓
DeepSeek 只产生结构化意图
  ↓
本地读取账户和流水
  ↓
本地构造计算上下文
  ↓
本地确定性计算
```

这正是本项目最重要的隐私设计之一：

> DeepSeek 不需要看到整份账户和流水，也能完成“识别用户想算什么”这一步。

## 九、数据最少化不是简单删除字段

数据最少化包括五个问题：

1. 是否需要收集？
2. 是否需要发送？
3. 是否需要保存？
4. 是否需要原始精度？
5. 是否需要长期保留？

例如，用户问：

```txt
我 12 个月后能攒到 10 万吗？
```

意图解析真正需要的是：

```json
{
  "type": "savings_goal",
  "targetAmount": "100000",
  "deadlineMonths": 12
}
```

它不需要：

- 每笔早餐消费。
- 账户真实名称。
- 商户名称。
- 银行卡尾号。
- CSV 原始文本。
- 负债备注。
- 完整计算历史。

本地计算可能需要月结余和流动账户余额，但也不代表这些数据必须先发送给 LLM。

## 十、哪些内容不要进入 Prompt

默认不要把以下内容发给 LLM：

- API Key。
- 完整 `.env.local`。
- 完整 SQLite 数据库内容。
- 未脱敏原始 CSV。
- 银行卡号、身份证号、手机号和邮箱。
- 带有真实姓名的账户备注。
- 与当前问题无关的流水。
- 完整错误堆栈。
- 本机绝对路径。
- Git 凭据或其他服务令牌。

即使将来为了生成自然语言解释需要发送计算结果，也应该优先发送：

```json
{
  "targetMet": true,
  "projectedAmount": "105230.18",
  "targetAmount": "100000.00",
  "months": 12
}
```

而不是：

```json
{
  "allAccounts": [],
  "allTransactions": [],
  "allLiabilities": [],
  "fullCalculationHistory": []
}
```

只发送生成回复所需的最小结果。

## 十一、用户自己输入了隐私信息怎么办

即使程序没有主动发送数据库，用户仍可能输入：

```txt
我的银行卡号是……
我的身份证号是……
我在某公司工作，税后收入是……
```

因此，产品界面应该明确提示：

> AI 问题会发送给外部模型服务进行意图解析，请不要输入银行卡号、身份证号、密码等不必要的敏感信息。

当前 MVP 可以先在 Chat 页面说明数据边界。

后续可以增加：

- 首次使用 AI 时的确认提示。
- 常见敏感格式的本地检测。
- 用户发送前的二次确认。
- 关闭 AI 功能的纯本地模式。
- 可查看的“本次将发送什么”预览。

但不要承诺：

```txt
程序能识别并拦截所有隐私信息
```

正则表达式和规则只能降低风险，不能保证零遗漏。

## 十三、环境变量不是魔法保险箱

当前项目使用：

```dotenv
DB_FILE_NAME=file:./data/dev.db
DEEPSEEK_API_KEY=你的真实密钥
DEEPSEEK_MODEL=当前项目已验证可用的模型
CHAT_SAVINGS_ANNUAL_RATE=3
```

环境变量解决的是：

```txt
配置与代码分离
```

它不自动解决：

- 本机文件权限。
- 终端历史。
- 截图泄露。
- 进程权限。
- 服务器密钥管理。
- Git 历史泄露。
- 日志泄露。

`.env.local` 仍然是一个包含明文的本地文件。

它应该被认真保护。

## 十四、为什么不能使用 `NEXT_PUBLIC_`

Next.js 中：

```txt
普通环境变量
  ↓
默认只在服务端可用
```

而：

```txt
NEXT_PUBLIC_ 开头
  ↓
可能在构建时进入浏览器 JavaScript
```

所以绝对不要写：

```dotenv
NEXT_PUBLIC_DEEPSEEK_API_KEY=真实密钥
```

正确命名是：

```dotenv
DEEPSEEK_API_KEY=真实密钥
```

并且只能在服务端模块中读取：

```ts
const apiKey = process.env.DEEPSEEK_API_KEY;
```

不要在带有：

```ts
"use client";
```

的组件中读取密钥。

Next.js 官方环境变量文档也明确说明：只有带 `NEXT_PUBLIC_` 前缀的变量才应暴露给浏览器，而且这些值会进入客户端构建产物。

## 十五、修正 `.env.example` 的忽略规则

当前项目 `.gitignore` 中有：

```gitignore
.env*
```

它会正确忽略：

```txt
.env.local
.env.production.local
```

但也会忽略：

```txt
.env.example
```

而 README 需要一份不含真实值的示例配置。

把对应部分改为：

```gitignore
# env files
.env*
!.env.example
```

含义是：

```txt
先忽略全部 .env 文件
  ↓
再单独允许提交 .env.example
```

不要删除 `.env*`。

否则真实 `.env.local` 可能进入 Git。

## 十六、创建安全的 `.env.example`

在项目根目录创建：

```txt
.env.example
```

内容写成：

```dotenv

DB_FILE_NAME=file:./data/dev.db

# 必填：只放在服务端，绝不能添加 NEXT_PUBLIC_ 前缀。
DEEPSEEK_API_KEY=

# 可选：不填写时使用项目默认模型。
DEEPSEEK_MODEL=

# 可选：储蓄目标计算采用的年化收益率百分比。
CHAT_SAVINGS_ANNUAL_RATE=3
```

注意：

- 示例文件只保留变量名、注释和安全默认值。
- 不要把真实 Key 复制进去再删掉。
- 不要用“看起来像真实 Key”的长字符串当示例。
- `DB_FILE_NAME` 可以使用项目内的相对开发路径。
- `.env.example` 可以提交。
- `.env.local` 不能提交。

## 十七、检查 Git 是否跟踪敏感文件

先运行：

```bash
git check-ignore -v .env.local data/dev.db
```

预期能看到对应忽略规则。

再运行：

```bash
git ls-files -- .env.local 'data/*.db' 'data/*.sqlite' 'data/*.sqlite3'
```

理想结果是：

```txt
没有输出
```

没有输出表示这些路径当前没有被 Git 跟踪。

然后确认示例文件可以被跟踪：

```bash
git check-ignore .env.example
```

修正规则后，这条命令应该没有输出，并返回“未被忽略”的结果。

最后查看状态：

```bash
git status --short
```

你应该能看到：

```txt
?? .env.example
```

但不应该看到：

```txt
?? .env.local
?? data/dev.db
```

## 十八、检查仓库中是否出现疑似密钥

不要运行会把所有环境变量值直接打印到屏幕的命令。

可以先只查找包含可疑内容的文件名：

```bash
git grep -l -E 'DEEPSEEK_API_KEY=.+|sk-[A-Za-z0-9_-]{20,}' -- ':!package-lock.json'
```

这条命令只列出文件名，不直接展示匹配行。

可能出现两种情况：

### 情况 1：测试文件

例如：

```ts
process.env.DEEPSEEK_API_KEY = "test-api-key";
```

这是测试占位值，不是真实密钥。

仍要人工确认它明显是假值。

### 情况 2：课程或 README

例如：

```dotenv
DEEPSEEK_API_KEY=你的真实密钥
```

这也是说明文字。

### 情况 3：疑似真实密钥

不要把匹配内容粘贴到聊天、Issue 或截图中。

先按本课后面的泄露响应流程处理。

## 十九、检查 Git 历史中是否提交过敏感文件名

当前工作区没有跟踪 `.env.local`，不代表它从未进入过历史。

可以检查文件名：

```bash
git log --all --name-only --pretty=format: -- .env.local '.env.*.local' 'data/*.db'
```

如果没有输出，说明这些精确路径没有出现在可见 Git 历史中。

还可以检查某个文件当前是否曾被提交：

```bash
git log --all -- .env.local
```

这里只是基础检查。

正式项目还可以使用专门的密钥扫描工具，但扫描结果仍需要人工判断。

## 二十、如果密钥已经泄露

处理顺序非常重要。

正确顺序：

```txt
1. 立即在服务提供商后台撤销旧 Key
2. 创建新 Key
3. 更新本地或服务器配置
4. 验证旧 Key 已失效
5. 从当前文件中删除
6. 评估并清理 Git 历史、日志、截图和构建产物
7. 记录泄露时间、影响范围和处理结果
```

不要只做：

```txt
删除最新提交中的 Key
```

因为旧提交、远程仓库、其他人的克隆和 CI 日志中仍可能存在。

也不要把已经泄露的 Key 继续使用。

> 删除历史不能让一个已公开的密钥重新变安全，撤销和轮换必须优先。

如果仓库已经与他人协作，重写 Git 历史会影响所有协作者。

不要在没有协调的情况下独自执行强制推送。

## 二十一、API Key 还需要哪些保护

最小规则包括：

- 不写进源码。
- 不写进 README。
- 不写进 `.env.example`。
- 不写进测试快照。
- 不写进错误响应。
- 不输出到浏览器控制台。
- 不使用 `NEXT_PUBLIC_`。
- 不提交到 Git。
- 不在截图中展示。
- 不通过聊天工具发送。
- 不与不相关项目共用。
- 怀疑泄露时立即轮换。

进入私有部署后，还应该考虑：

- 使用部署平台的 Secret 管理。
- 限制谁可以读取生产配置。
- 区分开发、测试和生产 Key。
- 设置用量或费用告警。
- 定期轮换。
- 记录轮换责任人和时间。

## 二十二、不要在错误响应中泄露内部信息

错误应该帮助用户行动，但不应该暴露：

- API Key。
- DeepSeek 完整响应头。
- 完整请求体。
- SQLite 绝对路径。
- SQL 语句和数据库结构细节。
- 服务端堆栈。
- 用户完整财务上下文。

对用户可以返回：

```json
{
  "ok": false,
  "error": {
    "code": "AI_UPSTREAM_FAILED",
    "message": "AI 服务暂时不可用，请稍后重试"
  }
}
```

服务端开发日志可以记录：

```txt
错误码
上游 HTTP 状态
请求追踪 ID
发生时间
```

但不要记录：

```txt
Authorization 请求头
完整 Prompt
完整流水
完整账户列表
```

## 二十三、日志也属于数据存储

很多人只检查数据库，却忘记日志。

如果代码中有：

```ts
console.log(requestBody);
console.log(userMessage);
console.log(rawModelOutput);
console.log(process.env);
```

日志可能复制出另一份敏感数据。

检查：

```bash
rg -n 'console\.(log|debug|info|warn|error)' app lib
```

逐条判断：

- 是否真的需要。
- 是否包含用户输入。
- 是否包含模型原始输出。
- 是否包含路径或环境变量。
- 是否会在生产环境长期保存。

不要机械删除所有日志。

应该保留可定位问题但不包含敏感内容的结构化信息。

例如：

```ts
console.error("chat request failed", {
  code: errorCode,
  status: upstreamStatus,
});
```

## 二十五、检查本地数据库边界

当前数据库配置来自：

```txt
DB_FILE_NAME
```

开发环境通常是：

```dotenv
DB_FILE_NAME=file:./data/dev.db
```

检查：

```bash
ls -lh data
```

你需要知道：

- 哪个文件是日常开发数据库。
- 哪个文件是第 34 课演示数据库。
- 哪些文件是备份。
- 哪些文件可以删除。
- 哪些文件包含真实数据。

不要只凭文件名猜测后直接删除。

## 二十六、数据库文件没有自动加密

普通 SQLite 文件可以被有文件读取权限的程序打开。

当前课程没有实现数据库加密。

因此 README 和检查记录必须明确写：

> 当前 SQLite 数据库为本地明文文件，安全性依赖操作系统账户、磁盘加密、文件权限和设备安全；项目尚未实现应用级数据库加密。

这不是项目失败。

这是诚实的安全边界。

如果用户设备丢失，本地文件是否受保护，主要取决于：

- 操作系统登录保护。
- 全盘加密。
- 备份加密。
- 系统账户隔离。
- 恶意软件防护。

## 二十七、设计最小备份方案

本地优先意味着用户也要承担本地数据丢失风险。

最低备份方案应回答：

```txt
备份什么？
备份到哪里？
多久一次？
如何恢复？
如何确认备份真的可用？
```

可以在项目外准备一个受保护的备份目录。

备份前：

1. 停止开发服务器，避免复制过程中仍有写入。
2. 确认源数据库路径。
3. 不覆盖唯一一份旧备份。
4. 不把备份放进 Git 仓库。

示例：

```bash
mkdir -p backups
cp data/dev.db backups/dev-2026-07-30.db
```

这里的日期要换成实际备份日期。

检查：

```bash
ls -lh backups
```

备份目录也应加入 `.gitignore`：

```gitignore
/backups/
```

如果备份包含真实数据，优先放在：

- 加密磁盘。
- 受保护的个人备份位置。
- 有访问控制和加密的备份服务。

不要上传到公开链接。

## 二十八、没有恢复演练的备份不够可靠

备份文件存在，不代表能恢复。

可以使用一个临时恢复数据库进行演练：

```txt
原数据库
  ↓
复制为备份
  ↓
再复制为临时恢复文件
  ↓
临时修改 DB_FILE_NAME
  ↓
启动应用并读取
  ↓
恢复原配置
```

例如：

```bash
cp backups/dev-2026-07-30.db data/restore-check.db
```

临时配置：

```dotenv
DB_FILE_NAME=file:./data/restore-check.db
```

确认：

- 账户能读取。
- 流水能读取。
- 计算历史能读取。
- 应用没有修改原数据库。

演练完成后，先恢复 `.env.local` 中原来的路径。

是否删除临时恢复文件，要在确认路径后自行决定。

## 三十二、构建通过不等于生产运行通过

`npm run build` 只证明生产构建可以生成。

还要运行：

```bash
npm run start -- --hostname 127.0.0.1
```

然后打开：

```txt
http://127.0.0.1:3000
```

为什么明确使用：

```txt
127.0.0.1
```

因为它表示只监听本机回环地址。

当前项目没有用户登录和权限隔离，不应该为了“让手机也能打开”就直接监听全部网卡。

冒烟检查：

- 首页可以打开。
- 账户页面可以读取数据。
- 仪表盘可以读取数据。
- CSV 导入页面可以打开。
- Chat 页面可以打开。
- 缺少 Key 时返回安全错误。
- 配置测试 Key 时不发真实请求。
- 使用真实 Key 的人工请求只在明确同意后执行。
- 错误页面不显示堆栈和密钥。

完成后停止服务器。

如果看到：

## 三十五、比较四种运行路线

### 路线 A：单机本地运行

```txt
同一台电脑
浏览器访问 127.0.0.1
Next.js 和 SQLite 都在本机
只有 AI 请求访问外部 DeepSeek
```

优点：

- 数据边界最简单。
- 不需要公网服务器。
- 不需要用户系统。
- SQLite 很适合单用户。
- 最符合当前课程定位。

缺点：

- 需要本机安装和启动 Node.js 应用。
- 跨设备使用不方便。
- 备份由用户负责。
- 仍需保存 DeepSeek Key。

### 路线 B：局域网私有部署

```txt
一台家庭服务器或个人电脑运行
同一局域网设备访问
```

优点：

- 手机和平板可以访问。
- 数据仍可留在个人设备或家庭服务器。

新增风险：

- 服务监听范围扩大。
- 其他局域网设备可能访问。
- 必须考虑登录、HTTPS 或可信网络。
- 设备休眠、地址变化和防火墙会影响可用性。

### 路线 C：云端私有部署

```txt
Next.js 运行在云服务器
浏览器通过互联网访问
数据库和密钥也在服务器
```

优点：

- 多设备随时访问。
- 可以集中备份和运维。

新增成本：

- 必须实现鉴权。
- 必须使用 HTTPS。
- 必须配置持久化存储。
- 必须保护服务器环境变量。
- 必须处理网络攻击、限流和更新。
- 必须重新评估 SQLite 并发和多实例。
- 财务数据不再“只在用户本机”。

### 路线 D：桌面封装

```txt
Web UI
  +
本地原生应用外壳
  +
本地数据库和系统能力
```

优点：

- 更像普通桌面软件。
- 可以提供安装包。
- 更容易管理本地文件和应用生命周期。
- 可以进一步接入操作系统钥匙串。

新增成本：

- 打包和多平台兼容。
- 应用签名。
- 自动更新。
- 原生权限。
- 桌面框架自身的安全边界。
- Next.js 服务端逻辑可能需要重新适配。

## 三十六、部署方式对比表

| 维度 | 单机本地 | 局域网私有 | 云端私有 | 桌面封装 |
| --- | --- | --- | --- | --- |
| 当前改造成本 | 低 | 中 | 高 | 高 |
| 多设备访问 | 否 | 同一网络 | 是 | 每台设备安装 |
| 数据默认位置 | 用户电脑 | 家庭服务器 | 云服务器 | 用户电脑 |
| 是否必须登录 | 当前可不做 | 强烈建议 | 必须 | 单用户可依赖系统账户 |
| HTTPS | 回环地址可暂不做 | 建议 | 必须 | 外部请求仍用 HTTPS |
| SQLite 适配度 | 高 | 单实例较高 | 需谨慎评估 | 高 |
| 备份责任 | 用户 | 运维者 | 运维者 | 用户或应用 |
| 密钥位置 | `.env.local` | 服务器 Secret | 云端 Secret | 本地安全存储 |
| 攻击面 | 最小 | 扩大 | 最大 | 原生权限带来新边界 |
| 当前推荐度 | 高 | 暂缓 | 不推荐直接进行 | 作为后续调研 |

## 三十七、为什么当前项目不能直接静态导出

Next.js 静态导出适合：

```txt
只需要 HTML、CSS 和浏览器 JavaScript 的网站
```

当前项目依赖：

- Route Handlers。
- 服务端环境变量。
- SQLite。
- 服务端 Drizzle。
- DeepSeek 服务端调用。
- 数据写入。

因此不能简单地把项目导出成一组静态文件后继续保留全部功能。

如果强行静态化，就必须重新设计：

- 数据库存在哪里。
- API Key 存在哪里。
- 浏览器如何安全调用 DeepSeek。
- 如何持久化计算历史。
- 如何保护用户数据。

尤其不能把 DeepSeek Key 移到浏览器来“解决”静态部署。

## 三十八、Node.js 私有部署需要什么

Next.js 可以作为 Node.js 服务运行：

```bash
npm run build
npm run start
```

但公开或远程访问前，至少需要：

- 用户身份认证。
- 授权检查。
- HTTPS。
- 反向代理。
- 请求体大小限制。
- 速率限制。
- 防火墙。
- 生产 Secret 管理。
- 持久化数据库目录。
- 备份和恢复。
- 安全更新。
- 错误日志脱敏。
- 健康检查。
- 故障告警。

Next.js 官方自托管文档建议在应用服务器前使用反向代理，以处理畸形请求、慢连接、请求大小和限流等问题。

不能把：

```txt
npm run start
```

直接等同于：

```txt
已经安全上线
```

## 三十九、为什么云端部署必须先做鉴权

当前本地版 API 包括：

```txt
/api/accounts
/api/transactions
/api/liabilities
/api/chat
/api/calculations/history
```

在本机回环地址上，它们只供当前设备使用。

一旦暴露到网络：

```txt
知道地址的人
  ↓
可能直接请求 API
  ↓
读取或修改财务数据
```

仅仅隐藏页面按钮没有作用。

鉴权必须在服务端 API 层执行。

未来多用户版本还必须让每条数据带有用户归属，并在每次查询中做授权过滤。

只增加一个登录页面，但数据库查询仍返回所有记录，不是真正的多用户隔离。

## 四十、SQLite 部署时要注意什么

SQLite 的优势是：

- 简单。
- 单文件。
- 本地优先。
- 很适合单用户和单实例。

但云端部署会出现新问题：

- 一些平台文件系统是临时的。
- 重新部署后本地文件可能丢失。
- 多实例可能拥有各自独立文件。
- 同时写入的并发模型需要评估。
- 备份和迁移需要正式流程。

因此云端部署不能只问：

```txt
Next.js 能不能启动？
```

还要问：

```txt
SQLite 文件是否位于持久化磁盘？
重启后是否仍存在？
多个实例是否读写同一份数据？
备份是否可恢复？
```

当前课程不进入多实例部署。

## 四十一、桌面封装不是“加一个壳”那么简单

常见方向包括：

- Tauri。
- Electron。

### Electron

Electron 使用 Web 技术构建桌面应用，并带有 Chromium 和 Node.js 能力。

它成熟、生态丰富，但原生能力也扩大了风险。

Electron 官方安全指南强调：

- 不要给不可信远程内容启用 Node.js 集成。
- 使用上下文隔离和进程沙箱。
- 不要关闭 `webSecurity`。
- 限制导航和新窗口。
- 校验 IPC 发送方。
- 保持 Electron 和依赖更新。

### Tauri

Tauri 使用系统 WebView，并通过 Rust 核心与前端通信。

它提供 capability 和 permission 机制，用于限制 WebView 可以访问的系统能力。

但这不表示使用 Tauri 后自动安全。

仍然需要：

- 最小权限。
- 安全的命令接口。
- 输入校验。
- 密钥存储设计。
- 更新和签名。
- 前端与核心进程之间的信任边界。

### 对当前项目的影响

当前项目把许多逻辑放在 Next.js Route Handlers 中。

桌面封装前需要先决定：

```txt
保留本地 Next.js 服务
```

还是：

```txt
把 API 和数据库能力迁移到桌面核心进程
```

这属于架构改造，不是本课的一次练习。

## 四十七、推荐的 P0 计划

```md
## P0：安全、正确性与可恢复性

### 1. 数据导出与全量备份

- 目标：用户可以主动备份自己的数据。
- 前置：明确所有数据表和版本。
- 最小交付：导出数据库或结构化 JSON。
- 验收：全新临时数据库可以恢复并读取核心数据。

- 目标：用户可以删除历史、导入数据或全部本地数据。

- 最小交付：清晰确认、删除范围说明、结果验证。
- 验收：删除后对应查询不再返回记录。

### 3. LLM 数据边界提示

- 目标：用户发送前知道问题会访问外部服务。
- 最小交付：Chat 页面提示和首次确认。
- 验收：未确认时不会发送请求。

### 4. 日志脱敏与错误分类

- 目标：错误可诊断，但不记录密钥和完整财务数据。
- 最小交付：统一错误码和安全日志字段。
- 验收：错误路径测试中不出现敏感字段。

### 5. 数据库版本与恢复测试

- 目标：迁移后旧数据仍可读取。
- 最小交付：迁移记录、备份说明、恢复演练。
- 验收：使用备份完成一次恢复。
```

P0 不一定最吸引人，但最接近“用户可以放心长期使用”。

- `npm run start -- --hostname 127.0.0.1` 可以启动。
- 生产模式基础页面可以打开。
- 错误路径不会展示密钥和服务端堆栈。

### 部署理解

- 能说明本地运行和私有部署的区别。
- 能说明局域网部署也扩大了访问面。
- 能说明公网部署为什么必须先做鉴权。
- 能说明当前项目为什么不能直接静态导出。
- 能说明 SQLite 在临时文件系统和多实例中的风险。
- 能说明桌面封装会引入新的权限和更新边界。
- 能为当前阶段选择单机本地运行，并写出重新评估条件。

## 五十四、常见错误

### 错误 1：本地优先等于所有数据都不出本机

当前用户问题会发送给 DeepSeek。

应该准确描述边界。

### 错误 2：把 Key 改成 `NEXT_PUBLIC_` 解决浏览器调用

这会把密钥暴露给客户端。

DeepSeek 必须由服务端调用。

### 错误 3：只在最后一次提交删除密钥

旧提交可能仍然包含密钥。

先撤销和轮换，再处理历史。

### 错误 4：把 `.env.example` 也永久忽略

新用户就不知道需要哪些变量。

应该使用忽略后的例外规则。

### 错误 5：示例配置放入“暂时可用”的真实 Key

示例文件会被提交。

Key 字段必须留空。

### 错误 6：有 SQLite 就认为数据已经加密

普通 SQLite 是明文数据库文件。

要依赖设备保护，或后续实现应用级加密。

### 错误 7：备份放在仓库中

`.gitignore` 不应该只忽略 `data/dev.db`，还要忽略备份目录。

### 错误 8：只备份，从不恢复

损坏或不可读的备份没有价值。

要用临时文件完成恢复演练。

### 错误 9：`npm run build` 通过就直接上线

构建不包含鉴权、HTTPS、备份和运维能力。

### 错误 10：为了手机访问直接监听 `0.0.0.0`

当前 API 没有权限保护。

这会扩大访问面。

### 错误 11：把“私有仓库”当作 Secret 管理

私有仓库仍可能被误共享、日志复制或账号泄露。

密钥不应该进入 Git。

### 错误 12：把所有财务数据交给 LLM，让它自己总结

这破坏数据最少化和确定性计算边界。

先在本地聚合，再只发送必要结果。

### 错误 13：使用 `npm audit fix --force` 后不测试

强制升级可能破坏依赖兼容性。

所有依赖升级都要重新运行测试和构建。

### 错误 14：同时做云部署和桌面封装

两条路线的运行时、密钥和数据存储设计不同。

应该先选择一个真实需求。

## 五十五、复习问题

### 1. 什么是本项目中的“本地优先”？

账户、流水、负债、计算历史和确定性计算默认留在本机；AI 意图解析仍会把用户当前问题发送给 DeepSeek。

### 2. 为什么本地优先不等于完全离线？

当前 Chat 功能依赖外部 DeepSeek API。

### 3. 当前 DeepSeek 是否需要读取整份数据库？

不需要。当前意图解析只需要用户问题，本地 service 在意图返回后读取账户和流水并计算。

### 4. 为什么数据最少化能提升安全性？

没有收集、发送或长期保存的数据，就不会在对应环节泄露。

### 5. 为什么密钥不能使用 `NEXT_PUBLIC_`？

带此前缀的值可能被 Next.js 内联到浏览器构建产物，任何用户都可能读取。

### 6. `.env.local` 和 `.env.example` 有什么区别？

`.env.local` 保存本机真实配置，不能提交；`.env.example` 只说明变量名和安全示例，可以提交。

### 7. 为什么当前 `.gitignore` 需要增加 `!.env.example`？

因为 `.env*` 会连示例文件一起忽略，需要显式允许示例文件。

### 8. 为什么检查 Git 当前文件还不够？

真实密钥可能已经存在于旧提交、远程仓库、构建日志或其他人的克隆中。

### 9. 密钥泄露后的第一步是什么？

立即在服务提供商后台撤销旧 Key，然后创建并替换新 Key。

### 10. SQLite 文件是否自动加密？

普通 SQLite 文件不自动加密，当前项目依赖设备、系统账户、磁盘加密和文件权限。

### 11. 为什么备份前建议停止应用？

可以降低复制过程中数据库仍在写入所带来的不一致风险。

### 12. 为什么需要恢复演练？

只有确认备份能重新启动并读取数据，才能证明备份具有实际恢复价值。

### 13. 为什么日志也要进入数据资产清单？

日志可能长期保存用户问题、错误上下文和模型输出，形成数据库之外的敏感副本。

### 14. 为什么生产模式要只监听 `127.0.0.1`？

当前应用没有完整鉴权，本地回环监听能限制普通网络设备直接访问服务。

### 15. 为什么局域网部署也需要安全设计？

同一网络中的其他设备可能访问服务，局域网并不等于只有当前用户。

### 16. 为什么不能直接静态导出？

项目依赖 Route Handlers、SQLite、服务端环境变量、数据写入和 DeepSeek 服务端调用。

### 17. 为什么云端部署必须使用持久化存储？

临时文件系统可能在重启或重新部署后丢失 SQLite 文件。

### 18. 为什么只做登录页面还不够？

服务端每次查询都必须验证用户身份和数据归属，否则仍可能读取或修改其他数据。

### 19. 桌面封装会带来什么新风险？

文件系统、系统命令、IPC、原生权限、应用签名和自动更新都会形成新的信任边界。

### 20. 当前项目最合适的运行方式是什么？

单机本地运行、只监听回环地址、SQLite 留在本地、DeepSeek 只做受限意图解析。

## 五十六、本课小结

这一课没有继续增加新的计算器或图表。

它完成的是项目从“能运行”走向“知道自己边界”的最后一步：

```txt
盘点敏感数据
  ↓
画出信任边界
  ↓
核对 LLM 外发内容
  ↓
确认账户和流水留在本地计算
  ↓
保护 .env.local 和 API Key
  ↓
检查 Git、日志、截图和备份
  ↓
运行测试、lint、build 和生产冒烟
  ↓
比较运行与部署路线
  ↓
选择单机本地运行
  ↓
整理后续 P0、P1、P2 计划
```

本项目最重要的产品原则仍然是：

> AI 负责理解语言和组织表达，财务结果必须由确定性代码计算。

本课又增加了一条同样重要的隐私原则：

> 默认让财务数据留在本地，只把完成当前 AI 任务真正需要的最少信息发送给外部服务。

完成全部 35 课后，你已经经历了一条完整项目路线：

```txt
JavaScript 与 TypeScript
  ↓
React 与 Next.js
  ↓
API、Zod、SQLite 与 Drizzle
  ↓
财务数据 CRUD
  ↓
Decimal 与确定性计算
  ↓
可追溯步骤和测试
  ↓
DeepSeek 受限意图解析
  ↓
Chat、CSV 和仪表盘
  ↓
端到端验收
  ↓
隐私、安全和部署决策
```

此时最有价值的下一步，不是立刻增加十个功能。

而是：

```txt
用一段时间
  ↓
记录真实问题
  ↓
优先修复数据安全、正确性和恢复能力
  ↓
再选择一个明确方向继续扩展
```

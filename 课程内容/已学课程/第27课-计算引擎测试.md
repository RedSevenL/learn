## 本课目标

从第 20 课开始，项目逐步建立了确定性计算引擎：

```txt

储蓄目标

```

每一课都写了一些测试。

当前项目已经有：

```txt
7 个测试文件
59 个测试
```

运行：

```bash
npm run test:run
```

当前结果是：

```txt
Test Files  7 passed
Tests       59 passed
```

这说明当前已写的用例都通过，但不自动代表：

```txt
所有重要规则都已经测试
所有边界都已经覆盖
以后重构一定不会出错
```

这一课不再重复“怎样写第一个 Vitest 测试”，而是系统整理：

```txt
业务规则
  ↓
测试矩阵
  ↓
正常值、边界值、异常值
  ↓
财务不变量
  ↓
回归测试
  ↓
安全重构
```

学完后，你应该能够：

- 区分单元测试和集成测试。
- 使用 Arrange、Act、Assert 组织测试。
- 从业务规则推导测试，而不是随意凑数量。
- 为正常值、边界值和异常值建立测试矩阵。
- 测试时区、舍入、除以零和不可达状态。
- 使用财务不变量检查汇总结果。
- 验证纯函数不会修改输入。
- 把已发生的 bug 固化为回归测试。
- 理解测试与重构的关系。
- 使用 Vitest 运行全部、单个文件或单个用例。
- 说明覆盖率数字为什么不能代替测试质量。

## 四、单元测试和集成测试

### 单元测试

单元测试关注一个小而明确的计算单元：

```ts
calculateSavingsGoal(input)
```

它不需要：

- 启动 Next.js。
- 发送 HTTP 请求。
- 连接 SQLite。
- 操作浏览器。
- 调用 AI。

本课的 `tests/finance/` 主要是单元测试。

### 集成测试

集成测试关注多个模块连接后是否正确：

```txt
POST API
  ↓
Zod
  ↓
计算函数
  ↓
service
  ↓
SQLite
```

例如：

```txt
POST /api/calculations/savings-goal
是否真的写入 calculation_history
```

这是 API 与数据库集成测试，不应伪装成纯计算测试。

本课优先把纯计算引擎测试完整。

API、数据库和页面测试会在后续产品闭环阶段继续增加。

## 五、为什么计算引擎适合单元测试

计算函数大多符合：

```txt
明确输入
  ↓
确定性公式
  ↓
明确输出
```

它们不读取：

- 当前时间。
- 数据库。
- 网络。
- React state。

相同输入应该得到相同输出。

因此测试可以稳定写成：

```ts
const result = calculateSomething(input);

expect(result).toEqual(expected);
```

这也是前面坚持把数据库和计算函数分开的直接收益。

## 六、使用 Arrange、Act、Assert

一个测试可以分为三部分。

### Arrange：准备

```ts
const input = {
  income: "10000",
  expense: "6500"
};
```

### Act：执行

```ts
const result = calculateMonthlySurplus(input);
```

### Assert：断言

```ts
expect(result.surplus).toBe("3500.00");
```

完整结构：

```ts
it("用月收入减去月支出得到月结余", () => {
  // Arrange
  const input = {
    income: "10000",
    expense: "6500"
  };

  // Act
  const result = calculateMonthlySurplus(input);

  // Assert
  expect(result.surplus).toBe("3500.00");
});
```

简单测试不一定要保留三行注释。

但思路应该始终清楚：

```txt
准备了什么
执行了什么
期待什么
```

## 七、测试名称应该描述业务行为

推荐：

```ts
it("收入为 0 时储蓄率不可计算", ...)
```

不推荐：

```ts
it("测试 1", ...)
it("测试函数", ...)
it("应该工作", ...)
```

失败时，Vitest 会直接显示测试名称。

好的名称应该让你不打开代码也能大致知道：

```txt
哪条业务规则坏了
```

## 八、三类基础测试

每个核心函数至少考虑三类。

### 1. 正常值

最常见、最能代表业务用途的输入。

例如：

```txt
收入 10000
支出 5000
结余 5000
```

### 2. 边界值

刚好位于规则边缘的输入。

例如：

```txt
收入为 0
支出为 0
期限为 1
目标刚好达成
时间刚好跨月
最后一期刚好还清
```

### 3. 异常值

违反输入约束的值。

例如：

```txt
负流水金额
0 个月
重复债务 id
非法月份
无限数字
```

## 九、建立计算引擎测试矩阵

先把业务规则整理成表，而不是立刻写更多 `it()`。

| 模块 | 正常值 | 边界值 | 异常值 | 不变量或回归 |
| --- | --- | --- | --- | --- |
| Money | 加减乘除 | 半分舍入、负数 | NaN、Infinity、除零 | 不出现浮点误差 |
| 月结余 | 收入大于支出 | 相等、零支出、负结余 | 非金额输入由 Money 拦截 | 收入减支出等于结余 |
| 现金流 | 收入、固定和可变支出 | 空数组、零收入、跨月时区 | 负金额、非法方向和月份 | 转账不影响收支 |
| 储蓄目标 | 正常复利 | 零利率、刚好达标、1 个月 | 负金额、非法期限 | 所需月储蓄向上取分 |
| 债务策略 | 雪球和雪崩 | 零利率、最后一期、同值排序 | 空数组、重复 id、预算不足 | 总支付=本金+利息 |
| What-if | 增支和减支 | 负结余、0 月达标、不可达 | 负基准、非法期限 | 差异=场景-基准 |
| 计算历史 | 正常 JSON 快照 | 固定版本和固定时间 | 不可序列化数据不应进入 | output 不重复 steps |

这张表不是最终答案。

它用于发现：

```txt
哪些规则已经测试
哪些规则仍然缺失
```

## 十、不要把测试数量当成目标

下面两个测试价值不同：

```ts
expect(addMoney("1", "1").toString()).toBe("2");
expect(addMoney("2", "2").toString()).toBe("4");
```

它们覆盖的是几乎相同的规则。

而：

```ts
expect(addMoney("0.1", "0.2").toString())
  .toBe("0.3");
```

直接保护了项目采用 `decimal.js` 的核心原因。

因此：

```txt
更多测试
≠
更好的测试
```

应优先保护：

- 高风险公式。
- 已知边界。
- 业务分支。
- 财务不变量。
- 曾经发生的 bug。

## 十二、用 it.each 减少重复

多个结构相同的输入可以使用参数化测试：

```ts
it.each([
  ["10", "10.00"],
  ["59.7", "59.70"],
  ["1.004", "1.00"],
  ["1.005", "1.01"],
  ["-1.005", "-1.01"]
])(
  "把 %s 标准化为 %s",
  (input, expected) => {
    expect(toMoneyString(input)).toBe(expected);
  }
);
```

如果采用这段参数化测试，可以替换原来重复的格式化断言。

不要同时保留大量完全相同的重复用例。

## 十三、Money 的财务回归用例

这一条必须长期保留：

```ts
it("不会出现普通浮点加法误差", () => {
  const result = addMoney("0.1", "0.2");

  expect(result.toString()).toBe("0.3");
  expect(result.toString()).not.toBe(
    "0.30000000000000004"
  );
});
```

它是一条回归测试。

以后如果有人把 `Decimal` 改回普通 `number`，这条测试会立即失败。

## 十五、测试上海时区跨月

修改导入：

```ts

```

增加：

```ts
it("按照上海时区判断月份边界", () => {
  const beforeJuly = Date.UTC(
    2026,
    5,
    30,
    15,
    59,
    59,
    999
  );

  const julyInShanghai = Date.UTC(
    2026,
    5,
    30,
    16,
    0,
    0,
    0
```

```txt

```


## 二十三、不要对整个储蓄目标结果使用脆弱快照

第 26 课给结果增加了：

```txt
steps
```

如果测试写成：

```ts
expect(result).toEqual({
  // 所有字段和所有步骤
});
```

任何步骤文案调整都会让整个业务结果测试失败。

更合适的做法是分层断言：

```ts
expect(result.projectedAmount).toBe("402609.52");
expect(result.reached).toBe(false);
expect(result.gap).toBe("97390.48");

expect(result.steps.map((step) => step.id))
  .toEqual(expectedStepIds);
```

业务结果和追溯结构分别测试。

这能减少不必要的测试耦合。

```ts
  "%s 策略满足总支付等于本金加利息",
  (strategy) => {
    const result = simulateDebtPayoff({
      debts,
      extraPayment: "1500",
      strategy
    });

    expect(
      toMoneyString(
        addMoney(
          result.totalPrincipal,
          result.totalInterest
        )
      )
    ).toBe(result.totalPaid);
  }
);
```

这比只断言某个示例数字更通用。

它保护的是：

```txt
总支付 = 初始本金 + 总利息
```

```ts
it("没有参数变化时两个场景结果相同", () => {
```

## 三十五、为什么历史构造测试不连接数据库

测试导入的是：

```txt
lib/finance/calculation-history.ts
```

而不是：

```txt
lib/services/calculation-history.ts
```

原因是 service 会导入数据库客户端。

纯快照测试只需要验证：

```txt
相同输入和固定 id、时间
  ↓
得到相同 JSON 结构
```

数据库是否真的写入属于集成测试。

不要为了“更真实”让所有单元测试都依赖 SQLite。

## 三十六、什么是回归测试

回归测试用于防止已经解决的问题再次出现。

流程：

```txt
发现 bug
  ↓
先写一个会失败的测试复现
  ↓
修复代码
  ↓
测试变绿
  ↓
长期保留这个测试
```

本项目已有典型回归规则：

- `0.1 + 0.2` 必须得到 `0.3`。
- 收入为 `0` 时储蓄率是 `null`。
- 转账不计入收入和支出。
- 所需月储蓄额向上取到分。
- 最后一期债务不能多还。
- 目标不可达时月份是 `null`。
- `outputJson` 不重复保存 steps。

## 三十七、先写失败测试，再修 bug

假设发现上海时间：

```txt
2026-07-01 00:00
```

被错误归入六月。

不要先修改 `toShanghaiMonth()`。

先写：

```ts
expect(
  toShanghaiMonth(
    Date.UTC(2026, 5, 30, 16)
  )
).toBe("2026-07");
```

确认它在旧代码上失败。

再修改实现，直到测试通过。

这样才能证明：

```txt
测试真的捕获了这个 bug
```

如果先修代码再写测试，测试可能从未证明自己能发现问题。

## 三十八、测试与重构的关系

重构是：

```txt
调整代码结构
但不改变外部行为
```

例如：

- 提取测试数据工厂。
- 拆分长函数。
- 重命名内部变量。
- 提取未来价值公共函数。
- 减少重复校验。

安全节奏：

```txt
1. 原测试全部通过
2. 只做一个小重构
3. 再次运行相关测试
4. 再运行全部测试
5. 确认结果行为没有变化
```

## 三十九、测试通过不代表重构一定正确

测试只能保护已经覆盖的行为。

如果没有测试：

```txt
上海时区跨月
```

重构时间函数后，即使所有旧测试通过，也可能已经破坏跨月规则。

所以重构前应该先问：

> 这次要修改的规则，是否已有足够测试？

如果没有，先补测试。

## 四十、用测试数据工厂减少重复

`debt-payoff.test.ts` 中多次创建债务对象。

可以在测试文件顶部增加：

```ts
import type {
  DebtPayoffDebt
} from "../../lib/finance/debt-payoff";

function createDebt(
  overrides: Partial<DebtPayoffDebt> = {}
): DebtPayoffDebt {
  return {
    id: "debt",
    name: "测试债务",
    balance: "10000",
    annualRate: "10",
    minimumPayment: "500",
    ...overrides
  };
}
```

测试变为：

```ts
const debts = [
  createDebt({ id: "a" }),
  createDebt({
    id: "b",
    balance: "20000"
  })
];
```

工厂只负责减少无关重复。

不要把业务结论藏进复杂工厂。

## 四十一、测试之间必须相互独立

不要写：

```ts
let result;

it("先计算", () => {
  result = calculateSomething();
});

it("再检查上一个测试结果", () => {
  expect(result).toBe(...);
});
```

每个测试都应该自己准备输入。

原因是 Vitest 可能：

- 改变执行顺序。
- 只运行一个测试。
- 并行运行测试。

一个测试不应依赖另一个测试先成功。

## 四十二、不要依赖当前时间

测试中不要直接写：

```ts
occurredAt: Date.now()
```

今天运行可能属于七月，未来运行可能属于八月。

应该使用固定时间：

```ts
const julyTimestamp = Date.UTC(
  2026,
  6,
  15,
  4
);
```

固定时间让测试：

```txt
今天运行
明年运行
在另一台电脑运行
```

都得到相同结果。

## 四十三、不要在纯单元测试里 mock Decimal

不要写一个假的 `decimal.js`：

```ts
vi.mock("decimal.js", ...)
```

本项目选择 Decimal 正是为了测试真实金额行为。

如果把它 mock 成普通 `number`：

- 测不到真实精度。
- 测不到真实舍入。
- 测试结果没有业务价值。

应该直接使用实际依赖。

## 四十四、什么时候需要 mock

适合 mock 的通常是外部边界：

- 网络请求。
- 当前时间。
- UUID。
- 邮件或消息发送。
- 第三方 AI。

纯计算函数已经通过参数接收输入，通常不需要 mock。

例如历史构造函数把：

```txt
id
createdAt
```

作为参数传入，因此测试不需要 mock：

```ts
crypto.randomUUID()
Date.now()
```

## 四十五、不要测试第三方库内部实现

不需要证明：

```txt
Decimal.plus() 内部如何实现
Vitest 的 expect 是否正确
JSON.stringify 是否会遍历对象
```

应该测试项目对第三方库的业务约定：

```txt
Money 加法不会出现浮点误差
金额按 HALF_UP 保留两位
所需月储蓄按 CEIL 取分
```

## 五十、理解测试失败信息

常见失败：

```txt
Expected: "15942.49"
Received: "15942.48"
```

先判断它属于：

- 实现错误。
- 测试期望错误。
- 业务规则已经正式改变。

不要看到红色就立刻把期望值改成实际值。

如果直接把：

```ts
expect(...).toBe("15942.49")
```

改成：

```ts
expect(...).toBe("15942.48")
```

虽然测试变绿，但可能只是把 bug 合法化。

## 五十一、覆盖率是什么

覆盖率通常统计：

- 行覆盖率。
- 函数覆盖率。
- 分支覆盖率。
- 语句覆盖率。

它能帮助发现：

```txt
某个分支从未运行
```

但高覆盖率不等于结果正确。

例如一个测试只调用函数，却没有有效断言，也可能提高覆盖率。

本课不把覆盖率百分比作为验收标准。

如果以后安装与当前 Vitest 版本匹配的覆盖率插件，可以把覆盖率作为发现遗漏的辅助工具。

不要为了达到 100%：

- 测试无意义的类型声明。
- 断言框架内部行为。
- 写没有业务价值的脆弱测试。

## 五十二、哪些内容暂时不放进 finance 单元测试

本课不在 `tests/finance/` 中测试：

- React 样式类名。
- 导航文字颜色。
- SQLite 是否能创建文件。
- Next.js 是否能解析路由。
- DeepSeek 是否在线。
- 浏览器是否能点击按钮。

这些属于：

- 组件测试。
- API 集成测试。
- 端到端测试。
- 外部服务测试。

测试分层不是忽略它们，而是把它们放在正确位置。

## 五十八、复习问题

### 1. 为什么开始修改前要先建立绿色基线？

这样才能区分原有失败和本次修改造成的回归。

### 2. 正常值、边界值和异常值有什么区别？

正常值代表主要业务流程，边界值位于规则临界点，异常值违反输入约束。

### 3. 什么是财务不变量？

它是在合法计算中始终应该成立的关系，例如债务总支付等于初始本金加总利息。

### 4. 为什么测试不能依赖当前时间？

当前时间会变化，使同一个测试在不同日期得到不同结果。应使用固定时间戳。

### 5. 为什么不在 Money 测试中 mock Decimal？

项目需要验证的正是真实 Decimal 精度和舍入行为，mock 会让测试失去意义。

### 6. 什么是回归测试？

它把已经发现和修复的问题固定成测试，防止以后再次出现。

### 7. 为什么修 bug 前应该先写失败测试？

先看到测试失败，才能证明测试确实捕获了这个问题；修复后变绿则证明问题被处理。

### 8. 测试和重构是什么关系？

测试提供行为保护网，重构改变内部结构但应保持外部行为不变。重构前要确认相关行为已有覆盖。

### 9. 为什么不能盲目追求 100% 覆盖率？

覆盖率只说明代码被执行，不说明断言正确或业务风险已经覆盖。

### 10. 为什么纯历史测试不导入数据库 service？

service 导入数据库客户端，会让单元测试依赖外部状态。纯构造器应单独测试。

### 11. 为什么不要对包含 steps 的整个结果做巨大快照？

步骤文案或展示字段变化会让无关业务断言失败，增加测试耦合。结果和追溯结构应分层断言。

### 12. 为什么相同输入重复运行也值得测试？

它可以帮助发现输入被修改、读取当前时间或其他隐藏副作用。

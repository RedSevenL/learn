## 一、从数据闭环进入计算闭环

第 19 课的主角是账户 CRUD。

这一阶段的主角会变成财务计算。

以后完整的数据流大致是：

```txt
SQLite 中的账户、流水和负债
  ↓
service 读取并整理数据
  ↓
财务计算函数
  ↓
返回明确的计算结果
  ↓
API 或页面展示结果
```

例如，后续计算月度现金流时：

```txt
transactions 表
  ↓
读取某个月的流水
  ↓
区分 income 和 expense
  ↓
汇总月收入和月支出
  ↓
计算月结余和储蓄率
```

这里要特别区分两件事：

### 1. 读取数据

读取数据会接触数据库：

```ts
const transactions = await db
  .select()
  .from(transactionTable);
```

这段代码依赖：

- SQLite 中当前保存了什么。
- 数据库连接是否正常。
- 查询是否成功。

### 2. 计算数据

计算函数只接收已经准备好的值：

```ts
const surplus = calculateMonthlySurplus({
  income: 10000,
  expense: 6500
});
```

它不需要知道：

- 数据来自 SQLite 还是测试用例。
- 当前运行在 API 还是脚本中。
- 页面是否打开。
- 网络是否正常。

一句话：

> service 负责取得数据，计算引擎负责计算数据。

这就是阶段四首先要建立的边界。

## 二、什么是纯函数

纯函数可以先理解成：

> 相同的输入，永远得到相同的输出，并且不会偷偷修改函数外部的状态。

例如：

```ts
function add(a: number, b: number) {
  return a + b;
}
```

只要输入一直是：

```ts
add(2, 3)
```

结果就一直是：

```txt
5
```

这个函数不会：

- 修改数据库。
- 请求网络。
- 改变页面状态。
- 修改传入的对象。
- 依赖当前时间。
- 生成随机数。

所以它是一个纯函数。

## 三、纯函数的两个判断条件

判断一个函数是不是纯函数，可以检查两个条件。

### 1. 相同输入得到相同输出

下面的函数是纯函数：

```ts
function calculateSurplus(income: number, expense: number) {
  return income - expense;
}
```

调用：

```ts
calculateSurplus(10000, 6500);
```

无论调用多少次，结果都是：

```txt
3500
```

下面的函数不是纯函数：

```ts
function createCalculationId() {
  return crypto.randomUUID();
}
```

它没有输入，但每次输出都不同。

下面的函数也不是纯函数：

```ts
function getCurrentYear() {
  return new Date().getFullYear();
}
```

它的结果依赖调用时的当前时间。

### 2. 不产生副作用

副作用是指：

> 函数除了返回结果，还修改了函数外部可观察到的状态。

常见副作用包括：

- 写入数据库。
- 修改文件。
- 发送网络请求。
- 修改 React state。
- 修改外部变量。
- 修改传入的对象或数组。
- 读取当前时间或随机值。

例如：

```ts
let total = 0;

function addToTotal(amount: number) {
  total += amount;
  return total;
}
```

`addToTotal` 修改了函数外部的 `total`。

因此它不是纯函数。

再看一个数组例子：

```ts
function addExpense(expenses: number[], amount: number) {
  expenses.push(amount);
  return expenses;
}
```

`push()` 会修改传入的原数组。

这也是副作用。

如果确实需要返回新数组，可以写成：

```ts
function addExpense(expenses: number[], amount: number) {
  return [...expenses, amount];
}
```

这次没有修改原数组，而是返回了一个新数组。

## 四、输入、输出和副作用

可以用三个问题检查一个函数：

```txt
输入从哪里来？
输出是什么？
函数还改变了什么？
```

以月结余函数为例：

```ts
function calculateMonthlySurplus(income: number, expense: number) {
  return income - expense;
}
```

它的结构是：

| 项目 | 内容 |
| --- | --- |
| 输入 | `income`、`expense` |
| 输出 | 月结余数字 |
| 副作用 | 无 |

再看数据库写入函数：

```ts
async function saveAccount(account: Account) {
  await db.insert(accounts).values(account);
}
```

它的结构是：

| 项目 | 内容 |
| --- | --- |
| 输入 | `account` |
| 输出 | Promise 完成状态 |
| 副作用 | 修改 SQLite 中的数据 |

`saveAccount` 不是纯函数。

但这不代表它是坏代码。

项目不可能完全没有副作用：

- 数据必须保存到数据库。
- 页面必须请求 API。
- React 必须更新状态。
- 计算历史必须写入表中。

真正的目标不是“所有函数都写成纯函数”，而是：

> 把不可避免的副作用放在边缘，把核心财务计算保持为纯函数。

## 五、为什么财务计算适合写成纯函数

财务计算关系到用户对结果的信任。

假设用户问：

```txt
我这个月收入 10000 元，支出 6500 元，还剩多少？
```

计算结果应该只由输入决定：

```txt
10000 - 6500 = 3500
```

不应该因为下面这些事情而改变：

- 数据库中还有其他账户。
- 当前是上午还是晚上。
- API 被调用了几次。
- 页面有没有刷新。
- AI 给出了什么回答。

纯函数有几个重要优点。

### 1. 结果容易验证

输入和输出都是明确的：

```txt
输入：收入 10000，支出 6500
输出：结余 3500
```

可以直接人工复算。

### 2. 容易编写测试

测试不需要启动浏览器或数据库：

```ts
expect(
  calculateMonthlySurplus({
    income: 10000,
    expense: 6500
  })
).toEqual({
  income: 10000,
  expense: 6500,
  surplus: 3500
});
```

### 3. 容易复用

同一个函数可以在多个位置使用：

```txt
API
命令行脚本
仪表盘
场景模拟
测试
```

### 4. 容易定位错误

如果输入正确但输出错误，问题就在计算函数内部。

不用同时怀疑：

- 数据库连接。
- HTTP 请求。
- React 状态。
- 页面渲染。

### 5. 容易追溯

后续保存计算历史时，可以清楚记录：

```txt
输入是什么
使用了什么公式
输出是什么
```

这会为第 26 课的“计算过程可追溯”打下基础。

## 六、财务计算的边界在哪里

阶段三已经有：

```txt
lib/services/
```

阶段四新增：

```txt
lib/finance/
```

这两个目录职责不同。

| 目录 | 负责什么 | 是否允许接触数据库 |
| --- | --- | --- |
| `lib/services/` | 查询、创建、修改业务数据 | 允许 |
| `lib/finance/` | 根据明确输入执行确定性计算 | 不允许 |

推荐的调用方向是：

```txt
API 或页面
  ↓
service 读取数据
  ↓
整理成计算函数需要的输入
  ↓
lib/finance 中的纯函数
  ↓
得到计算结果
```

不推荐：

```txt
calculateMonthlySurplus()
  ↓
函数内部查询数据库
  ↓
函数内部读取当前月份
  ↓
函数内部写入计算历史
```

因为这样会把“读取”“计算”“保存”混在一起。

一个清楚的计算函数应该像这样：

```ts
calculateMonthlySurplus({
  income: 10000,
  expense: 6500
});
```

而不是：

```ts
calculateMonthlySurplusFromDatabase();
```

前者的输入一眼就能看清。

后者必须打开函数内部，才知道它：

- 查询了哪张表。
- 查询了哪个月份。
- 是否排除了软删除数据。
- 是否修改了其他内容。

## 八、设计月结余函数的输入和输出

月结余公式是：

```txt
月结余 = 月收入 - 月支出
```

先设计输入：

```ts
export type MonthlySurplusInput = {
  income: number;
  expense: number;
};
```

再设计输出：

```ts
export type MonthlySurplusResult = {
  income: number;
  expense: number;
  surplus: number;
};
```

为什么不只返回一个数字？

只返回：

```ts
3500
```

调用方无法仅凭结果知道：

- 使用了多少收入。
- 使用了多少支出。
- 结果对应什么输入。

返回完整对象：

```ts
{
  income: 10000,
  expense: 6500,
  surplus: 3500
}
```

更容易：

- 展示。
- 调试。
- 测试。
- 保存计算历史。
- 查看计算依据。

这是本项目“计算结果可追溯”的第一步。

## 九、编写第一个计算函数

新建：

```txt
lib/finance/monthly-surplus.ts
```

先写：

```ts
export type MonthlySurplusInput = {
  income: number;
  expense: number;
};

export type MonthlySurplusResult = {
  income: number;
  expense: number;
  surplus: number;
};

export function calculateMonthlySurplus(
  input: MonthlySurplusInput
): MonthlySurplusResult {
  return {
    income: input.income,
    expense: input.expense,
    surplus: input.income - input.expense
  };
}
```

这个函数没有：

- `async`。
- `fetch()`。
- `db.select()`。
- `db.insert()`。
- `Date.now()`。
- `crypto.randomUUID()`。
- React state。
- 环境变量。

它只根据输入得到输出。

所以它是纯函数。

## 十一、什么是单元测试

单元测试是：

> 用代码自动检查一个小功能是否得到预期结果。

这里的“单元”就是：

```txt
calculateMonthlySurplus()
```

人工测试通常是：

1. 启动项目。
2. 打开页面。
3. 输入收入和支出。
4. 点击按钮。
5. 查看结果。

单元测试可以直接写：

```ts
expect(calculateMonthlySurplus(...)).toEqual(...);
```

它不需要：

- 启动浏览器。
- 点击页面。
- 连接 SQLite。
- 手动反复输入数据。

单元测试不会替代所有人工测试。

它主要帮助我们快速确认：

```txt
给定输入后，计算函数是否返回正确输出
```

## 十二、为什么财务计算需要测试

一个减法函数看起来很简单。

但后面的计算会越来越复杂：

- 汇总多条收入和支出。
- 计算储蓄率。
- 计算复利。
- 推算目标是否达成。
- 模拟债务雪球法和雪崩法。
- 比较 What-if 场景。

任何一个公式或判断写错，都可能让用户做出错误决定。

测试至少能帮助我们：

### 1. 防止公式写错

例如不小心写成：

```ts
surplus: input.income + input.expense
```

测试会立即失败。

### 2. 防止修改旧代码时破坏旧结果

以后把 `number` 改成 `Decimal` 时，测试可以确认：

```txt
输入意义没有变化
输出结果仍然正确
```

### 3. 保存业务规则

测试本身也是一种规则说明：

```ts
it("支出高于收入时返回负结余", () => {
  // ...
});
```

看到测试名称，就知道项目如何定义“超支”。

### 4. 检查边界情况

正常输入之外，还需要考虑：

- 收入和支出相等。
- 没有支出。
- 支出高于收入。
- 输入为负数。
- 输入不是有限数字。

## 十五、编写第一个测试

新建：

```txt
tests/finance/monthly-surplus.test.ts
```

写入：

```ts
import { describe, expect, it } from "vitest";
import {
  calculateMonthlySurplus
} from "../../lib/finance/monthly-surplus";

describe("calculateMonthlySurplus", () => {
  it("用月收入减去月支出得到月结余", () => {
    const result = calculateMonthlySurplus({
      income: 10000,
      expense: 6500
    });

    expect(result).toEqual({
      income: 10000,
      expense: 6500,
      surplus: 3500
    });
  });
});
```

这段测试可以分成三部分。

### 1. Arrange：准备输入

```ts
const input = {
  income: 10000,
  expense: 6500
};
```

### 2. Act：执行函数

```ts
const result = calculateMonthlySurplus(input);
```

### 3. Assert：检查结果

```ts
expect(result).toEqual({
  income: 10000,
  expense: 6500,
  surplus: 3500
});
```

这种结构经常简称：

```txt
AAA
Arrange
Act
Assert
```

当前代码把准备输入直接写在函数调用里，也完全可以。

重要的是你能区分：

```txt
准备什么
执行什么
期待什么
```

## 十六、认识 describe、it、expect

测试文件里第一次出现了三个新函数。

### 1. describe

```ts
describe("calculateMonthlySurplus", () => {
  // 多个相关测试
});
```

`describe` 用来组织一组相关测试。

这里表示：

```txt
下面都在测试 calculateMonthlySurplus
```

### 2. it

```ts
it("用月收入减去月支出得到月结余", () => {
  // 一个具体测试
});
```

`it` 表示一个具体行为。

测试名称应该说明：

```txt
什么条件下，应该发生什么
```

避免只写：

```ts
it("测试 1", () => {});
```

这种名称无法解释业务规则。

### 3. expect

```ts
expect(result).toEqual(expectedResult);
```

`expect` 用来声明预期结果。

`toEqual` 会比较对象中的字段和值。

如果实际结果和预期结果不同，测试就会失败。

## 十八、亲眼观察一次失败测试

只看绿色的通过结果，还不容易理解测试的作用。

可以临时把预期结果改错：

```ts
expect(result).toEqual({
  income: 10000,
  expense: 6500,
  surplus: 9999
});
```

重新运行测试。

这时应该看到失败信息，指出：

```txt
Expected: 9999
Received: 3500
```

这说明测试不是“运行函数看看有没有报错”。

它会真正比较：

```txt
实际结果
预期结果
```

观察失败信息后，把预期值改回：

```ts
surplus: 3500
```

再次运行，确认测试恢复通过。

> 故意制造失败只是学习动作。完成本课时，测试必须恢复为通过状态。

## 十九、补充月结余的边界测试

一个正常用例不能说明所有情况都正确。

继续在同一个 `describe` 中增加测试。

### 1. 收入和支出相等

```ts
it("收入和支出相等时结余为 0", () => {
  const result = calculateMonthlySurplus({
    income: 5000,
    expense: 5000
  });

  expect(result.surplus).toBe(0);
});
```

### 2. 没有支出

```ts
it("没有支出时结余等于收入", () => {
  const result = calculateMonthlySurplus({
    income: 8000,
    expense: 0
  });

  expect(result.surplus).toBe(8000);
});
```

### 3. 支出高于收入

```ts
it("支出高于收入时返回负结余", () => {
  const result = calculateMonthlySurplus({
    income: 3000,
    expense: 4500
  });

  expect(result.surplus).toBe(-1500);
});
```

这里要明确业务含义：

```txt
正数：有结余
0：收支平衡
负数：发生超支
```

不要为了让结果“看起来好看”而把负数强行改成 `0`。

负结余是有意义的财务结果。

## 二十、边界情况和异常输入不是一回事

下面这些是合法的边界情况：

| 输入 | 业务含义 |
| --- | --- |
| `income: 0` | 当月没有收入 |
| `expense: 0` | 当月没有支出 |
| `income === expense` | 收支平衡 |
| `expense > income` | 当月超支 |

下面这些更可能是异常输入：

| 输入 | 问题 |
| --- | --- |
| `income: -1000` | “收入”是否应该允许负数不明确 |
| `expense: -500` | 可能把退款和支出概念混在一起 |
| `income: NaN` | 无法进行可信计算 |
| `expense: Infinity` | 不是有限金额 |

边界情况通常需要返回一个合法结果。

异常输入通常需要：

- 在进入计算函数前被 Zod 拦截。
- 或由计算函数明确拒绝。

目前项目的 `createTransactionSchema` 已经负责校验 API 请求。

但计算函数将来可能被：

- API 调用。
- 测试调用。
- 脚本调用。
- 场景模拟调用。

所以后续还需要决定：

```txt
哪些规则属于输入格式校验
哪些规则属于财务业务规则
```

本课先不扩展异常处理代码。

先把以下合法规则固定下来：

```txt
收入和支出可以为 0
支出高于收入时允许得到负结余
相同输入必须得到相同输出
```

## 二十一、Zod 校验和计算函数不是一回事

第 17 课已经学习了 Zod。

Zod 负责确认输入结构是否合法，例如：

```txt
amount 是不是金额字符串
direction 是不是允许的枚举值
accountId 是不是空字符串
```

计算函数负责业务计算，例如：

```txt
收入减支出得到多少
储蓄率是多少
目标能否按时达成
```

它们的关系是：

```txt
外部数据
  ↓
Zod 检查格式
  ↓
整理成计算输入
  ↓
纯函数执行计算
```

不要把所有公式都写进 Zod 的 `refine()`。

也不要因为 API 已经有 Zod，就认为计算函数不需要测试。

Zod 只能说明：

```txt
输入长得对不对
```

单元测试要说明：

```txt
公式算得对不对
```

## 二十二、纯函数不应该直接读取数据库

下面这种写法把数据库和计算混在了一起：

```ts
export async function calculateMonthlySurplus() {
  const rows = await db.select().from(transactions);

  // 在这里筛选、汇总并计算
}
```

它会带来几个问题：

- 测试必须准备数据库。
- 数据库内容变化会影响结果。
- 函数名称看不出计算的是哪个月份。
- 计算规则和查询规则混在一起。
- 很难单独测试公式。

更清楚的拆分是：

```ts
const transactions = await listTransactions();
const input = buildMonthlySurplusInput(transactions);
const result = calculateMonthlySurplus(input);
```

这里可以分成三层：

| 步骤 | 职责 |
| --- | --- |
| `listTransactions()` | 从数据库读取流水 |
| `buildMonthlySurplusInput()` | 把流水整理成计算输入 |
| `calculateMonthlySurplus()` | 执行确定性计算 |

本课只实现第三步。

第 22 课学习现金流计算时，再处理流水汇总。

## 二十三、纯函数也不应该读取当前时间

财务计算经常需要“当前日期”。

例如：

```txt
计算本月流水
距离目标日期还有几个月
计算贷款剩余期限
```

下面的函数内部读取当前时间：

```ts
function calculateRemainingMonths(targetDate: Date) {
  const now = new Date();
  // ...
}
```

不同日期运行，结果会变化。

它不是严格的纯函数。

可以改成把当前时间作为输入：

```ts
function calculateRemainingMonths(
  currentDate: Date,
  targetDate: Date
) {
  // ...
}
```

测试时就可以明确写：

```txt
当前日期：2026-07-24
目标日期：2028-07-24
```

核心原则是：

> 凡是会影响结果的信息，都尽量通过参数明确传入。

本课的月结余函数暂时不需要日期。

但这个原则会在后面的储蓄目标计算中继续使用。

## 二十四、测试是否修改了输入

纯函数不应该修改传入对象。

当前月结余函数只读取：

```ts
input.income
input.expense
```

没有修改 `input`。

可以增加一个测试：

```ts
it("不会修改传入的对象", () => {
  const input = {
    income: 10000,
    expense: 6500
  };

  calculateMonthlySurplus(input);

  expect(input).toEqual({
    income: 10000,
    expense: 6500
  });
});
```

这个测试在当前函数中很容易通过。

但以后计算输入包含数组时，它会更有意义。

例如不要写：

```ts
transactions.sort(...);
```

因为 `sort()` 会修改原数组。

可以写：

```ts
[...transactions].sort(...);
```

先复制数组，再排序。

## 二十五、测试驱动的基本节奏

常见的开发节奏是：

```txt
先写一个会失败的测试
  ↓
写最少的代码让它通过
  ↓
整理代码但保持测试通过
```

这个过程常被称为：

```txt
Red → Green → Refactor
```

### Red：红

先写测试，但函数还不存在或结果不正确。

测试失败。

### Green：绿

实现最少的正确代码。

测试通过。

### Refactor：重构

在不改变行为的情况下整理：

- 命名。
- 重复代码。
- 类型。
- 文件结构。

然后再次运行测试。

如果仍然通过，说明重构没有破坏已有规则。

本课程不要求每一行代码都必须先写测试。

但计算引擎中的关键公式应该逐步形成这个习惯。

## 二十七、常见问题

### 1. 运行 npm test 提示 Missing script: test

检查 `package.json` 的 `scripts` 中是否有：

```json
"test": "vitest"
```

同时检查上一行末尾是否有逗号。

### 2. 提示找不到 vitest

确认在：

```txt
ai-finance-cfo/
```

目录执行过：

```bash
npm install -D vitest
```

并确认 `package.json` 的 `devDependencies` 中出现 `vitest`。

### 3. 测试文件没有被发现

测试文件名应包含：

```txt
.test.
```

例如：

```txt
monthly-surplus.test.ts
```

不要写成：

```txt
monthly-surplus.ts
```

### 4. 测试文件无法导入计算函数

当前测试文件路径是：

```txt
tests/finance/monthly-surplus.test.ts
```

源码路径是：

```txt
lib/finance/monthly-surplus.ts
```

因此相对导入路径是：

```ts
import {
  calculateMonthlySurplus
} from "../../lib/finance/monthly-surplus";
```

两个 `..` 分别从：

```txt
finance/ → tests/ → 项目根目录
```

然后进入：

```txt
lib/finance/
```

### 5. 测试一直不退出

`npm test` 会进入监听模式，这是正常行为。

按：

```txt
q
```

退出。

如果只想运行一次：

```bash
npm run test:run
```

### 6. 为什么不直接测试数据库里的真实流水

因为本课测试的是月结余公式，不是数据库连接。

如果测试依赖真实数据库：

- 数据变化会让测试结果变化。
- 测试前必须准备记录。
- 测试后可能要清理记录。
- 很难判断失败来自公式还是数据库。

纯函数测试直接传入固定值，更快、更稳定。

### 7. 负结余是不是应该报错

不是。

支出高于收入是正常存在的财务状态。

它应该返回：

```txt
负结余
```

而不是抛出错误。

真正需要拒绝的是 `NaN`、`Infinity` 或业务上不允许的输入。

异常输入规则会随着 Money 类型和现金流模型继续完善。

## 三十、复习问题

### 1. 什么是纯函数？

纯函数在相同输入下总是得到相同输出，并且不会修改函数外部的状态。它不应该偷偷读取数据库、当前时间或随机数，也不应该修改传入的对象和数组。

### 2. 为什么财务计算要尽量写成纯函数？

因为财务结果需要稳定、可验证、可测试和可追溯。纯函数让结果只由明确输入决定，出现问题时可以单独检查公式，不需要同时排查数据库、网络和页面状态。

### 3. service 和 `lib/finance/` 有什么区别？

service 可以读取和修改数据库，负责取得业务数据；`lib/finance/` 接收已经整理好的输入并执行确定性计算。前者位于副作用边缘，后者保持为纯计算核心。

### 4. Zod 校验通过，为什么还需要单元测试？

Zod 只能确认输入结构和格式符合要求，不能证明公式正确。即使 `income` 和 `expense` 都是合法数字，代码仍可能误写成相加。单元测试负责验证计算行为和预期结果。

### 5. 为什么测试不直接读取真实 SQLite 数据？

本课只测试公式。使用固定输入可以让测试快速、稳定、可重复。如果测试依赖数据库，失败时无法立即判断是查询问题、数据问题还是公式问题。

### 6. 支出高于收入属于异常输入吗？

不属于。它表示当月超支，合法结果是负结余。边界情况仍然是业务允许的情况，而 `NaN`、`Infinity` 等才属于无法可信计算的异常输入。

### 7. 为什么函数返回完整对象，而不是只返回 surplus？

完整对象保留了收入、支出和结余之间的关系，更容易展示、调试、测试和保存计算历史，也为后续可追溯计算打下基础。

### 8. 为什么本课暂时使用 number？

本课的目标是理解纯函数和测试，所以先用整数金额降低学习负担。JavaScript 浮点误差和正式的金额类型会在第 21 课单独处理，本课版本不是最终金额方案。

### 9. `npm test` 和 `npm run test:run` 有什么区别？

`npm test` 进入监听模式，文件变化后自动重跑，适合开发过程；`npm run test:run` 只运行一次并退出，适合课程验收和提交代码前检查。

### 10. 什么信息应该成为计算函数的参数？

凡是会影响计算结果的信息，都应该尽量明确传入。例如收入、支出、当前日期、目标日期和利率。这样相同输入才能得到相同输出，测试也能稳定复现结果。

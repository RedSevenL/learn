# 从零复刻前端项目结构的方法

## 这份笔记解决什么问题

当前项目已经形成了一个基础前端结构：

```txt
app/          页面和路由
components/   可复用 UI 组件
types/        业务数据类型
lib/          假数据、工具函数、后续服务逻辑
```

如果之后要自己从 0 写出类似项目，不应该一上来就直接写组件。

更稳的顺序是：

```txt
先想清楚产品结构
  ↓
再设计页面和数据
  ↓
再定义类型
  ↓
再写假数据
  ↓
再写页面骨架
  ↓
再拆组件
  ↓
最后整理状态流和校验
```

写代码只是中间一步。真正重要的是先把“页面、数据、状态、组件职责”想清楚。

## 一、先想清楚产品有哪些页面

当前项目是 AI 个人财务 CFO，所以先按功能拆页面：

| 页面 | 路径 | 职责 |
| --- | --- | --- |
| 首页 | `/` | 展示项目入口和功能模块 |
| 对话页 | `/chat` | 后续承载 AI 财务问答 |
| 仪表盘 | `/dashboard` | 当前管理账户，后续展示财务摘要 |
| 场景模拟 | `/scenarios` | 后续模拟未来财务选择 |
| CSV 导入 | `/import` | 后续导入账单流水 |

这里先不要想数据库，也不要想 AI。

先回答：

- 用户进入项目后看到什么？
- 有哪些核心模块？
- 每个模块应该有独立页面，还是只是某个页面里的小组件？
- 哪个页面最先做成可交互版本？

当前项目选择先让 `/dashboard` 有真实交互，因为账户管理是后续财务数据的基础。

## 二、再设计目录职责

目录不是随便建的。每个目录都应该有清楚职责。

```txt
app/
```

放页面和路由。凡是浏览器可以访问的页面，都从这里开始。

```txt
components/
```

放可复用或从页面里拆出来的 UI 组件。

```txt
types/
```

放业务数据类型，例如账户、流水、负债。

```txt
lib/
```

放页面之外的共享数据和逻辑。当前阶段是 `mock-data.ts`，后续可以放 API helper、数据库查询、财务计算函数。

可以用一句话判断文件该放哪里：

```txt
能被 URL 访问的是 app
页面局部 UI 拆出来是 components
描述业务数据形状的是 types
被多个地方复用的数据或逻辑是 lib
```

## 三、写代码前要先梳理数据模型

比如账户管理，不要先写表单。

先问：

```txt
一个账户需要哪些字段？
```

当前项目得到：

```ts
export type AccountType = "cash" | "bank" | "credit" | "investment";

export type Account = {
  id: string;
  name: string;
  type: AccountType;
  balance: number;
};
```

这个类型放在：

```txt
types/finance.ts
```

原因是 `Account` 不是某个组件自己的东西，而是整个财务业务都会用到的数据结构。

后续新增流水时，也应该先设计类似类型：

```ts
export type Transaction = {
  id: string;
  title: string;
  amount: number;
  category: string;
  date: string;
};
```

## 四、再准备假数据

在没有 API 和数据库前，需要用假数据撑起页面。

当前项目把假数据放到：

```txt
lib/mock-data.ts
```

例如：

```ts
export const initialAccounts: Account[] = [
  {
    id: "account_001",
    name: "工资卡",
    type: "bank",
    balance: 20000
  }
];
```

这样做有三个好处：

- 页面文件不会堆满假数据。
- 多个页面或 API 可以复用同一份数据。
- 后续替换成 API 或数据库时，迁移路径更清楚。

写假数据时要注意：

- 字段必须和 `types/finance.ts` 里的类型一致。
- id 要稳定，方便作为 React 的 `key`。
- 数据不要太多，能表达页面状态就够。
- 最好包含正常值和边界值，例如信用卡余额可以是负数。

## 五、先写页面骨架，再写交互

页面骨架先解决布局问题。

每个页面可以先按统一结构写：

```txt
main
  ↓
页面容器
  ↓
header 标题区
  ↓
section 内容区
```

例如：

```tsx
<main className="min-h-screen bg-gray-50 px-6 py-8">
  <div className="mx-auto max-w-5xl">
    <header className="mb-8">
      <p>模块名</p>
      <h1>页面标题</h1>
      <p>页面说明</p>
    </header>

    <section>页面内容</section>
  </div>
</main>
```

这个阶段优先保证：

- 页面路径能打开。
- 导航能跳转。
- 页面标题清楚。
- 内容区能表达未来功能方向。

不要一开始就拆很多组件。

## 六、什么时候拆组件

初学阶段不要为了拆而拆。

当页面里出现下面情况时再拆：

- 一段 UI 有清楚独立职责。
- 这段 UI 代码太长，影响阅读页面主流程。
- 这段 UI 未来可能复用。
- 这段 UI 只需要通过 props 接收数据。

当前项目拆出的组件是：

```txt
components/accounts/
  AccountForm.tsx
  AccountList.tsx
  AccountCard.tsx
  EmptyAccounts.tsx
  ErrorMessage.tsx
```

它们的职责分别是：

| 组件 | 职责 |
| --- | --- |
| `AccountForm` | 显示新增账户表单 |
| `AccountList` | 判断账户是否为空，并渲染列表 |
| `AccountCard` | 显示单个账户 |
| `EmptyAccounts` | 显示空状态 |
| `ErrorMessage` | 显示错误信息 |

拆组件时要保留一个原则：

```txt
页面负责状态和动作
组件负责展示和触发回调
```

## 七、如何设计状态

状态不是看到输入框就随便写。

先区分三类数据：

### 1. 业务数据

例如账户列表：

```ts
const [accounts, setAccounts] = useState<Account[]>(initialAccounts);
```

它代表当前页面真正管理的数据。

### 2. 表单输入状态

例如：

```ts
const [name, setName] = useState("");
const [type, setType] = useState<Account["type"]>("bank");
const [balance, setBalance] = useState("");
```

它们只是用户正在输入的临时值。

注意 `balance` 虽然最终是数字，但表单里先用字符串保存，因为输入框天然拿到的是字符串。

### 3. UI 状态

例如：

```ts
const [error, setError] = useState("");
```

后续还会有：

```ts
const [isLoading, setIsLoading] = useState(false);
const [isSubmitting, setIsSubmitting] = useState(false);
```

设计状态时可以问：

- 这个数据会不会变化？
- 变化后是否需要页面重新渲染？
- 是业务数据、表单输入，还是 UI 状态？
- 它应该由哪个页面或组件拥有？

当前项目的答案是：

```txt
accounts、name、type、balance、error 都由 DashboardPage 拥有
```

因为新增账户会影响账户列表，账户列表和表单需要共享同一个父页面状态。

## 八、如何设计组件接口

组件接口就是 props。

以 `AccountForm` 为例，它需要两类 props：

### 1. 当前值

```ts
name: string;
type: Account["type"];
balance: string;
error: string;
```

这些决定表单显示什么。

### 2. 回调函数

```ts
onNameChange: (value: string) => void;
onTypeChange: (value: Account["type"]) => void;
onBalanceChange: (value: string) => void;
onSubmit: (event: React.FormEvent<HTMLFormElement>) => void;
```

这些让表单把用户动作通知父组件。

设计组件 props 时可以用这个模板：

```txt
这个组件要显示哪些数据？
  ↓
这些数据作为值 props 传入

这个组件会触发哪些动作？
  ↓
这些动作作为 onXxx 回调传入
```

命名习惯：

- 值用名词：`name`、`type`、`accounts`
- 动作用 `on` 开头：`onSubmit`、`onNameChange`
- 父组件里的更新函数通常是 `setXxx`

所以：

```tsx
<AccountForm
  name={name}
  onNameChange={setName}
/>
```

可以读成：

```txt
AccountForm 显示 name
当 name 变化时，调用 setName
```

## 九、当前项目的数据流

当前 dashboard 的数据流是：

```txt
lib/mock-data.ts
  ↓ initialAccounts
DashboardPage
  ↓ useState 保存 accounts
  ↓ 把表单值和回调传给 AccountForm
  ↓ 把 accounts 传给 AccountList
AccountList
  ↓ map accounts
AccountCard
  ↓ 显示单个 account
```

新增账户时：

```txt
用户输入
  ↓
AccountForm 调用 onNameChange / onTypeChange / onBalanceChange
  ↓
DashboardPage 更新表单状态
  ↓
用户提交表单
  ↓
AccountForm 调用 onSubmit
  ↓
DashboardPage 执行 handleSubmit
  ↓
校验输入
  ↓
创建 newAccount
  ↓
setAccounts([...accounts, newAccount])
  ↓
AccountList 重新渲染
```

这个流程可以复用到很多功能。

例如新增流水：

```txt
transactions
TransactionForm
TransactionList
TransactionCard
handleSubmit
```

新增负债：

```txt
liabilities
LiabilityForm
LiabilityList
LiabilityCard
handleSubmit
```

## 十、可以复用的编写流程

以后写一个新模块，可以照这个流程走。

### 第一步：写一句模块目标

例如：

```txt
我要做一个流水管理模块，用户可以查看流水列表，并新增一条流水。
```

### 第二步：定义业务类型

放到：

```txt
types/finance.ts
```

例如：

```ts
export type Transaction = {
  id: string;
  title: string;
  amount: number;
  category: string;
  date: string;
};
```

### 第三步：准备假数据

放到：

```txt
lib/mock-data.ts
```

例如：

```ts
export const initialTransactions: Transaction[] = [];
```

### 第四步：先在页面里写完整功能

先不要急着拆组件。

让页面里先跑通：

```txt
useState
表单输入
handleSubmit
列表渲染
错误提示
```

### 第五步：按职责拆组件

拆成：

```txt
TransactionForm
TransactionList
TransactionCard
EmptyTransactions
ErrorMessage
```

如果已有 `ErrorMessage` 可以复用，就不要重复写。

### 第六步：检查数据流

确认：

```txt
页面是否持有状态？
子组件是否只通过 props 接收数据？
子组件是否通过 onXxx 回调通知父组件？
列表是否使用稳定 id 作为 key？
错误状态是否能显示？
空状态是否能显示？
```

## 十一、写代码之外必须先想清楚什么

写代码之前，至少要能回答这些问题。

### 1. 页面问题

- 这个功能属于哪个页面？
- 是否需要新路由？
- 是否需要加入顶部导航？
- 这个页面的标题和说明是什么？

### 2. 数据问题

- 这个功能操作的核心数据是什么？
- 每条数据有哪些字段？
- 字段类型是什么？
- 哪些字段是用户输入的？
- 哪些字段是系统生成的？

### 3. 状态问题

- 哪些数据会变？
- 哪些只是展示用？
- 哪些是表单临时输入？
- 哪些是错误、空状态、loading？
- 状态应该放在页面，还是组件内部？

### 4. 组件问题

- 哪些 UI 可以留在页面？
- 哪些 UI 应该拆成组件？
- 每个组件只负责一件什么事？
- 组件需要哪些值 props？
- 组件需要哪些回调 props？

### 5. 后续扩展问题

- 现在的数据以后会不会来自 API？
- 当前假数据以后会不会替换成数据库？
- 当前表单提交以后会不会改成 POST？
- 类型以后是否会和 Zod、数据库 schema 对应？

这些问题想清楚后，写代码会更顺。

## 十二、和 Codex 协作时如何描述需求

不要只说：

```txt
帮我做一个流水页面
```

更好的描述是：

```txt
请在当前教学项目里新增一个流水管理页面。
要求：
- 路径是 /transactions。
- 先使用前端假数据，不接 API。
- 在 types/finance.ts 里定义 Transaction 类型。
- 在 lib/mock-data.ts 里新增 initialTransactions。
- 页面先持有状态，支持新增流水。
- 表单、列表、卡片拆到 components/transactions/。
- 不要直接引入数据库或接口。
- 保持和 dashboard 账户模块相同的数据流风格。
```

这样 Codex 会更容易生成和当前项目一致的代码。

## 十三、让 Codex 修改前先做的检查

可以要求 Codex 先检查：

```txt
请先阅读 app/dashboard/page.tsx、components/accounts/、types/finance.ts、lib/mock-data.ts，
总结当前账户模块的数据流。
然后再按同样模式新增流水模块。
```

这样能避免它凭空发明结构。

如果是课程项目，还要加一句：

```txt
这是教学项目。除非我明确要求直接改源码，否则优先整理课程说明，不要替我写练习答案。
```

如果你确实要它写源码，再明确说：

```txt
这次请直接修改项目代码。
```

## 十四、让 Codex 写完后如何检查

可以要求它按下面清单自查：

```txt
请检查：
1. 是否新增或修改了正确路径下的文件。
2. 是否遗漏 import。
3. 类型是否集中放在 types/finance.ts。
4. 假数据是否集中放在 lib/mock-data.ts。
5. 页面是否负责状态和提交逻辑。
6. 组件是否只负责展示和调用回调。
7. 空状态和错误状态是否可见。
8. 是否能通过 npm run lint 或 npm run build。
9. 是否和现有 dashboard 模块风格一致。
```

如果出现问题，可以继续追问：

```txt
请只解释这个 import 是从哪里来的，以及为什么应该放在这个文件顶部。
```

或者：

```txt
请画出这个模块的数据流，不要改代码。
```

## 十五、自己写时如何避免迷路

可以每写完一步就做一次小检查。

### 写类型后

问：

```txt
这个类型描述的是业务数据，还是组件 props？
```

业务数据放 `types/`。

组件 props 通常留在组件文件里。

### 写假数据后

问：

```txt
假数据字段是否完全符合类型？
```

### 写页面后

问：

```txt
这个页面是否能独立说明自己是什么模块？
```

### 写组件后

问：

```txt
这个组件是否只做一件事？
它有没有偷偷保存不该由自己保存的状态？
```

### 写表单后

问：

```txt
输入框 value 从哪里来？
onChange 最终调用的是哪个 setXxx？
提交时由谁创建新数据？
```

### 写列表后

问：

```txt
列表数据从哪里来？
map 的 key 是否稳定？
为空时显示什么？
```

## 十六、最重要的复刻模板

以后遇到类似模块，可以直接套这个思路：

```txt
1. 确定页面路径
2. 定义业务类型
3. 准备假数据
4. 页面 useState 接住假数据
5. 页面写 handleSubmit
6. 表单组件接收值和 onXxx 回调
7. 列表组件接收数组
8. 卡片组件接收单个对象
9. 空状态和错误状态单独处理
10. 检查数据流是否单向清楚
```

对应数据流：

```txt
types 定义数据形状
  ↓
lib 提供初始数据
  ↓
page 持有状态和动作
  ↓
form/list/card 通过 props 展示
  ↓
用户操作通过回调回到 page
```

这就是当前项目最核心的可复用模式。

## 十七、当前阶段不要过早做的事

为了保持学习节奏，当前阶段不要急着做：

- 一开始就接数据库。
- 一开始就写复杂全局状态管理。
- 一开始就把所有 UI 都抽成通用组件。
- 一开始就把所有 props 类型都放到 `types/`。
- 一开始就把页面改得过度抽象。

当前更重要的是把这条链路练熟：

```txt
类型
  ↓
假数据
  ↓
页面状态
  ↓
表单输入
  ↓
提交校验
  ↓
列表渲染
  ↓
组件拆分
```

把这条链路写顺之后，再接 API、SQLite、Zod 和 AI，会更稳。

# 第 8 课账户表单编程思路

这段代码是一个基于 React、Next.js Client Component 和 TypeScript 编写的账户管理页面。

核心功能：

> 用户填写账户信息，点击新增账户后，页面把新账户加入账户列表。

整体可以按四块理解：

```txt
环境声明与导入
  ↓
类型定义与初始数据
  ↓
子组件
  ↓
主组件：状态、逻辑、页面结构
```

## 一、代码整体结构

### 1. 环境声明与导入

```tsx
"use client";

import { useState } from "react";
```

- `"use client"`：声明当前文件是 Next.js 客户端组件。
- `useState`：React 的状态 Hook，用来保存会变化的数据。

因为本页要处理输入框、表单提交和列表更新，所以必须是客户端组件。

### 2. 类型定义与初始数据

先定义账户对象的结构：

```tsx
type Account = {
  id: string;
  name: string;
  type: "cash" | "bank" | "credit" | "investment";
  balance: number;
};
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `id` | 唯一标识 |
| `name` | 账户名称 |
| `type` | 账户类型，只能是四种指定值之一 |
| `balance` | 账户余额 |

然后准备 `initialAccounts`，作为页面首次加载时的模拟数据。

这一步的作用是：

> 先把数据规则定下来，再围绕这个规则写组件和逻辑。

### 3. 子组件

页面拆出两个展示组件：

| 组件 | 职责 |
| --- | --- |
| `AccountCard` | 展示单个账户的名称、类型和余额 |
| `AccountList` | 展示账户列表；如果为空，显示“暂无账户”提示 |

拆分思路：

```txt
AccountCard 负责一个账户
AccountList 负责一组账户
```

这样主组件不用关心每个账户卡片的具体展示细节。

### 4. 主组件 `Home`

`Home` 是页面入口，负责三件事：

1. 保存状态。
2. 处理提交逻辑。
3. 拼装页面 JSX。

页面最终由三块组成：

```txt
标题与描述
  ↓
账户新增表单
  ↓
账户列表
```

## 二、先从需求拆步骤

账户表单页面可以拆成这些小需求：

1. 页面一开始有一组账户数据。
2. 页面能展示账户列表。
3. 用户能输入账户名称。
4. 用户能选择账户类型。
5. 用户能输入账户余额。
6. 点击提交时要校验输入。
7. 校验通过后创建新账户对象。
8. 把新账户加入账户列表。
9. 提交成功后清空表单。
10. 输入错误时显示错误提示。

写代码时推荐顺序：

```txt
先定义数据长什么样
  ↓
先把假数据展示出来
  ↓
再让列表可以变化
  ↓
再加表单输入
  ↓
最后处理提交和校验
```

## 三、把会变化的数据放进状态

账户列表会变化，因为用户可以新增账户。

所以不能只写固定变量：

```tsx
const accounts = initialAccounts;
```

应该写成状态：

```tsx
const [accounts, setAccounts] = useState<Account[]>(initialAccounts);
```

可以读作：

```txt
accounts 是当前账户列表
setAccounts 用来更新账户列表
初始值来自 initialAccounts
```

新增账户时：

```tsx
setAccounts([...accounts, newAccount]);
```

意思是：

> 用旧账户列表和新账户组成一个新数组，再交给 React 保存。

## 四、表单状态

表单里用户正在输入的内容也会变化，所以也要放进状态：

```tsx
const [name, setName] = useState("");
const [type, setType] = useState<Account["type"]>("bank");
const [balance, setBalance] = useState("");
const [error, setError] = useState("");
```

这些状态不是最终账户对象，而是“表单草稿”。

| 状态 | 作用 |
| --- | --- |
| `name` | 当前输入的账户名称 |
| `type` | 当前选择的账户类型 |
| `balance` | 当前输入的账户余额 |
| `error` | 当前错误提示 |

提交时，再用这些草稿组装成真正的 `newAccount`。

## 五、受控组件

输入框要同时做到两件事：

1. 显示当前状态。
2. 用户输入时更新状态。

账户名称输入框：

```tsx
<input
  value={name}
  onChange={(event) => setName(event.target.value)}
  placeholder="例如：工资卡"
/>
```

可以读作：

```txt
输入框里显示 name
用户输入时，把输入框的新内容保存回 name
```

这里：

- `value`：输入框当前显示的内容。
- `onChange`：输入框内容变化时触发。
- `event`：这次输入变化产生的事件对象。
- `event.target`：触发事件的输入框。
- `event.target.value`：输入框当前的新内容。

下拉框和余额输入框也是同样思路。

## 六、提交逻辑

表单提交函数 `handleSubmit` 的步骤：

```txt
阻止浏览器默认刷新
  ↓
整理输入
  ↓
校验输入
  ↓
创建 newAccount
  ↓
更新 accounts
  ↓
清空表单和错误提示
```

核心代码：

```tsx
function handleSubmit(event: React.SubmitEvent<HTMLFormElement>) {
  event.preventDefault();

  const trimmedName = name.trim();
  const numericBalance = Number(balance);

  if (trimmedName.length === 0) {
    setError("请输入账户名称。");
    return;
  }

  if (!Number.isFinite(numericBalance)) {
    setError("请输入合法的账户余额。");
    return;
  }

  const newAccount: Account = {
    id: `account_${Date.now()}`,
    name: trimmedName,
    type,
    balance: numericBalance
  };

  setAccounts([...accounts, newAccount]);
  setName("");
  setType("bank");
  setBalance("");
  setError("");
}
```

注意顺序：

> 先校验，再创建账户；校验失败就 `return`，不继续执行新增逻辑。

## 七、把提交函数接到表单

```tsx
<form onSubmit={handleSubmit}>
  ...
  <button type="submit">新增账户</button>
</form>
```

可以读作：

```txt
用户点击提交按钮
  ↓
触发表单 submit
  ↓
执行 handleSubmit
```

`button` 要写 `type="submit"`，这样它才会触发表单提交。

## 八、错误提示和空状态

错误提示来自 `error` 状态：

```tsx
{error && <p className="text-red-600">{error}</p>}
```

可以读作：

```txt
如果 error 有内容，就显示 error
如果 error 是空字符串，就不显示
```

列表为空时，在 `AccountList` 里显示空状态：

```tsx
if (accounts.length === 0) {
  return <p>暂无账户，请先新增一个账户。</p>;
}
```

这样可以避免列表为空时页面一片空白。

## 九、本课核心模式

这一课真正练的是一个常见模式：

```txt
表单状态
  ↓
用户输入
  ↓
提交事件
  ↓
校验
  ↓
生成新对象
  ↓
更新列表状态
  ↓
页面重新渲染
```

以后做流水录入、负债录入、储蓄目标设置，也会反复使用这个模式。

## 十、通用拆解方法

以后遇到类似页面，可以按这些问题拆：

1. 页面要管理什么数据？
2. 哪些数据是固定的，哪些会变化？
3. 每条数据长什么样？先定义类型。
4. 哪些组件只负责展示？
5. 哪些数据需要放进 `useState`？
6. 用户会触发哪些事件？
7. 每个事件要按什么步骤处理？
8. 哪些输入需要校验？
9. 成功后更新哪个状态？
10. 失败时显示什么错误？

这就是从需求走到代码的基本路线。

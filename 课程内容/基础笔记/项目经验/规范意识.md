# 规范意识

> 编程中的思维习惯和设计原则。不是背规则，而是建立可迁移的心智模型。
> 长期记录，持续补充。具体易忘的操作细节见「易错细节」笔记。

---

## 一、核心思考框架：数据跨边界检查

隐蔽 Bug 大多来自同一个模式：**数据跨过边界后，不再可靠。**

每当你从"对面"拿到数据，先默认它可能不靠谱。这里的"对面"包括：

- 用户填的表单
- API 返回结果
- 数据库里读出来的字段
- 第三方库的输出
- 环境变量和配置文件
- `as` 断言或 `any` 转换后的值

关键习惯是问自己一句：**"对面有没有可能给我一个意想不到的东西？"**

这不是疑心重，而是因为对面不受你控制。类型系统是辅助工具，不是安全保证。

### TypeScript 类型不是运行时校验

类型系统只在开发期有效。代码编译成 JavaScript 后，所有类型信息全部丢失。运行时从 API、表单、AI 等边界传入的数据，TypeScript 管不了。

所以需要 Zod 在运行时再做一次校验。两者的关系是：

```
TypeScript  → 开发期约束，写代码时发现问题
Zod        → 运行时安全层，拦截真实非法数据
```

互补，不替代。

### 调试时按链路分层查，不信感觉信证据

问题排查不要凭感觉乱改代码。按链路逐层查，每一层有客观证据：

1. 浏览器 Console 直接 `fetch("/api/xxx")`，看 API 返回了什么。
2. 如果 API 返回正确，问题在前端（fetch 写错、状态没更新）。
3. 如果 API 报错或为空，查 Zod 校验规则和 service 层。
4. 如果怀疑数据库，用 `sqlite3` 直接查询表内容。

用 API 响应和数据库内容作为判断依据，不靠猜。

## 二、代码表达意识

### 变量名要说清楚"是什么"

变量名是代码的文档。金额、账户、负债、流水本身就容易混淆，清晰命名是降低认知负担的第一步。不要用 `a`、`b`、`x` 这种无意义的名字，尤其在财务项目里。

### 属于同一个事物的数据放在一起

几条相关的数据如果用分散的变量保存，阅读和理解的成本会变高。数据之间的"从属关系"应该由代码结构表达，而不是靠注释或程序员记忆。

### 数组和对象组合描述业务数据

一条流水是一个对象，多条流水就是一个数组。这是后端 API 返回、数据库读取、前端列表渲染的统一数据形态。从写练习的第一天就用这种结构，后面接触 API 和数据库时会自然觉得"本来就是这样"。

## 三、逻辑封装意识

### 一段业务逻辑只在一个地方维护

不要在页面里写一遍、API 里又写一遍、测试里再写一遍。后续公式必然漏改。函数是封装逻辑的基本单元，它让计算变得可复用、可测试、可审计。

### 函数输入输出的规格比实现更重要

写函数时先想清楚两件事：输入需要什么参数、各是什么类型；输出返回什么、调用方拿到后能直接用吗。这个习惯能避免"参数顺序靠自己记"、"返回值少个字段"的情况。

### 同样的输入必须得到同样的输出

这是"确定性计算"的基本要求，也是"可测试"的前提。如果一个函数同样的参数每次结果不一样，就没法写测试，也没法排查问题。

## 四、类型约束意识

### 用类型把"允许值"说清楚

不要用宽松的 `string` 或 `number` 概括一切。联合类型让不合法的数据在写代码时就被发现，而不是等到运行时报错。

### 可选字段表达不确定性

数据里有些字段不是每条记录都有。用 `?` 明确标出来，而不是靠跳过不写或者填空字符串。

### 类型是演进的，不是一步到位的

初学阶段写的类型不用追求完美。先定义核心字段跑通流程，后面再加字段、调结构是正常的。类型设计要有前瞻性，但不用提前过度设计。

### 主键用独立 ID，不用业务数据做标识

每条记录都需要一个唯一标识（主键）。不要用业务数据（如名称、日期）当主键，因为业务数据可能重复（两个账户都叫"工资卡"）。独立的 `id` 字段保证主键不重复，是数据完整性的基本保障。

### 字段名分层命名

不同层使用各自的语言习惯，通过映射桥接。TypeScript 代码中用驼峰命名（`createdAt`、`updatedAt`），数据库中用下划线命名（`created_at`、`updated_at`）。不要在数据库层写驼峰，也不要在 TS 层写下划线。同理，API 返回给前端的字段名又该用驼峰（前端习惯），这由序列化层负责转换。每层只关心自己的命名习惯，不互相污染。

## 五、组件设计意识

### 一个组件只做一件事

职责越单一，理解和修改的成本越低。如果一段 JSX 超过二三十行，或者一个文件里混了多个不相关的 UI 块，就该考虑拆分。

### 过早拆分不如先看清结构

拆组件不是越早越好。初学阶段先看清楚页面结构、理清数据从哪里来到哪里去，再抽组件会更稳。当你发现某块结构在多个页面重复，并且职责清晰时，再拆更合适。过早拆分会让数据来源和逻辑链路变得难追踪。

### Props 传整个对象，不传散装字段

子组件需要的数据如果天然是一个对象，就直接传整个对象。对象作为 props 更容易扩展：业务对象后面加字段，组件内部取用即可，不用改调用的地方。

### 先做界面，再接数据

开发新功能时，先用写死的假数据把界面搭出来，等界面确认没问题了，再替换成真实的 API 或数据库读取。一次只聚焦一件事。

## 六、状态管理意识

### 区分"固定值"和"状态"

固定不变的数据用普通变量。会随用户操作变化的数据才放 `useState`。放 state 的东西越多，组件重渲染的触发点越多。

### 不直接修改原数组或原对象

React 状态更新依赖"新引用"。用 `push`、`splice` 等直接修改原数组，React 无法感知变化。创建新数组（`...`展开、`filter`、`map`）再交给 set 函数。

### 受控组件的 value 和 onChange 成对出现

React 表单里，输入框显示什么由 state 控制，用户输入时通过 `onChange` 写回 state。只写 `value` 不写 `onChange`，输入框会无法输入。

### 校验在提交函数中前置执行

表单提交函数的结构：先阻止默认刷新，再校验，校验不通过就提前 return，通过才继续处理。不要出现"数据不合法但已经提交了"的情况。

### 空状态给用户指路

列表为空时，不只要说"暂无数据"，还应该告诉用户为什么没有、下一步该做什么。空状态是引导用户开始使用的入口。

### 数据驱动的 UI 考虑三态

每个从外部获取数据的 UI 都应该考虑三种状态：

- **empty**：没有数据时显示什么——不是空白页，是指引或占位。
- **error**：出错时怎么告诉用户——不是抛异常，是可读的错误提示。
- **loading**：等待时如何避免重复操作——禁用按钮或显示加载指示。

这三个状态覆盖了用户操作的常见场景，缺一个都会导致用户体验断档。

### 防重复提交用 ref 锁，不止靠按钮 disabled

React 状态更新不是同步互斥锁。快速连击时两次事件可能都在重新渲染前触发。提交函数开头用 ref 锁拦截：

```txt
if (lockRef.current) return;
lockRef.current = true;
// ... 异步请求 ...
lockRef.current = false;
```

按钮 disabled 和 ref 锁两层保护，降低重复请求和重复创建历史的风险。

### 每一个结果绑定到对应的消息，不用全局状态

多条消息场景下，每个助手消息携带自己的结构化结果。不把结果放在全局 `latestResult` 中，否则第二条回复会覆盖第一条的结果，旧消息和新结果错配。

## 七、UI 表达意识

### 内部值和展示值分开

程序内部存统一的值（英文、数字），只在展示层做转换。这样既保证数据一致性，又保证用户体验。

### 用视觉元素表达数据状态

数据的状态（正/负、空、错误、聚焦）应该通过视觉直接传达，而不是让用户自己读数字判断。负数用红色、金额加千分位、错误用浅红背景块。

### 布局限制宽度，内容不铺满

财务类页面不要让内容铺满整屏。限制最大宽度配合居中，阅读体验更好。

### 结构化结果和自然语言回复分开展示

API 同时返回 `reply`（给人阅读）和 `calculation`（给界面展示）。页面不应当从一段自然语言中正则提取金额数字。金额、缺口、所需储蓄等关键值使用结构化字段展示，保证精度和一致性。

### 假设信息不能隐藏

计算结果依赖的数据口径（数据月份、金额来源、月储蓄来源、收益率假设）必须结构化展示给用户。"假设"不是脚注装饰，是财务结果的一部分。用户需要判断结果是否建立在可接受的口径上。

## 八、架构意识

### 分层职责

一个系统里不同模块各有分工：AI 理解语言、代码做校验和计算、数据库负责持久化。各层不要串职责。AI 不直接给财务结论，代码不直接跟用户对话。

另一组典型分层是 API 层的分层职责：Route Handler 管 HTTP（解析请求、决定状态码、包装响应），Zod 管校验（拦截非法数据），service 管业务逻辑和数据库读写。API 文件不应该直接写 `db.insert()`，数据库操作放在 service 层。

```
app/api/accounts/route.ts    → HTTP 请求入口
schemas/finance.ts           → 运行时校验
lib/services/accounts.ts     → 业务逻辑 + 数据库操作
lib/db/schema.ts             → 表结构描述
lib/db/client.ts             → 数据库连接
```

每层只关心自己的事，不跨越职责边界。

### 每个环节对上一个环节保持警惕

上一步传过来的数据可能不靠谱：AI 解析出错、数据库返回 null、用户填了非法值。流程中要有校验点，而不是默认"上一步肯定没问题"。

### 计算结果要保存

不仅仅是为了给用户看，更是为了后续排查、审计、复现。计算历史本身就是一种数据资产。

### 学习新技术时先跑通单层链路

接触新概念（API、数据库、AI 调用）时，先让核心链路单独跑通，验证它本身没问题，再串联到页面或上游调用。如果同时做太多事，出错时很难判断问题在哪里。例如：先让 API 单独返回假数据并确认响应正确，再让前端 fetch 它，再接入真实数据库。每一层独立验证，定位问题更快。

### 财务金额在存储层不做精度妥协

不要在数据库、文件等存储层用普通小数保存金额。精度问题一旦写进存储，后续计算无论如何补救都无法挽回（比如存储了 `0.30000000000000004`）。金额用字符串（`TEXT`）保存原始值，计算时再交给专门的数学工具（如 decimal.js）处理。从源头守住精度，不在存储环节引入失真。

### 表关系是架构设计的一部分

数据实体之间的关联关系（如一条流水属于哪个账户）应该在数据库层设计时就明确。`transactions` 里的 `account_id` 关联到 `accounts.id`，这不是偶然的字段命名，是职责划分的结果。先画出表草图，再编码实现。

### ORM 是翻译层，不替代 SQL 理解

ORM 用代码语言描述表结构和查询，但使用 ORM 仍然要理解背后在操作数据库表。不要因为用了 ORM 就放弃对数据库的理解——字段是什么类型、查询做了几次往返、主键约束在哪里。ORM 的目的是减少重复劳动，不是屏蔽底层知识。

### 数据模型先行，再写代码

在写页面、API、组件之前，先把核心数据模型想清楚：有哪些实体、每个实体有哪些字段、实体之间怎么关联。数据模型混乱后，后面所有代码都会跟着歪。哪怕只是 MVP，也要先画表草图，让每个数据有明确归属。

### 只做当前闭环需要的模型

财务系统可以很复杂（分类表、预算表、汇率表、持仓表），但当前只做支撑核心功能的表。判断标准：这张表不加入，当前需求能不能跑通？能跑通就先不加。过早设计超过 MVP 需要的模型，会让学习周期变长。

## 九、页面与路由意识

### 文件夹结构即 URL 路径

Next.js App Router 中，`app/` 的文件夹结构直接决定页面 URL。创建页面时先想清楚路径，再建文件夹，再写 `page.tsx`。

### 先搭页面骨架，再填充功能

真实项目开发不建议一步到位：先确认产品结构是否合理，看到全貌后再逐页填充，不会把所有代码堆在一个文件里。

### 区分"服务端组件"和"客户端组件"

Next.js 默认是服务端组件。只有需要浏览器交互时才写 `"use client"`。不需要每个文件都写，也不该写的时候不写。

### 公共内容抽到布局

顶部导航、页脚、全局样式这些每个页面都有的内容，放在 `layout.tsx` 里，而不是每个页面单独写一遍。新增页面时自动拥有导航。

### 多页面应用职责清楚

每个页面只负责自己的模块内容。首页是入口，只做引导和介绍，不把对话、仪表盘、导入等功能全部堆在一个页面里。页面职责模糊后，用户找不到功能入口，代码也会越来越难维护。

### 假数据和类型集中管理

当前阶段用的临时假数据和类型定义，不要散落在各页面文件里。集中到 `lib/mock-data.ts` 和 `types/` 下，后续接入 API 和数据库时只替换集中位置的数据来源，页面代码不需要改。替换时机到了再换，不要提前混合。

## 十、变更管理意识

### Commit 是对未来自己的交代

commit message 要说明"改了什么、为什么改"。几个月后回头看历史，好的 message 能让你快速定位当时的修改意图。

### 提交前先检查再提交

不要信任自己的记忆。养成 `git status` → `git diff` → `git add` → `git commit` 的习惯，避免把临时文件和调试代码一起提交。

### 只提交源码和配置

依赖（`node_modules/`）、构建产物（`.next/`、`out/`）、环境变量（`.env*.local`）不提交。这些要么可重建，要么含敏感信息。

## 十一、API 设计意识

### 响应格式统一，前端不猜数据在哪里

API 的成功响应和错误响应应该使用固定结构。前端收到响应后先看 `ok` 字段，走不同分支。格式统一后，每个 API 的行为可预测，前端也不用为每个接口单独写解析逻辑。

推荐的思维判断：写 API 时统一用 `{ ok: true, data: ... }` 和 `{ ok: false, error: { code, message } }`，而不是让每个接口各自发明格式。

### API 路径表达资源，HTTP 方法表达动作

路径用复数名词（`/accounts`、`/transactions`），HTTP 方法表示做什么（`GET` 获取、`POST` 新增）。不要用路径表达动作（如 `/getAccountList`、`/addNewAccount`）。同一个路径通过不同方法处理不同操作，路径本身保持稳定。

### API 先返回假数据，再替换真实数据源

开发时先让 API 返回写死的假数据，确认请求链路跑通后，再替换成数据库查询或外部服务调用。这样做的好处是：接口路径和响应格式可以先确定，页面开发不等待后端完成。每一层独立验证，减少串行依赖。

### LLM 是"不可信的语言适配器"，不是计算器

LLM 在系统中的位置是理解自然语言、抽取结构化参数、组织回复。它不是财务计算器，不直接给财务结论。LLM 输出和表单输入、CSV 导入在同一信任层级——不可信，必须过 Zod。

### 两段式 AI 调用，不走捷径

正确流程是两段分开调用：第一段 LLM 只输出意图 JSON，程序调用计算引擎得到确定性结果，第二段 LLM 再把结果组织成自然语言。不走"让模型直接输出最终结论"的捷径。

### 意图 ≠ 计算输入

LLM 从用户问题中抽取的参数（如 targetAmount、deadlineMonths）是意图的一部分。计算函数需要的完整输入（当前余额、月储蓄、收益率）来自数据库和应用规则。LLM 不编造数据库中的数据，后端负责补齐可信输入。

### 业务编排层是编排器，不是转发器

Chat API 不是把用户问题转发给 LLM 就完事。编排层的职责是：校验请求 → 解析意图 → 白名单检查 → 读取数据 → 补充配置 → 调用计算器 → 保存历史 → 构造响应。每一层有明确边界，不把 LLM、数据库和计算逻辑混在一个文件里。

### 依赖注入让编排可测试

业务编排层的数据库、AI 调用、时间等外部依赖通过参数注入，测试时传假函数，生产时传真实实现。这样单元测试不访问网络、不读真实数据库、不产生费用，且固定当前时间保证结果可重复。

### Client Component 不导入服务端实现

浏览器页面只通过 HTTP 调用 API。不直接导入数据库 client、DeepSeek client、服务端环境变量。即使 `import type` 通常会被擦除，让页面依赖服务端文件仍会模糊职责边界。

## 十二、数据模型设计意识

### 三种 schema 职责分离，不混为一谈

项目里存在三种看起来相似但职责不同的描述方式：

- **前端类型**（`types/finance.ts`）：帮编辑器在写代码时提醒数据形状。只存在开发期，编译后消失。
- **Zod schema**（`schemas/*.ts`）：在程序运行时校验数据是否合法，比如表单提交时检查名称是否为空。
- **Drizzle schema**（`lib/db/schema.ts`）：描述数据库表结构，驱动建表和查询。关心字段类型、主键、默认值。

三者分别管不同阶段：写代码时提醒 → 运行时校验 → 持久化时建表。不要用 Drizzle schema 代替校验，也不要用前端类型代替运行时检查。

### 保留原始数据，不让导入内容丢失

外部数据（CSV 导入、API 回调）解析后，字段可能被拆分、转换、归类。保留一份原始内容（如 `rawPayload`），方便后续排查解析错误、重新处理格式变化、给用户核对原始记录。解析层可以错，但原始数据不丢。

### 关键数据优先软删除

财务应用中，一条记录删除后，历史计算、统计、审计可能因此失去上下文。软删除（标记 `deletedAt` 时间戳，不真正删除）让数据可追溯、可恢复。查询时默认过滤已删除记录，但审计时能还原完整链路。

### 计算历史保存审计链路

AI 财务结论不能只给一个最终答案。保存每次计算的输入、使用的公式和中间值、最终输出、AI 解析痕迹。这样用户和开发者都能回答"这个结论是从哪来的"。计算历史不是聊天记录，是财务计算的审计档案。

## 十三、校验意识

### 运行时校验是独立的安全层，不为类型系统替代

TypeScript 类型只在开发期有效，编译后全部消失。运行时从 API、表单、AI 等边界传入的数据，TypeScript 管不了。Zod 是运行时安全层，拦截真实非法数据。两者互补，不替代。

判断标准：数据跨边界后，不要以为 TypeScript 类型已经保证了合法性，必须用运行时校验工具再查一遍。

### safeParse 优于 parse

API 里用 `safeParse` 而不是 `parse`。因为：

- `parse` 校验失败会抛异常，程序被迫跳转到错误处理流程。
- `safeParse` 返回 `{ success, data/error }`，程序自己控制走成功分支还是失败分支，可以返回清晰的 400 响应。

这和"不要用异常控制业务逻辑"的编程原则一致。

### 校验失败返回统一结构

前端不猜校验失败的数据在哪里。API 校验失败时统一返回：

```
{ ok: false, error: { code: "VALIDATION_ERROR", message, issues: [{ path, message }] } }
```

前端取 `result.ok` 判断成功/失败，取 `issues[0].message` 展示第一条错误。

### 校验逻辑集中管理

Zod schema 放在独立的 `schemas/` 目录下，不散落在 API 或页面里。API 和前端都能引用同一套 schema，保证校验规则不分裂。后续新增字段时只改 schema 文件一处。

### AI 输出也要校验

Zod 不只校验用户输入。AI 输出的 JSON 同样不可靠，也要通过 Zod 校验后才能进入确定性计算。原则不变：AI 负责理解语言，Zod 负责校验结构，代码负责确定性计算。

### LLM 输出和表单输入在同一信任层级

正确心态：AI 很擅长理解语言，但它的输出仍然是外部输入。把 LLM 当成系统边界外的输入源，和用户表单、CSV 文件、外部 API 在同一层级——都不可信，必须过运行时校验。

### JSON.parse 和 Zod 分工明确

```txt
模型原始字符串
  ↓
JSON.parse          → 只检查是否是合法 JSON
  ↓
Zod safeParse       → 检查是否是合法 FinanceIntent
```

前者回答"是不是 JSON"，后者回答"是不是业务可接受的意图"。两者不能合并，也不能省略一个。

### Prompt 提高概率，Zod 决定结果

```txt
Prompt 负责提高输出符合契约的概率
Zod 负责决定输出是否可以进入系统
```

两者不能互相替代。不能因为 Prompt 写了"只输出 JSON"就不做校验，也不能因为做了校验就随意写 Prompt。

### 外部 API 响应也要过 Zod

不仅 LLM 输出要校验，调用 LLM 时收到的 API 响应本身也要校验。DeepSeek 返回的 HTTP 响应同样不可信——状态码 200 不等于数据结构合法。需要为外部 API 响应写最小 Zod schema，校验 choices、content、finish_reason 等字段。

完整成功链路：

```txt
HTTP 200
  ↓
响应 JSON 可解析
  ↓
响应结构合法（choices 非空、content 非空）
  ↓
finish_reason 不是 "length"
  ↓
content 是合法 JSON
  ↓
content 符合 FinanceIntent schema
```

### 客户端收到的 API 响应也要校验

服务端返回的 JSON 到浏览器后仍然是运行时不可信数据。客户端写 `as ChatSuccessData` 只是告诉 TypeScript"相信我"，不会检查 `historyId`、`calculation.steps`、`assumptions` 等字段是否存在。应该在 fetch 后把响应作为 `unknown` 传给 Zod schema 校验，在网络边界立即发现契约不一致。

### 同时检查 HTTP 状态和业务状态

```txt
HTTP 200 + body.ok === false
  → 业务失败，不能当成功处理

HTTP 500 + body.ok === true
  → 异常组合，不能信任
```

完整成功要求 HTTP 状态成功且业务壳成功，两者缺一不可。

### 多层错误映射，不把内部细节暴露给用户

内部错误有明确分类（DeepSeekError、ChatServiceError、未知错误），每类映射到稳定的 HTTP 状态码和对外 code。对外只返回安全的用户文案，不暴露数据库路径、供应商内部细节、堆栈或 API Key。

## 十四、安全配置意识

### 密钥与源码分离

API Key、数据库密码等敏感凭据不写在 TypeScript 源码中。源码只引用环境变量名（如 `process.env.DEEPSEEK_API_KEY`），真实值放在 `.env.local` 中。

### 密钥不进入 Git、不进入浏览器、不进入日志

- `.gitignore` 忽略 `.env*`，阻止密钥意外提交。
- 不使用 `NEXT_PUBLIC_` 前缀暴露给浏览器。
- 不把密钥打印到日志、错误消息或页面中。
- 密钥只出现在服务端 HTTP Authorization header 里。

### 外部 API 调用设超时、限制长度

调用外部 API（DeepSeek 等）时：用 AbortController 设超时，不给程序无限等待的机会；用户输入设长度上限，控制费用和延迟；`max_tokens` 设合理上限，防止输出膨胀。

### 错误分类，不改写用户内容

外部 API 的错误分不同类别处理：配置错误（缺少 Key）直接报错；临时错误（超时、网络）可有限重试；认证/余额错误不重试。错误信息在服务端保留诊断细节，对用户只展示可读的简短提示，不暴露内部细节。

### 最小必要上下文

向 LLM 发送意图解析请求时只发送用户问题本身，不发送账户余额、流水明细、数据库内容等冗余信息。减少 token 消耗、降低隐私风险、减少无关信息干扰。

### 不满 localStorage 保存对话

用户财务问题可能包含收入、资产目标、债务等敏感信息。不要把对话内容随意写入浏览器 localStorage 或 cookies。持久化对话需要单独设计隐私、过期和删除规则。

### 不自动重试可能已写入历史的 POST

Chat API 成功时会创建 calculation_history。如果响应在网络中丢失，客户端自动重试可能创建重复历史记录。在没有幂等键的情况下，不应对写入类接口做无限自动重试。

### 模型名安全暴露，不泄露 Key

审计记录需要保存模型名称，但不应该让业务层拿到 API Key。通过无密钥函数（如 `getDeepSeekModelName()`）暴露模型名，Key 只存在 Authorization header 中。

# 代码编排与书写顺序的思路

## 编排：按职责分组，而不是按关键字分组

一个文件里，代码应该按**职责和阅读顺序**组织，而不是按 `import` / `export` / `function` / `const` 这样的声明关键字归类。

### 按关键字分组（直觉但不好读）

```
import ...                    // 所有 import

export type A = {};           // 所有 export 堆在前面
export type B = {};
export function main() {}

function helperA() {}         // 所有 function 堆在后面
function helperB() {}
```

问题：读到 `main()` 里面调了 `helperA`，但 `helperA` 在很远的地方，视线要来回跳。

### 按职责分组（推荐）

```
import ...                          // 依赖声明，始终在最前

// ── 帮助函数 ──                    // 内部零件，最底层
function helperA() {}
function helperB() {}

// ── 类型 ──                        // 公共契约，中间层
export type Input = {}
export type Output = {}

// ── 主函数 ──                      // 顶层入口，依赖上面所有
export function main() {}
```

读文件的视线是**单向的、自顶向下**的：
1. 先看到依赖（`import`）
2. 再看到内部工具函数（了解主函数会用哪些小零件）
3. 再看到输入输出类型（了解主函数的合同长什么样）
4. 最后看到主函数（零件和合同都认识了，读起来不卡顿）

### 示例：`cash-flow.ts` 的实际结构

```
┌─ import
├─ 常量    (FIXED_EXPENSE_CATEGORIES, SHANGHAI_OFFSET_MS)
├─ 帮助函数 (isFixedExpense, assertMonth, toShanghaiMonth)
├─ 类型     (CashFlowTransaction, ..., MonthlyCashFlowResult)
└─ 主函数   (calculateMonthlyCashFlow)
```

## 阅读顺序 ≠ 书写顺序

| | 顺序 | 原因 |
|---|---|---|
| **写** | 主函数 → 零件 | 大脑在探索"我要做什么"，从目标往下拆 |
| **读 / 维护** | 零件 → 主函数 | 大脑在理解"它怎么做的"，从基础往上构建 |

### 实际书写过程

以 `savings-goal.ts` 为例：

1. 先写出函数签名——明确输入输出。

```ts
export function calculateSavingsGoal(
  input: SavingsGoalInput,
): SavingsGoalResult {
```

2. 接着写核心计算——复利公式。

```ts
const monthlyRate = annualRate.dividedBy(100).dividedBy(12);
growthFactor = monthlyRate.plus(1).pow(input.months);
annuityFactor = growthFactor.minus(1).dividedBy(monthlyRate);
```

3. 写着写着发现需要校验——顺手写 `assertMonths`、`assertNonNegative`。先放在主函数旁边。

4. 主函数写完后，再回头看这些辅助函数——意识到它们是内部细节、不需要暴露，**挪到类型定义前面**。

所以过程是：**主函数 → 发现需要的零件 → 写在手边 → 写完后整理搬位置**。

### 例外：组件文件

`page.tsx` 和 UI 组件文件不需要写完了再调顺序。因为它们的结构是模板化的：

```
imports
types/props
component function  (直接从头到尾)
```

组件不像计算函数那样有复杂的内部零件需要拆出来，从一开始就能按最终顺序写。

## 小结

- **文件应该能像文章一样从头读到尾**，而不是像一本倒着翻的字典。
- 写代码是自顶向下拆解，整理代码是自底向上构建。
- 最终呈现以"读"的体验为准——代码被读的次数远超被写的次数。

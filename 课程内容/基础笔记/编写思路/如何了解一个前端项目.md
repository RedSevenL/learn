# 如何了解一个前端项目

## 这篇笔记解决什么问题

拿到一个没见过的项目，第一反应可能是茫然：从哪个文件开始看？关注哪些内容？哪些可以跳过？

这篇笔记以 `ai-finance-cfo` 项目为例，讲一套**通用的探索流程**，以后面对任何项目都可以复用。

---

## 第一步：看 package.json — 知道用了什么工具

`package.json` 的 `dependencies` 和 `devDependencies` 列了所有依赖。只看几个关键项：

```json
{
  "dependencies": {
    "next": "16.2.7",         // 框架，告诉你是 Next.js 项目
    "react": "19.2.4",        // UI 库
    "zod": "^4.4.3",          // 数据校验库
    "drizzle-orm": "^0.45.2", // 数据库 ORM
    "@libsql/client": "^0.17.3" // SQLite 客户端
  },
  "devDependencies": {
    "tailwindcss": "^4",      // 样式框架
    "typescript": "^5",       // 类型系统
    "drizzle-kit": "^0.31.10" // 数据库迁移工具
  }
}
```

**关注点**：框架是什么（Next.js）、UI 库是什么（React）、样式方案（Tailwind）、数据库（SQLite + Drizzle）、数据校验（Zod）。

**跳过**：版本号、`@types/*` 类型包、eslint 配置等工具类依赖。

这一步得到结论：这是一个 **Next.js + TypeScript + Tailwind + SQLite** 的项目。

---

## 第二步：看项目顶层目录结构 — 知道文件夹分工

```
ai-finance-cfo/
├── app/              # 页面和 API 路由（Next.js 的路由层）
├── components/       # 可复用的 UI 组件
├── lib/              # 通用逻辑：数据库、工具函数
├── schemas/          # Zod 校验规则（数据的"门卫"）
├── types/            # TypeScript 类型定义
├── scripts/          # 一次性脚本
├── drizzle.config.ts # 数据库迁移配置
└── next.config.ts    # Next.js 配置
```

**关注点**：每个文件夹的职责。Next.js 项目最大的特点是 `app/` 既是页面路由也是 API 路由。

**跳过**：`.next/`（构建产物）、`node_modules/`（依赖包）、`next-env.d.ts`、`next.config.ts`（通常不需要改）。

---

## 第三步：看 pages — 知道有哪些页面

Next.js 的路由是由 `app/` 下的文件结构决定的：

```
app/
├── page.tsx          → /
├── layout.tsx        → 全局布局（导航栏）
├── dashboard/
│   └── page.tsx      → /dashboard （仪表盘）
├── scenarios/
│   └── page.tsx      → /scenarios （场景模拟）
├── chat/
│   └── page.tsx      → /chat （AI 对话）
├── import/
│   └── page.tsx      → /import （CSV 导入）
└── api/
    ├── health/
    │   └── route.ts  → /api/health （健康检查）
    └── accounts/
        └── route.ts  → /api/accounts （账户增删查）
```

**关注点**：有哪些页面、每个页面做什么、哪些是骨架页（还没写真实逻辑）。

在这个项目里，`/dashboard` 是唯一有交互逻辑的页面，其余都是骨架。

## 第四步：看数据模型 — 知道业务在管什么

先看 **TypeScript 类型**（`types/finance.ts`），它是数据的"蓝图"：

```ts
export type Account = {
  id: string;
  name: string;
  type: "cash" | "bank" | "credit" | "investment";
  balance: number;
};
```

再看 **数据库表结构**（`lib/db/schema.ts`），它是数据在数据库里的真实样子：

```ts
export const accounts = sqliteTable("accounts", {
  id: text("id").primaryKey(),
  name: text("name").notNull(),
  type: text("type").notNull(),
  balance: text("balance").notNull(),  // 存成字符串避免浮点精度问题
  ...
});
```

再看 **Zod 校验规则**（`schemas/finance.ts`），它是前端/API 接收数据时的"门卫"：

```ts
export const createAccountSchema = z.object({
  name: z.string().trim().min(1),
  type: accountTypeSchema,
  balance: moneyStringSchema  // 限定金额格式
});
```

**关注点**：项目在管什么数据（Account、Transaction、Liability），每个数据有哪些字段。

| 数据 | 用途 |
|---|---|
| Account | 账户（银行卡、现金等） |
| Transaction | 流水（收入、支出、转账） |
| Liability | 负债（贷款、信用卡账单） |
| Goal | 储蓄目标 |
| Scenario | 场景模拟配置 |
| CalculationHistory | 计算结果追溯 |

## 第五步：看页面交互 — 知道数据怎么流动

从头到尾追踪一个功能的完整流程。以"新增账户"为例：

**入口**：`app/dashboard/page.tsx`

```tsx
// 1. 页面声明状态
const [accounts, setAccounts] = useState<Account[]>(initialAccounts);
const [name, setName] = useState("");

// 2. 提交时更新状态
function handleSubmit(event) {
  setAccounts([...accounts, newAccount]);
  setName("");
}

// 3. 把状态和回调传给子组件
<AccountForm
  name={name}
  onNameChange={setName}
  onSubmit={handleSubmit}
/>

// 4. 把列表数据传给列表组件
<AccountList accounts={accounts} />
```

**子组件**：`components/accounts/AccountForm.tsx`

```tsx
// 接收 props，触发回调
<input value={name} onChange={(e) => onNameChange(e.target.value)} />
<form onSubmit={onSubmit}>...</form>
```

**目前的数据来源**：`lib/mock-data.ts`（假数据），后续要改成从 API `/api/accounts` 获取。

**关注点**：数据从哪里来（目前是假数据）、存在哪里（useState）、流向哪里（通过 props 传给子组件）、用户操作怎么触发更新（事件 → setState）。

## 第六步：看 API 层 — 知道后端长什么样

`app/api/accounts/route.ts` 是账户相关的 API：

```ts
// GET /api/accounts — 获取账户列表
export async function GET(request: Request) {
  return Response.json({ ok: true, data: { accounts: initialAccounts } });
}

// POST /api/accounts — 新增账户
export async function POST(request: Request) {
  const body = await request.json();
  const result = createAccountSchema.safeParse(body);  // 先校验
  if (!result.success) {
    return Response.json({ ok: false, error: ... }, { status: 400 });
  }
  return Response.json({ ok: true, data: { account: result.data } }, { status: 201 });
}
```

**关注点**：API 返回格式统一为 `{ ok, data, error }`，数据进来先过 Zod 校验。

## 了解新项目的通用步骤

| 顺序 | 看什么 | 得到什么 |
|---|---|---|
| 1 | `package.json` | 技术栈（框架、库、数据库） |
| 2 | 目录结构 | 项目分工方式 |
| 3 | `app/` 下的页面 | 有哪些页面和 API |
| 4 | `types/` + `schemas/` + 数据库表 | 业务数据模型 |
| 5 | 一个交互完整的页面 | 数据怎么流动（state → props → 事件） |
| 6 | API 文件 | 前后端怎么对接 |

**一个原则**：不要从头读到尾，而是**按层看**——先看"有哪些页面"，再看"页面里有什么数据"，再看"数据怎么流动"。每层只看关键文件，不纠结细节。

**另一个原则**：区分"核心"和"骨架"。有交互逻辑的页面（如 `/dashboard`）值得细看，纯展示的骨架页扫一眼结构就够了。

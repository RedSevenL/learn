# 从想法到代码的编写顺序

## 核心思路

写代码不是一上来就想“我要写什么语法”，而是先把任务拆成几个层次：

1. 页面上需要有什么。
2. 页面要长成什么样。
3. 程序里要记住什么数据。
4. 数据要怎么变化。
5. 数据变化后怎么显示到页面。
6. 用户做了什么操作。
7. 每个操作会怎样改变数据。

简单说：

> 先看页面，再找状态；先让数据成立，再让页面变化；最后才绑定事件。

## 第一步：先拆页面元素

拿到一个需求，先不要急着写 TypeScript。

先问：

> 页面上必须出现哪些东西？

以“比大小游戏”为例，页面需要：

- 按钮 A：开始游戏。
- 按钮 B：结束游戏。
- 区域 A-D：显示 4 个随机数。
- 区域 E：显示题数、得分、正确率。

所以第一步写 HTML，本质上是在回答：

> 这个程序有哪些可见元素？

这一步不用思考数据和逻辑，只要把页面元素摆出来。

## 第二步：再写 CSS 布局

HTML 解决“有什么”，CSS 解决“怎么摆”。

这一阶段只关心：

- 哪些元素在一行。
- 哪些元素像按钮。
- 哪些元素像可点击区域。
- 哪个区域用来显示信息。

CSS 仍然不负责游戏逻辑。

所以前两步可以这样记：

> HTML 定义结构，CSS 定义外观。

## 第三步：找出程序要记住的状态

进入 TypeScript 后，不要先想事件。

先问：

> 这个程序运行过程中，有哪些东西会变化，而且需要被记住？

这就是“状态”。

比大小游戏里会变化的东西有：

- 游戏是否正在进行：`playing`
- 做了几题：`round`
- 当前得分：`score`
- 当前 A-D 四个区域的数字：`numbers`

所以可以定义：

```ts
type GameState = {
  playing: boolean;
  round: number;
  score: number;
  numbers: Record<Zone, number>;
};
```

这一步很重要，因为状态就是程序的核心。

页面只是显示状态，事件只是修改状态。

## 第四步：给关键概念起类型

有些值不是随便什么都可以，而是固定几个选项。

比如区域只有：

```ts
"A" | "B" | "C" | "D"
```

所以先定义：

```ts
type Zone = "A" | "B" | "C" | "D";
```

这样后面函数参数、对象字段、返回值都可以复用这个类型。

这一步是在回答：

> 程序里有哪些核心概念？这些概念允许哪些值？

## 第五步：先写纯逻辑函数

纯逻辑函数指的是：不碰页面，只处理数据。

比如：

```ts
function generateNumbers(): Record<Zone, number> {
  // 生成 A-D 四个随机数
}
```

这个函数只负责生成数字，不负责显示页面。

再比如：

```ts
function getMaxZone(numbers: Record<Zone, number>): Zone {
  // 找出最大数所在区域
}
```

这个函数只负责判断最大值，不负责加分，也不负责刷新页面。

这样写的好处是：

- 每个函数职责很清楚。
- 出错时容易定位。
- 不依赖 DOM，容易测试。

简单记：

> 先写数据逻辑，再写页面逻辑。

## 第六步：把状态渲染到页面

有了状态之后，再问：

> state 里的数据要显示到页面哪里？

比大小游戏里：

- `state.numbers.A` 显示到区域 A。
- `state.numbers.B` 显示到区域 B。
- `state.numbers.C` 显示到区域 C。
- `state.numbers.D` 显示到区域 D。
- `state.round`、`state.score`、正确率显示到区域 E。

所以写：

```ts
function render(): void {
  zoneA.textContent = state.numbers.A.toString();
  zoneB.textContent = state.numbers.B.toString();
  zoneC.textContent = state.numbers.C.toString();
  zoneD.textContent = state.numbers.D.toString();

  const accuracy = state.round === 0 ? 0 : Math.round((state.score / state.round) * 100);
  statusPanel.textContent = `题数：${state.round}，得分：${state.score}，正确率：${accuracy}%`;
}
```

`render()` 的职责是：

> 根据当前 state，把页面更新成对应样子。

它不应该负责生成随机数，也不应该负责判断答案。

## 第七步：最后写交互事件

事件是用户动作。

写事件前先问：

> 用户可以做哪些动作？

比大小游戏里有三个动作：

1. 点开始按钮。
2. 点 A-D 某个区域。
3. 点结束按钮。

再问：

> 每个动作会怎么改变 state？

开始按钮：

- `playing = true`
- `round = 0`
- `score = 0`
- 生成新数字
- `render()`

选择区域：

- 如果没开始，直接结束。
- 判断用户选的是不是最大值。
- `round + 1`
- 答对 `score + 1`
- 答错 `score - 1`
- 生成下一题
- `render()`

结束按钮：

- `playing = false`
- `render()`

这一步可以记成：

> 事件函数 = 修改 state + 调用 render。

## 一个可复用的编写顺序

以后做一个小项目，可以按这个顺序：

1. 写 HTML：页面上有什么。
2. 写 CSS：页面怎么摆。
3. 定义类型：核心概念有哪些。
4. 定义状态对象：程序要记住什么。
5. 写纯逻辑函数：数据怎么生成、判断、计算。
6. 获取 DOM 元素：页面上的东西怎么拿到。
7. 写 `render()`：状态怎么显示到页面。
8. 写事件函数：用户操作怎么改变状态。
9. 绑定事件：把用户动作接到函数上。
10. 最后补增强功能：倒计时、弹窗、结束统计、动画等。

## TypeScript 文件里的推荐摆放顺序

当一个 `.ts` 文件开始变长时，建议按“从基础到启动”的顺序摆放代码。

推荐顺序：

```text
1. 类型定义
2. 状态对象
3. DOM 元素查询
4. 纯逻辑函数
5. 渲染函数
6. 计时器、请求等辅助流程函数
7. 事件处理函数
8. 最下面绑定事件或启动程序
```

以比大小游戏为例：

```ts
type Zone = "A" | "B" | "C" | "D";

const state = {
  // 游戏状态
};

const startButton = document.querySelector("#startButton") as HTMLButtonElement;
const zoneA = document.querySelector("#zoneA") as HTMLDivElement;

function generateNumbers() {
  // 生成数据
}

function getMaxZone() {
  // 判断最大值
}

function render() {
  // 把 state 显示到页面
}

function startTimer() {
  // 倒计时流程
}

function startGame() {
  // 开始游戏
}

function chooseZone() {
  // 选择答案
}

function endGame() {
  // 结束游戏
}

startButton.addEventListener("click", startGame);
zoneA.addEventListener("click", () => chooseZone("A"));
```

这样组织的好处是：

- 读代码时能从“数据结构”一路读到“用户操作”。
- 函数职责更清楚。
- 最下面一眼能看到程序是怎么启动的。
- 事件绑定不会散落在文件中间。

函数顺序不是完全随便的。虽然 `function fn() {}` 有函数提升，技术上可以先调用后定义，但为了可读性，建议：

> 先定义，再使用；先底层，再上层；最后启动。

例如：

- `generateNumbers()` 是基础函数，放前面。
- `chooseZone()` 会用到 `generateNumbers()`、`getMaxZone()`、`render()`，所以放后面。
- `addEventListener()` 是启动和连接用户操作的代码，所以放最下面。

还有一个判断标准：

> 如果一个函数内部已经调用了 `render()`，外面通常不要再重复调用 `render()`。

比如 `startTimer()` 里已经重置了 `timeLeft` 并调用 `render()`，那 `startGame()` 里调用 `startTimer()` 后，就不需要再写一次 `render()`。

## 判断自己下一步该写什么

如果不知道下一步写什么，就问这几个问题：

| 问题 | 对应代码 |
| --- | --- |
| 页面还缺东西吗？ | 写 HTML |
| 页面不好看或没排好？ | 写 CSS |
| 有哪些数据会变化？ | 写 state |
| 某些值只有固定选项？ | 写 type |
| 有计算或判断规则？ | 写纯函数 |
| 数据怎么显示？ | 写 render |
| 用户能做什么？ | 写事件函数 |
| 点了没反应？ | 绑定 addEventListener |

## 最重要的一句话

小项目的核心不是“先写很多代码”，而是先分清楚：

> 页面结构、状态数据、逻辑函数、渲染函数、事件函数。

只要这五块分清楚，代码顺序就会自然很多。

## 三、什么是端到端验收

本课中的端到端不是只测试：

```txt
一个函数输入
  ↓
一个函数输出
```

也不是只测试：

```txt
POST /api/chat
  ↓
返回 201
```

完整链路必须跨越：

```txt
用户界面
  ↓
HTTP API
  ↓
运行时校验
  ↓
AI 意图解析
  ↓
业务编排
  ↓
数据库读取
  ↓
确定性计算
  ↓
数据库写入
  ↓
HTTP 响应
  ↓
用户界面展示
```

任何一段断开，都不能说 MVP 已经完成完整演示。

## 四、验收不是“随便点一遍”

随便点页面通常只能证明：

```txt
某个按钮没有立刻报错
```

正式验收要提前定义：

- 输入数据。
- 预期业务结果。
- 预期 HTTP 结果。
- 预期数据库结果。
- 预期页面结果。
- 错误路径。
- 证据位置。

本课会使用一套固定演示数据，让结果可复核。

## 五、先定义 MVP 必做范围

本阶段的 MVP 必做功能是：

### 数据层

- 创建账户。
- 更新账户余额。
- 删除账户。
- 创建负债。
- 创建或 CSV 导入流水。
- 查询有效账户、流水和负债。

### 计算层

- 金额使用 Decimal。
- 月现金流计算。
- 储蓄率。
- 储蓄目标计算。
- What-if 场景计算。
- 债务策略计算。
- 计算步骤可追溯。
- 计算历史可保存。

### AI 层

- DeepSeek 接收用户问题。
- 输出受限 JSON 意图。
- Zod 校验意图。
- 暂只允许已支持意图进入计算器。
- AI 不直接计算金额。

### 交互层

- Chat 页面有输入、loading 和错误状态。
- Chat 页面显示结构化结果。
- Chat 页面可以展开计算步骤。
- CSV 导入前有预览和确认。
- 仪表盘显示核心指标和趋势。
- 无数据时有空状态。
- 最近计算历史可以查看。

### 工程层

- 核心测试通过。
- lint 通过。
- 生产构建通过。
- README 是项目说明，不是脚手架说明。

## 七、什么可以作为证据

有效证据包括：

- 浏览器页面截图。
- HTTP 响应中的 `historyId`。
- `/api/calculations/history` 返回记录。
- 历史页面中的记录。
- 测试命令输出。
- lint 输出。
- build 输出。
- Git 提交 ID。
- 精确的失败步骤和错误码。

无效或较弱的证据包括：

```txt
“我记得刚才能用”
“代码看起来没问题”
“大概是 AI 算的”
“页面没有明显报错”
```

验收记录应该让另一个人能够复查。

## 十六、自动测试绝不能偷偷访问真实 DeepSeek


- `fetcher` 被注入或 mock。

## 十九、为什么历史 JSON 不能直接 JSON.parse 后信任

`calculation_history` 保存：

```txt
inputJson
formulaJson
outputJson
modelTraceJson
```

这些字段虽然由项目写入，但仍可能因为：

- 旧版本结构。
- 手工调试数据。
- 数据迁移。
- 部分损坏。
- 未来公式升级。

而不符合当前页面预期。

错误做法：

```ts
const input = JSON.parse(row.inputJson) as SavingsGoalInput;
```

正确做法：

```txt
JSON.parse
  ↓
unknown
  ↓
Zod 校验
  ↓
可展示历史
```

坏记录应该被单独标记，不能让整个页面崩溃。

## 二十、建立历史响应 schema

创建：

```txt
schemas/calculation-history.ts
```

写入：

```ts
import * as z from "zod";

export const calculationHistoryRowSchema = z.object({
  id: z.string().min(1),
  intentType: z.string().min(1),
  inputJson: z.string(),
  formulaJson: z.string(),
  outputJson: z.string(),
  modelTraceJson: z.string().nullable(),
  createdAt: z.number().int().positive()
});

export const calculationHistoryResponseSchema = z.object({
  ok: z.literal(true),
  data: z.object({
    histories: z.array(calculationHistoryRowSchema)
  })
});

export type CalculationHistoryRow = z.infer<
  typeof calculationHistoryRowSchema
>;
```

再建立错误响应：

```ts
export const calculationHistoryErrorResponseSchema = z.object({
  ok: z.literal(false),
  error: z.object({
    code: z.string(),
    message: z.string()
  })
});

export const calculationHistoryApiResponseSchema =
  z.discriminatedUnion("ok", [
    calculationHistoryResponseSchema,
    calculationHistoryErrorResponseSchema
  ]);
```

## 二十一、建立历史内部 JSON schema

继续在同一文件增加：

```ts
import { savingsGoalSchema } from "@/schemas/savings-goal";

const calculationValueSchema = z.union([
  z.string(),
  z.number(),
  z.boolean(),
  z.null()
]);

const calculationStepSchema = z.object({
  id: z.string(),
  title: z.string(),
  description: z.string(),
  formula: z.string(),
  inputs: z.record(z.string(), calculationValueSchema),
  outputs: z.record(z.string(), calculationValueSchema)
});

const savingsGoalFormulaSchema = z.object({
  calculator: z.literal("savings_goal"),
  version: z.string(),
  assumptions: z.object({
    annualRateType: z.string(),
    contributionTiming: z.string(),
    moneyRounding: z.string(),
    requiredSavingRounding: z.string()
  }),
  steps: z.array(calculationStepSchema)
});

const savingsGoalOutputSchema = z.object({
  targetAmount: z.string(),
  currentAmount: z.string(),
  monthlySaving: z.string(),
  annualRate: z.string(),
  months: z.number().int(),
  projectedAmount: z.string(),
  reached: z.boolean(),
  gap: z.string(),
  excess: z.string(),
  requiredMonthlySaving: z.string()
});

const modelTraceSchema = z.object({
  provider: z.literal("deepseek"),
  model: z.string(),
  parsedIntent: z.literal("savings_goal")
});
```

注意：

```txt
outputJson
```

不包含 `steps`。

步骤保存在：

```txt
formulaJson.steps
```

这是第 26、30 课建立的审计结构。

## 二十二、安全解析单条历史

继续增加：

```ts
export type ParsedSavingsGoalHistory = {
  status: "valid";
  id: string;
  createdAt: number;
  input: z.infer<typeof savingsGoalSchema>;
  formula: z.infer<typeof savingsGoalFormulaSchema>;
  output: z.infer<typeof savingsGoalOutputSchema>;
  modelTrace: z.infer<typeof modelTraceSchema> | null;
};

export type InvalidCalculationHistory = {
  status: "invalid";
  id: string;
  createdAt: number;
  message: string;
};

export function parseCalculationHistory(
  row: CalculationHistoryRow
): ParsedSavingsGoalHistory | InvalidCalculationHistory {
  if (row.intentType !== "savings_goal") {
    return {
      status: "invalid",
      id: row.id,
      createdAt: row.createdAt,
      message: `暂不支持展示 ${row.intentType} 历史`
    };
  }

  try {
    const inputValue: unknown = JSON.parse(row.inputJson);
    const formulaValue: unknown = JSON.parse(row.formulaJson);
    const outputValue: unknown = JSON.parse(row.outputJson);
    const modelTraceValue: unknown =
      row.modelTraceJson === null
        ? null
        : JSON.parse(row.modelTraceJson);

    const input = savingsGoalSchema.safeParse(inputValue);
    const formula =
      savingsGoalFormulaSchema.safeParse(formulaValue);
    const output =
      savingsGoalOutputSchema.safeParse(outputValue);
    const modelTrace =
      modelTraceValue === null
        ? { success: true as const, data: null }
        : modelTraceSchema.safeParse(modelTraceValue);

    if (
      !input.success ||
      !formula.success ||
      !output.success ||
      !modelTrace.success
    ) {
      return {
        status: "invalid",
        id: row.id,
        createdAt: row.createdAt,
        message: "历史结构与当前版本不兼容"
      };
    }

    return {
      status: "valid",
      id: row.id,
      createdAt: row.createdAt,
      input: input.data,
      formula: formula.data,
      output: output.data,
      modelTrace: modelTrace.data
    };
  } catch {
    return {
      status: "invalid",
      id: row.id,
      createdAt: row.createdAt,
      message: "历史 JSON 无法解析"
    };
  }
}
```

不要把 Zod 的完整内部错误直接显示给普通用户。

开发调试可以在受控日志中记录必要信息。

```ts
    ParsedSavingsGoalHistory |

  >
```

加载：

```ts
useEffect(() => {
  const controller = new AbortController();

  async function loadHistories() {
    try {
      setIsLoading(true);
      setError(null);

      const response = await fetch(
        "/api/calculations/history",
        { signal: controller.signal }
      );
      const body: unknown = await response.json();
      const parsed =
        calculationHistoryApiResponseSchema.safeParse(body);

      if (!parsed.success) {
        throw new Error("历史响应结构不正确");
      }

      if (!response.ok || !parsed.data.ok) {
        throw new Error(
          parsed.data.ok
            ? "历史请求失败"
            : parsed.data.error.message
        );
      }

      setHistories(
        parsed.data.data.histories.map(
          parseCalculationHistory
        )
      );
    } catch (error) {
      if (
        error instanceof DOMException &&
        error.name === "AbortError"
      ) {
        return;
      }

      setError("计算历史加载失败，请稍后重试。");
    } finally {
      if (!controller.signal.aborted) {
        setIsLoading(false);
      }
    }
  }

  void loadHistories();

  return () => {
    controller.abort();
  };
}, []);
```

在另一个隔离演示数据库中准备：


```txt

```

这个错误路径证明业务编排在保护计算边界。

## 五十三、验收不支持的意图

如果 Chat service 当前只支持：

```txt

```

预期是：

```txt
UNSUPPORTED_INTENT
```

页面应该诚实提示暂不支持。

## 五十四、验收历史保存失败语义

这个场景不建议通过破坏真实数据库人工测试。

在 `chat-service.test.ts` 中注入：

```ts
saveSavingsGoalCalculation: async () => {
  throw new Error("database unavailable");
}
```

预期：

```txt
HISTORY_SAVE_FAILED
```

即使计算已经完成，接口也不能返回完整成功。

因为产品承诺包含：

```txt

```

历史未保存，就不满足完整成功条件。

```txt
客户端锁
```

## 九十八、复习问题

### 1. 单元测试和端到端验收有什么区别？

单元测试验证隔离函数或模块；端到端验收验证用户操作跨越页面、API、AI、计算和数据库后能形成完整结果。

### 2. 为什么要固定演示数据？

固定输入才能提前得到可复核预期，避免看到任何数字都误认为正确。

### 3. 为什么使用独立演示数据库？

它避免清空或污染原数据，也让演示结果更容易复现。

### 4. 为什么 Chat 演示数据必须属于当前月份？

当前上下文构造明确使用上海当前月份计算月结余。

### 5. 为什么投资账户进入仪表盘资产，却不进入 Chat 当前金额？

两个指标口径不同：仪表盘资产包含投资账户，Chat 储蓄目标当前金额只使用流动性更高的 cash 和 bank。

### 6. 为什么只看 AI 回复不能证明结果正确？

回复是自然语言展示，无法证明意图、数据库上下文、公式、历史和结构化金额正确。

### 7. 如何证明金额由代码计算？

检查受限意图类型、Chat service 调用、确定性计算结果、步骤、公式版本和不依赖模型的单元测试。

### 8. 为什么历史保存失败不能返回成功？

项目承诺结果可追溯，历史未保存意味着完整业务承诺没有完成。

### 9. 为什么历史 JSON 仍要运行时校验？

持久化数据可能来自旧版本、手工调试或损坏记录，TypeScript 不能保证数据库字符串结构。

### 10. 为什么坏历史只影响单条记录？

一条旧数据不应该阻止用户查看其他合法历史。

### 11. 为什么自动测试不能使用真实 DeepSeek？

真实网络会带来费用、波动、速度和不可重复性，普通测试应稳定且离线可运行。

### 12. 真实 DeepSeek 应该在哪里验证？

在显式、受控的人工端到端演示中验证一次。

### 13. 为什么先运行自动检查再人工演示？

自动检查能更快发现确定性问题，减少把基础错误误判为 AI 或网络问题。

### 14. 为什么不能只检查 HTTP 200？

还需要检查业务响应、数据库后果、页面结果和完整因果链。

### 15. 为什么 README 不能继续使用默认模板？

默认模板不能说明项目定位、配置、功能、口径、运行方式和限制。

### 16. `.env.example` 为什么不能包含真实 Key？

它会被提交并用于公开配置说明，真实密钥只能保存在未提交的本地环境文件中。

### 17. 为什么要记录 Git commit？

验收结果只对特定代码状态有效，版本变化后需要判断回归范围。

### 18. 为什么不能为了通过验收而修改预期？

预期来自固定输入和明确公式；迁就错误输出会让验收失去意义。

### 19. 修复现金流规则后为什么要回归 Chat 和仪表盘？

两者都消费现金流结果，修改会影响月支出、结余、储蓄率和储蓄目标输入。

### 20. MVP 完成意味着没有任何限制吗？

不意味着。MVP 完成表示约定范围内的核心链路可用、可测试、可演示，并且限制已被明确记录。

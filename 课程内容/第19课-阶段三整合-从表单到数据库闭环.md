# 第 19 课：阶段三整合：从表单到数据库闭环

## 本课目标

阶段三已经学过：

- HTTP 与 API。
- SQLite。
- Drizzle ORM。
- 财务数据模型。
- Zod 数据校验。
- CRUD。

现在要把这些内容整理成一条完整链路：

```txt
表单输入
  ↓
fetch 请求 API
  ↓
Zod 校验
  ↓
service 层处理业务逻辑
  ↓
Drizzle 写入 SQLite
  ↓
API 返回 JSON
  ↓
前端刷新账户列表
```

这一课不追求新增很多功能。

重点是让账户数据闭环稳定可用。

学完本课后，你应该能够：

- 画出账户 CRUD 的完整数据流。
- 说明前端类型、Zod schema、Drizzle schema 如何协作。
- 说明 service 层为什么存在。
- 调试 API、Zod、数据库和前端状态问题。
- 确认新增账户后刷新页面数据仍然存在。

## 一、当前页面要从本地状态切到 API

`app/dashboard/page.tsx` 当前负责账户管理。

它之前用的是：

```ts
initialAccounts
```

这种方式只适合前端练习。

现在要改成：

```txt
页面加载时请求 GET /api/accounts
提交表单时请求 POST /api/accounts
请求成功后更新账户列表
刷新页面后重新从数据库读取账户
```

页面不再自己“制造”账户数据。

页面只负责：

- 保存表单输入状态。
- 调用 API。
- 展示 loading、empty、error 状态。
- 把 API 返回的数据传给组件。

## 二、账户闭环的数据流

新增账户的数据流是：

```txt
用户填写账户名称、类型、余额
  ↓
点击新增账户
  ↓
handleSubmit
  ↓
fetch POST /api/accounts
  ↓
createAccountSchema.safeParse(body)
  ↓
createAccount(result.data)
  ↓
db.insert(accounts).values(account)
  ↓
SQLite 保存账户
  ↓
API 返回新增账户
  ↓
setAccounts([...accounts, account])
```

查询账户的数据流是：

```txt
页面首次打开
  ↓
useEffect
  ↓
fetch GET /api/accounts
  ↓
listAccounts()
  ↓
db.select().from(accounts)
  ↓
API 返回账户列表
  ↓
setAccounts(result.data.accounts)
```

这就是本阶段最重要的闭环。

## 三、三种 schema 如何协作

项目里会同时出现三类数据结构。

| 名称 | 示例文件 | 负责什么 |
| --- | --- | --- |
| 前端类型 | `types/finance.ts` | 帮 React 组件知道数据长什么样 |
| Zod schema | `schemas/finance.ts` | 校验 API 请求体是否合法 |
| Drizzle schema | `lib/db/schema.ts` | 描述 SQLite 表结构 |

以账户为例：

```txt
前端类型 Account
  用于 AccountCard、AccountList、DashboardPage

createAccountSchema
  用于 POST /api/accounts 校验用户提交内容

accounts 表
  用于 Drizzle 创建表和读写 SQLite
```

它们不是互相替代关系。

它们分别守住不同位置。

```txt
组件展示靠前端类型
请求入口靠 Zod
数据库结构靠 Drizzle
```

## 四、统一账户类型

当前数据库里的账户余额是字符串。

前端账户类型也应该和 API 返回值保持一致。

打开：

```txt
types/finance.ts
```

账户类型可以整理成：

```ts
export type AccountType = "cash" | "bank" | "credit" | "investment";

export type Account = {
  id: string;
  name: string;
  type: AccountType;
  currency: string;
  balance: string;
  createdAt: number;
  updatedAt: number;
  deletedAt: number | null;
};
```

这样组件读到的账户结构，就和数据库返回的数据一致。

如果 `AccountCard` 里还在写：

```ts
account.balance.toLocaleString()
```

需要改成适合字符串金额的展示方式：

```tsx
{Number(account.balance).toLocaleString()} 元
```

后续接入 `decimal.js` 后，可以再统一封装金额格式化函数。

## 五、整理 API 返回类型

前端调用 API 时，可以先定义一个简单类型帮助理解。

例如在页面里临时写：

```ts
type ApiSuccess<T> = {
  ok: true;
  data: T;
};

type ApiFailure = {
  ok: false;
  error: {
    code: string;
    message: string;
    issues?: {
      path: string;
      message: string;
    }[];
  };
};

type ApiResult<T> = ApiSuccess<T> | ApiFailure;
```

然后账户列表响应可以理解成：

```ts
type AccountsResponse = ApiResult<{
  accounts: Account[];
}>;
```

初学阶段也可以先不抽公共类型。

但一定要知道 API 返回结构：

```txt
成功时读 result.data
失败时读 result.error
```

不要直接假设返回结果就是数组。

## 六、改造仪表盘页面

打开：

```txt
app/dashboard/page.tsx
```

顶部需要从 React 导入：

```tsx
import { useEffect, useState } from "react";
```

移除：

```tsx
import { initialAccounts } from "@/lib/mock-data";
```

账户状态从空数组开始：

```tsx
const [accounts, setAccounts] = useState<Account[]>([]);
const [isLoading, setIsLoading] = useState(true);
const [error, setError] = useState("");
const [isSubmitting, setIsSubmitting] = useState(false);
```

页面加载时读取账户：

```tsx
useEffect(() => {
  async function loadAccounts() {
    try {
      setIsLoading(true);
      setError("");

      const response = await fetch("/api/accounts");
      const result = await response.json();

      if (!result.ok) {
        setError(result.error.message);
        return;
      }

      setAccounts(result.data.accounts);
    } catch {
      setError("账户数据加载失败，请稍后重试。");
    } finally {
      setIsLoading(false);
    }
  }

  loadAccounts();
}, []);
```

这样页面刷新后，会重新从 SQLite 读取账户。

## 七、改造表单提交

表单提交不再手动创建本地账户。

改成请求 API：

```tsx
async function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
  event.preventDefault();
  setError("");
  setIsSubmitting(true);

  try {
    const response = await fetch("/api/accounts", {
      method: "POST",
      headers: {
        "Content-Type": "application/json"
      },
      body: JSON.stringify({
        name,
        type,
        balance
      })
    });

    const result = await response.json();

    if (!result.ok) {
      const firstIssue = result.error.issues?.[0];
      setError(firstIssue?.message ?? result.error.message);
      return;
    }

    setAccounts((currentAccounts) => [
      ...currentAccounts,
      result.data.account
    ]);

    setName("");
    setType("bank");
    setBalance("");
  } catch {
    setError("新增账户失败，请稍后重试。");
  } finally {
    setIsSubmitting(false);
  }
}
```

这里不再需要前端自己判断：

```tsx
Number.isFinite(numericBalance)
```

金额是否合法交给 Zod。

前端仍然可以做基础提示，但后端校验一定不能省。

## 八、表单组件支持提交中状态

`AccountForm` 可以增加一个 prop：

```ts
isSubmitting: boolean;
```

按钮根据提交状态变化：

```tsx
<button
  type="submit"
  disabled={isSubmitting}
  className="rounded-md bg-gray-900 px-4 py-2 text-sm font-medium text-white hover:bg-gray-700 disabled:cursor-not-allowed disabled:bg-gray-400"
>
  {isSubmitting ? "提交中..." : "新增账户"}
</button>
```

页面调用组件时传入：

```tsx
<AccountForm
  name={name}
  type={type}
  balance={balance}
  error={error}
  isSubmitting={isSubmitting}
  onNameChange={setName}
  onTypeChange={setType}
  onBalanceChange={setBalance}
  onSubmit={handleSubmit}
/>
```

这样可以避免用户连续点击按钮重复提交。

## 九、处理 loading、empty、error

账户列表区域可以按顺序展示：

```tsx
{isLoading ? (
  <p className="text-sm text-gray-500">正在加载账户数据...</p>
) : (
  <AccountList accounts={accounts} />
)}
```

错误提示可以继续交给表单里的 `ErrorMessage`。

也可以在列表上方单独展示：

```tsx
{error && (
  <p className="mb-4 rounded-md bg-red-50 px-3 py-2 text-sm text-red-700">
    {error}
  </p>
)}
```

空状态由 `AccountList` 处理。

因为它已经有：

```tsx
if (accounts.length === 0) {
  return <EmptyAccounts />;
}
```

三种状态的判断顺序是：

```txt
先判断 loading
再判断 error
最后判断 empty 或正常列表
```

## 十、检查账户 API

`app/api/accounts/route.ts` 应该只保留 HTTP 相关逻辑。

结构可以是：

```ts
export async function GET() {
  const accounts = await listAccounts();

  return successResponse({
    accounts
  });
}

export async function POST(request: Request) {
  const body = await request.json();
  const result = createAccountSchema.safeParse(body);

  if (!result.success) {
    return errorResponse(...);
  }

  const account = await createAccount(result.data);

  return successResponse({ account }, { status: 201 });
}
```

API 文件不应该直接写：

```ts
db.insert(...)
```

数据库操作放在：

```txt
lib/services/accounts.ts
```

这样后续业务规则变多时，API 文件仍然清楚。

## 十一、检查 service 层

账户 service 至少需要：

```ts
listAccounts()
createAccount(input)
getAccountById(id)
updateAccount(id, input)
deleteAccount(id)
```

其中 `listAccounts()` 要排除软删除数据：

```ts
where(isNull(accounts.deletedAt))
```

`deleteAccount()` 不直接删除记录，而是设置：

```ts
deletedAt: Date.now()
```

这和第 16 课的数据模型设计保持一致。

## 十二、调试完整链路

调试时不要凭感觉乱改。

按链路一层一层查。

### 1. API 是否能返回账户

浏览器 Console 运行：

```js
fetch("/api/accounts")
  .then((response) => response.json())
  .then(console.log);
```

如果这里失败，先查 API、service、db。

不要先改页面组件。

### 2. 新增账户是否能写入

运行：

```js
fetch("/api/accounts", {
  method: "POST",
  headers: {
    "Content-Type": "application/json"
  },
  body: JSON.stringify({
    name: "工资卡",
    type: "bank",
    balance: "20000"
  })
})
  .then((response) => response.json())
  .then(console.log);
```

成功后再运行：

```js
fetch("/api/accounts")
  .then((response) => response.json())
  .then(console.log);
```

应该能看到刚才新增的账户。

### 3. 数据库里是否真的有数据

进入项目目录：

```bash
cd ai-finance-cfo
```

打开数据库：

```bash
sqlite3 data/dev.db
```

查询：

```sql
SELECT id, name, type, balance, deleted_at FROM accounts;
```

退出：

```sql
.quit
```

如果数据库有数据但页面没有，问题多半在前端 fetch 或状态更新。

如果数据库没数据，问题多半在 API、Zod、service 或 Drizzle。

## 十三、刷新页面验证持久化

这是本课最重要的验收动作。

操作顺序：

1. 打开 `/dashboard`。
2. 新增一个账户。
3. 看到账户出现在列表里。
4. 刷新浏览器页面。
5. 账户仍然存在。

如果刷新后数据消失，说明页面还在使用本地状态或假数据。

真正的数据持久化必须经过：

```txt
POST /api/accounts
  ↓
SQLite
  ↓
刷新后 GET /api/accounts
```

## 十四、常见问题定位

### 1. 表单提交成功但刷新消失

检查 `handleSubmit` 是否只是：

```tsx
setAccounts([...accounts, newAccount])
```

如果只是更新前端状态，没有请求 API，就不会保存到数据库。

### 2. API 返回 VALIDATION_ERROR

查看返回的：

```txt
error.issues
```

常见原因：

- `name` 是空字符串。
- `type` 不是允许值。
- `balance` 不是标准金额字符串。

### 3. 数据库提示表不存在

运行：

```bash
npx drizzle-kit push
```

然后用：

```sql
.tables
```

确认表存在。

### 4. 页面类型报错

检查 `types/finance.ts` 是否和 API 返回结构一致。

尤其注意：

```txt
balance 是 string
createdAt 是 number
currency 是 string
```

### 5. 删除后仍然能查到数据

软删除不会从数据库中移除记录。

它只是设置 `deleted_at`。

列表接口必须过滤：

```txt
deleted_at 为空
```

## 十八、验收标准

完成后检查：

- 新增账户后，列表立即显示新账户。
- 刷新页面后，新账户仍然存在。
- `GET /api/accounts` 返回 SQLite 中的账户。
- `POST /api/accounts` 会经过 Zod 校验。
- 非法请求会返回 `400 VALIDATION_ERROR`。
- 页面加载中有 loading 状态。
- 账户为空时有 empty 状态。
- API 请求失败时有 error 状态。
- 代码中 API、schema、service、db 分层清楚。
- 能画出账户 CRUD 数据流。
